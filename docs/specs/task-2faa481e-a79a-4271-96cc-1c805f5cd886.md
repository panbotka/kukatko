# Storage move: failed derived-object moves are retryable and visible

When a thumbnail, HLS or sidecar copy fails after the original's row was committed (R2 429/5xx is not treated as systemic), the photo is counted as done, the old original deleted, and its derived objects stay orphaned at the root. Signed thumbnail URLs then point at keys that do not exist (blank tiles, HLS 404s), `Retry` never revisits the photo (it only re-takes photos still in the old layout), and the error ring keeps the last 50 entries only. Nothing in the UI shows it.

## Context (verify with rg before starting)
- `internal/rekey/step.go` `completePhoto` (~185–210): derived failures are logged, the photo completes, the old original is deleted.
- `internal/rekey/store.go` (~89–104): the pending/retry query selects photos whose `file_path` still lacks the prefix; the error ring is capped at 50 (~133–141).
- Heal paths exist but are manual: `/process/thumbnails` backfill (plan checks the bucket under the new prefix) and `maintenance repair` MissingRenditions + encode backfill.
- Progress UI: `web/src/pages/SystemProjectPage` (or the storage card component) reads `GET /projects/{uid}/rekey`.
- Runbook: `docs/OPERATIONS.md` "kukatko storage rekey".

## Requirements
- A derived-object move failure is recorded durably per photo (a new column or table keyed by photo uid, listing the failed derived kinds), the photo still completes (the original is safe either way) and the old derived objects are NOT deleted for that photo.
- `Retry`, a resume, and every further pass of the job re-plan the derived moves for photos with recorded derived failures (and for any photo whose `file_path` is prefixed but whose root derived keys still exist), delete the root copies only after the prefixed copies exist, and clear the record on success. A run ends `done` only when no derived failure remains; otherwise it ends with a distinct state or a non-zero `derived_failed` count that `--status`, the API and the storage card show, with a "retry" affordance.
- `kukatko maintenance scan` reports derived objects at the root for a prefixed photo (bucket listing, not the local thumbnail cache) under a named check, and `repair` can move them.
- Unit tests: a derived copy failure keeps the root tiles, a later pass moves them, the count drops to 0. Integration test for the store's new query.
- Runbook additions in `docs/OPERATIONS.md`: pre-move checks (`file_size > 0` and a 64-hex `file_hash` on every row of the project; no original over 5 GiB — those cannot be server-side copied and block `done`), a short note that old keys have no grace period (an open tab may 404 on tiles until reload), that `kukatko backup` should run right after `done` and the pre-move dump is kept as the only rollback, and that a run stuck `running` after a dead-lettered job is unstuck with `--pause` then `--resume`.

## Out of scope
- Multipart server-side copy for > 5 GiB objects (separate task if production has any).
- Changing the move's per-photo order or rate.
