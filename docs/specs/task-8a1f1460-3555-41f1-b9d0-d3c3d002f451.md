# The photo viewer's autocomplete renders its suggestion list off-screen

Regression found in the pre-release walkthrough of `ea97e70` (the v0.22.0 range), introduced by
`606b1f3 fix(family): show the whole suggestion list in the add-relative dialog`.

**Severity: BLOCK-level.** Adding a photo to an album or attaching a label from the photo
detail — a core curation path — shows the user nothing at all on desktop.

## Symptom

Desktop 1440x900, signed in, open any photo, click **Informace**, type `Panor` into
*Přidat do alba*. No suggestion list appears anywhere on screen, even though the album
"Panorama" exists and matches. Same for *Přidat štítek*.

Screenshot: `/mnt/nas-botka/kukatko/prerelease-ea97e70/BLOCK-autocomplete-offscreen.png`
(user typed "Panor", nothing is rendered).

## Cause (measured on staging)

`useAnchoredMenu` measures the anchor with `getBoundingClientRect()` — viewport coordinates —
and applies them as `position: fixed` offsets:

    web/src/hooks/useAnchoredMenu.ts:74-79
    const rect = element.getBoundingClientRect()
    setPosition({ top: rect.bottom + GAP, left: rect.left, width: rect.width, maxHeight })

That is only correct when no ancestor establishes a containing block for fixed positioning.
The photo viewer's info panel does:

    <aside class="kk-viewer__panel is-open">  ->  transform: matrix(1, 0, 0, 1, 0, 0)

**Any** transform value other than `none` — an identity matrix included — makes that element
the containing block for `position: fixed` descendants. Measured:

    inline style : position: fixed; top: 704.75px; left: 1041px; width: 368px
    actual rect  : left = 2066   (viewport is 1440 wide)  -> ~1025px off-screen right
    input rect   : left = 1041   (the aside starts at x ~= 1025)

The hook's own doc comment reasons about `overflow: auto` ancestors but not about transformed
ones, which break `position: fixed` outright.

## Scope (all verified on staging ea97e70)

- **Broken:** `OrganizePanel` inside `aside.kk-viewer__panel` — both *Přidat do alba* and
  *Přidat štítek*. Desktop only.
- **Not broken:** the add-relative dialog (R5's actual target) — menu anchored correctly at
  left 480 = input left 480, 282px tall, nothing clipped. `MySubjectCard` on /account —
  menu left 412 = input left 412.
- **Not broken on mobile:** at 390px the hook takes its `position: static` in-flow branch,
  which does not depend on the containing block. Verified: menu at left 12, w 366, inside
  viewport.
- **Partial workaround that still works:** keyboard selection. Typing then `ArrowDown` +
  `Enter` does attach the right item (verified: `POST /api/v1/labels/{uid}/photos` -> 204).
  So the data path is fine; the list is simply invisible to a mouse user.

## What to do

Make the desktop overlay survive a transformed ancestor. Options worth weighing:

1. Subtract the containing block's origin: walk up for the nearest ancestor whose computed
   `transform`/`filter`/`perspective`/`will-change`/`contain` is not `none`, and offset
   `top`/`left` by its `getBoundingClientRect()`.
2. Portal the menu to `document.body` so no transformed ancestor is between it and the
   viewport — simplest and removes the whole class of bug.

Whichever is chosen, it must keep R5's original fix intact (the add-relative dialog's list
must stay unclipped) and keep the phone's in-flow branch untouched.

## Acceptance

- In the photo viewer's info panel, typing in *Přidat do alba* and *Přidat štítek* shows the
  suggestion list anchored under the input, fully inside the viewport.
- The add-relative dialog, `MySubjectCard`, `AttachPersonField` and `MultiSelect` are all
  still correctly anchored (regression-test the four callers).
- A test covers the transformed-ancestor case specifically — e.g. render the anchored menu
  inside a wrapper carrying `transform: translate(0,0)` and assert the menu's resolved
  position matches the anchor's, so this cannot come back silently.
- `make check` passes.

## Notes

- Reproduce at desktop width; at <= 576px the bug is invisible because the other branch runs.
- Probe recipe used: read `getComputedStyle(menu).position` + `menu.getBoundingClientRect()`
  and compare against the inline `style` attribute — the mismatch between the two is the
  whole finding.
