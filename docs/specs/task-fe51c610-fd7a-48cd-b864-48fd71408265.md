BLOCKER for the PhotoPrism cutover. Full evidence: docs/READINESS_AUDIT.md §2.1.

## The defect

internal/photoprism/photoprism.go:126 sets `merged=true` on every photo listing so each
photo carries its Files[]. PhotoPrism then collapses several file rows into one photo
entry, so a merged page is ALWAYS shorter than the requested count. Measured against the
production library (fotky.kotrzina.cz, count=1000):

    offset=0    no merged   -> 1000 rows
    offset=1000 no merged   -> 1000 rows
    offset=0    merged=true ->  914 rows
    offset=1000 merged=true ->  987 rows
    offset=2000 merged=true ->  996 rows

Every loop over ListPhotos terminates with `if len(page) < pageSize { return nil }`, so it
reads the FIRST page as the end of the library and returns success.

## Sites to fix (all four)

- internal/ppimport/photos.go:69     - the full photo import: imports ~900 of 20 670 and
                                      reports done
- internal/ppimport/organize.go:182  - album membership: an album past one page loses the rest
- internal/ppimport/organize.go:318  - label membership: same
- internal/importverify/importverify.go:250 - source enumeration for the completeness check:
                                      reconciles against ~994 instead of 20 670

Do NOT touch the loops over ListAlbums / ListLabels / ListSubjects
(organize.go:70,111,233,254 and people.go:199). Those endpoints take no `merged` parameter,
return full pages, and are correct as they stand.

## Why this is the top priority

The verifier has the same blindness as the importer, and `kukatko import verify` is the
phase-4 gate in docs/MIGRATION_PLAN.md that guards the point of no return. After a full run
it would compare ~900 imported photos against ~994 "source" photos and could report the
library COMPLETE while 19 700 photos are missing. Nothing else about the migration can be
trusted until this is fixed.

## Fix direction

Terminate on `len(page) == 0`, not on a short page. A short page is not evidence of
exhaustion for any endpoint that filters or merges server-side. Keep advancing the offset by
len(page) as today. Watch for a non-terminating loop if the source ever returns a page
without advancing — an offset that stops moving must also end the loop.

## Verification (mandatory)

- Unit tests with a fake PhotoPrism source that returns SHORT non-empty pages followed by an
  empty one, asserting the loop reads every page. A test that only returns full pages would
  pass against the current buggy code and is worthless here.
- One test per fixed site.
- `make check` green.
