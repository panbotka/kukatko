# Record whether an account is approved and whether it has seen the welcome

Two facts about an account have nowhere to live: whether an administrator has approved it
(self-service registration will create accounts that wait), and whether the person has
already been shown the first-run welcome.

## Requirements

- A migration adds two nullable timestamp columns to `users`:
  - when the account was approved — `NULL` means "registered, waiting for an
    administrator"
  - when the person last dismissed or completed the welcome — `NULL` means "never seen"

  Every account existing when the migration runs is backfilled as **approved**, because it
  was created by an administrator. The welcome column stays `NULL` for everybody.
- An account created through the admin API is approved immediately: an administrator
  creating an account *is* the approval.
- The approval timestamp must stay distinguishable from the existing `disabled` flag
  everywhere it is read. "Never approved" and "approved and later blocked" are different
  states and the user listing must be able to tell them apart.
- `GET /auth/me` reports whether the signed-in account has seen the welcome, alongside the
  subject link it already returns.
- `POST /auth/welcome-seen` — any authenticated role — stamps the welcome column with the
  current time. Calling it again is harmless and never moves the timestamp backwards.
- The admin user listing returns the approval timestamp for every account.

## Definition of done

- Integration tests against the real test database cover: the backfill marking existing
  accounts approved, an admin-created account being approved on creation, the welcome
  endpoint stamping once and being idempotent, and `GET /auth/me` reflecting it.
- `docs/API.md` documents the new endpoint and the new fields.
- `make check` passes.
