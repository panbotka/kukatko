Round-2 review of the multi-tenancy programme (2026-10-14, main 672357f6). Report: `/mnt/nas-botka/kukatko/multitenancy-review-2/fixes-review.md` §B2 and §B3. Design spec: `docs/superpowers/specs/2026-10-11-multi-tenancy-design.md`. Verify with `rg` that it still holds.

Finding: the upload pipeline's near-duplicate warning (`internal/ingest/ingest.go` ~744-757 → `internal/photos/store_extras.go` ~170-174) searches the pHash table across every project. A member — or an anonymous uploader on a public upload link — who uploads an image similar to a photo of another project gets a warning naming that photo's uid. On by default. Must be fixed before a second real project is created. The tenancy guard cannot see this shape: a whole-table scan over a child table like `photo_phashes` (B3).

## Requirements
- The near-duplicate lookup at ingest (and any other pHash / embedding neighbour lookup reachable from ingest or uploadlinkapi) joins to `photos` and filters on the uploader's project. Check the exact-SHA256 dedup path too: a byte-identical file already in another project must not be reported as a duplicate of a foreign photo, and must not be silently "deduplicated" into the other project (it must be ingested into the uploader's project as its own photo, or refused with a neutral message — check what the design spec says about cross-project file_hash uniqueness and follow it).
- Integration tests (projecttest): an image near-identical to A's photo uploaded into B → no warning naming A; the upload-link path too; a byte-identical file in B. Must fail on the current code where it leaks.
- If feasible within reason, extend `internal/tenancyguard` to flag a SELECT over a known child table of a root table (`photo_phashes`, `embeddings` etc.) with no join to its parent carrying a `project_id` predicate; otherwise allow-list the remaining legit cases with reasons and note the limitation in docs/PACKAGES.md.
