# Tasks: whose turn is it

The task queue (`internal/phototask`, `internal/phototaskapi`, `kukatko ctl tasks`, `/tasks` in the web) is used as a conversation between an AI agent (account `panbotka`, working through `kukatko ctl`) and a human. The agent opens questions, the human answers in the thread; the agent polls `tasks list --answered` to find replies. Today the "somebody answered" signal is wrong and neither side has a reliable "what waits on me" view.

## What is wrong today

- `has_new_answer` (computed in the store's task columns as `last_comment_at > state_at`) ignores **who** wrote the comment. When the agent adds a context comment to its own `working` task, its own listing shows `NEW = yes` and `--answered` returns that task; the human sees a "Nová odpověď" badge for their own reply. Live example on production: task `tk3ksfcn5e8h8k4c1353fc3pi0` has exactly one comment, written by its author, and is listed as answered.
- Nobody records who moved the state last (`state_at` exists, `closed_by` exists, but there is no `state_by`), so "the other side acted after me" cannot be answered.
- Participants carry `added_by` (asked) vs NULL (acted), but an asked row never turns into an acted one, so "asked and I have not touched it yet" is not derivable either.

## Requirements

- `has_new_answer` becomes **relative to the caller**: true when a live (not soft-deleted) comment written by somebody **other than the caller** was created after `state_at`. Same semantic in the listing, the detail, the `answered=` list filter and `tasks list --answered`. The ctl `NEW` column and the web "Nová odpověď" badge keep working unchanged, they just stop lying.
- Add `state_by` to `photo_tasks` (nullable user uid, `ON DELETE SET NULL`): set on every state change in the same transaction as `state_at`; existing rows may stay NULL (treat NULL as the creator).
- Every task read (listing and detail) carries three new read-only fields: `last_activity_at`, `last_activity_by` (user uid, may be empty), `last_activity_by_name`. Last activity is the newer of: the last state change (`state_at` / `state_by`), the task's creation, and the newest live comment on the task (by its author). Photo additions/removals and participant changes do not count as activity.
- Every task read carries a per-caller boolean `waiting_on_me`: the task is open (`question`, `working`, `review`), the caller is a participant, and `last_activity_by` is not the caller (an empty `last_activity_by` counts as "not me"). For somebody who is not on the task it is always false. A task the human just opened and assigned to the agent therefore waits on the agent; after the agent comments it waits on the human; after the human replies it waits on the agent again.
- List filter `waiting=1` (same boolean parsing as `open`/`answered`): only tasks with `waiting_on_me` true for the caller. Combinable with `state`, `q`, `participant`. Because it is caller-relative it must be evaluated server-side, never by post-filtering a page.
- `kukatko ctl tasks list --waiting` maps to it. `tasks show` prints a `Last activity` line ("2026-09-19 17:21 by Tomáš Kozák") and a `Waiting on you` line (`yes`/`no`). The `-o llm` output includes the new fields.
- The web queue (`web/src/pages/TasksPage.tsx`) gets a chip "Na mně" (en: "On me") bound to `waiting=1`, URL-persisted like the existing `answered`/`mine` toggles. Each row shows the last activity in the metadata line ("naposledy Tomáš Kozák · před 2 h") so the reader sees whose move it is without opening the task.
- Audit: no new audit actions; the state change entry that already exists is enough.

## Edge cases

- Soft-deleted comments never count, for either flag.
- A closed task can never be `waiting_on_me`, even if someone comments on it afterwards; `has_new_answer` may still be true on a closed task (a late reply is worth seeing).
- A viewer (read-only role) can comment, so a viewer's reply must flip `has_new_answer` for everybody else and clear their own `waiting_on_me`.
- The `whatsnew` counter and anything else reading `photo_tasks` must keep compiling; grep the repo for `has_new_answer` and `state_at` before you finish.
