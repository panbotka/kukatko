# 450 photos are missing from the production catalogue and the import reported success

The full PhotoPrism import finished on 2026-08-02 reporting
`imported=20197 updated=1 skipped=704 failed=0`, with an empty `import_failures`
table. `kukatko import verify` then said:

```
PhotoPrism photos: source=20660  kukatko=20197  deduplicated=13  missing=450
albums 437/437   labels 113/113   people 104/104
```

`20 197 + 13 + 450 = 20 660`. **450 source photos never reached the catalogue and the
run called itself clean.** The owner wants every photo; this is the highest-value
defect on the list.

## Root cause

`internal/ppimport/photos.go:254-257`, in `catalogue`:

```go
created, err := s.photos.Create(ctx, photo)
if errors.Is(err, photos.ErrFileHashTaken) {
    return photos.Photo{}, false, nil
}
```

`ErrFileHashTaken` is a `photos.file_hash` unique-constraint violation
(`internal/photos/store.go:139`) — the identical content is already catalogued.
Kukátko deduplicates on SHA256 while PhotoPrism keeps the same bytes as two photo
entries, so meeting this is expected. What the path does with it is not:

- it returns `(false, nil)`, so `importNew` returns `outcomeSkipped, nil`
  (`photos.go:205-206`) and `importOnePhoto` counts it as `Skipped` — the same
  bucket as a legitimate "nothing changed";
- **nothing is logged**;
- **no failure is recorded**, hence `failed=0` and an empty `import_failures`;
- and the source photo's identity is dropped on the floor.

The comment above `catalogue` explains how it got there: the swallow was written for
"a unique-content race (the same bytes catalogued **concurrently**)". The import is
sequential, and 450 occurrences are not races — the exception became the normal path.

**What is actually lost is not pixels.** The content is in the catalogue under the
row that won the race for that hash. What is lost is the second photo's *identity*,
and with it everything that hangs off the identity: its albums, its labels and its
face markers, because `importPhotoDetail` has no row to attach them to. It is also
invisible to `import verify` and to the photo-sorter feeds, which match on
`photoprism_uid`.

## The hard part — read before designing

**The data model cannot currently express this.** Measured on production:

```
idx_photos_photoprism_uid ON photos (photoprism_uid) WHERE photoprism_uid IS NOT NULL
   -- a plain partial index, NOT unique
columns named photoprism_uid anywhere in the schema: 1  (photos.photoprism_uid)
```

One row carries exactly one `photoprism_uid`, and there is no mapping table. So for
these 450 the obvious fix — "do what `dedupByContent` does and call
`SetPhotoprismRef`" — **does not work**: the surviving row already holds the *other*
photo's uid. That is precisely why `dedupByContent` guards with
`if existing.PhotoprismUID == nil` (`photos.go:228`); it cannot overwrite either.
The 13 it did heal were rows that had no uid yet (content that arrived from
elsewhere). None of the 450 are in that state.

So this task has a design decision at its centre, and it must be made explicitly:

- **A mapping table** (`photoprism_uid → photo_uid`, many-to-one) that lets one
  catalogue row answer to several source identities. This is the complete answer:
  verify can reconcile, the feeds can match, and the duplicate's albums, labels and
  markers can be attached to the surviving row. It costs a migration and every
  reader of `photoprism_uid` has to learn about it.
- **Or** accept that duplicates collapse, and record the alias in a way that at
  minimum makes the outcome *visible and reconcilable* rather than silent.

Pick one, justify it, and say what it costs. Do not patch the symptom.

## Also settle this

`dedupByContent` and `Create` both key on `photos.file_hash`, so the pre-check should
have caught these before the download and taken the (guarded) correct path. It ran
for 13 and missed 450 — find out why:

- Does the hash used for the pre-check (`staged.hash`) differ from the one inserted
  (`stored.Hash`, via `storeOriginal` → `buildPhoto`)?
- Or does `GetByFileHash` filter rows the unique constraint does not (archived, stack
  members)?

State what you found and how you proved it.

## What to build

1. **Resolve the identity problem** per the decision above, so a source photo whose
   content is already catalogued still ends up findable by its own uid, with its
   albums, labels and markers attached.
2. **Count it as its own outcome**, not as `Skipped`. The run summary must
   distinguish "already up to date" from "content already present" from "dropped".
3. **Record and log anything dropped.** No path may leave the catalogue short while
   reporting `failed=0`.
4. **Heal the existing library.** 450 photos are affected in production *now*. After
   the fix, a re-run of the incremental import must bring `import verify` to
   `missing=0`. Verify that rather than assuming it; if a re-run cannot heal them,
   provide the repair path and say so plainly.

## Sequencing note (for context, not a constraint on you)

The photo-sorter feeds import carries **no incremental cursor** — every run scans the
whole feed and a photo it cannot find is merely `Skipped`
(`internal/psfeedsimport/psfeedsimport.go:26`). So the operator may run phase 3
before this fix lands; re-running it afterwards will pick the healed photos up. Your
fix does not need to preserve any feed state.

## Verification

- An integration test reproducing the exact shape: two source photos with
  byte-identical content, imported in one run, where the second must remain findable
  by its own `photoprism_uid` and its albums/labels/markers must land on the
  surviving row.
- A test that a photo which genuinely cannot be catalogued lands in `import_failures`
  and makes the run non-clean.
- Re-run `import verify` against the fixture and assert `missing=0`.
- `make check` **and** `make test-integration` must pass.

## Production constraints

Kukátko is live at https://kukatko.kotrzina.cz with the real library.

- **Do not touch the production instance, its database or its bucket.** The numbers
  above are already gathered; the operator will re-run the import after deploying.
- Migrations run automatically at startup, each in its own transaction, against
  ~20 000 photos. No destructive DDL, no long locks. `CREATE INDEX CONCURRENTLY`
  cannot run inside a transaction and is therefore unavailable.
- **Never write a path that drops or rewrites originals or R2 objects.**
- **Do not run `make dev`** — it binds the port of the developer's own instance.
- The deployed image is pinned and there is no auto-updater, so merging does not
  deploy.
