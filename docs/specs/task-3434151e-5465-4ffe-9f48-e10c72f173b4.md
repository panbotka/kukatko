# System administrators are invisible inside a project

Only a handful of people will ever hold the instance-level **system administrator** role (`maintainer`). The direction of the product is that people get their own project and run it themselves; they must not even learn that system administrators exist. Today project-facing screens leak the role. The clearest case is the project's member list (`/p/<slug>/members`, `web/src/pages/MembersPage.tsx`): a maintainer's membership shows "Správce systému" with an explanation instead of a role select, and the members API carries `maintainer: true` (`internal/memberapi/handlers.go`, the `Maintainer` field) and refuses role changes with 409 `maintainer`.

## Requirements

- **Members page and members API (`/api/v1/p/{project}/members`):** a maintainer who is a member of the project is listed like any other member, with their stored project role, a normal role select and the normal remove action. The `maintainer` field disappears from the project-scoped response, and so does the 409 `maintainer` refusal on role change and removal. Changing or removing the stored membership is allowed: the maintainer's instance-wide access does not depend on it. The existing guards still apply (never your own role, last-admin guard counts real stored admin memberships).
- A maintainer who is **not** a member of the project never appears in its member list, member directory (`GET /p/{project}/users`), mention autocomplete, task assignee pickers or any other people list of the project. Check that the maintainer's implicit access does not add them anywhere.
- **No project-facing text names the role.** Find every user-visible string that mentions "správce systému" / "system administrator" (cs and en locales) on screens an ordinary member can reach, and reword it neutrally. In particular:
  - `ForbiddenPage`: today it says "Na tuhle část potřebujete roli správce systému — požádejte o ni někoho, kdo ji už má". It should say only that the page is not accessible, with the way back to the library.
  - `AccountPage`: a non-maintainer sees no instance role at all, only their project roles.
  - `HelpPage` and the role explanations shown to members: describe the project roles (viewer, curator, editor, admin) only. Maintainer-facing help may stay, but only rendered for a maintainer.
- Project-scoped API responses (members, users directory, `/auth/me` as seen by a non-maintainer, comments, tasks, audit as seen by a project admin) never carry a flag or role value that reveals another account is a maintainer. A maintainer's own `/auth/me` keeps telling the client that it is one, because the client needs it for the `/system` screens.
- Instance-level screens (`/system/*`, `/api/v1/projects`, `/api/v1/users`) keep showing and managing the role; nothing changes there.
- Tests: Go API tests for the members endpoint (a maintainer member listed with a plain role, role change and removal allowed, no `maintainer` key, a non-member maintainer absent from the list and the directory). Vitest for MembersPage (maintainer row looks like any member), ForbiddenPage text, AccountPage without the instance role for a non-maintainer. Grep-level check that no cs/en string reachable by a non-maintainer names the system administrator role.
- Update `docs/API.md` (members API shape, removed 409) and `docs/FRONTEND.md`.
