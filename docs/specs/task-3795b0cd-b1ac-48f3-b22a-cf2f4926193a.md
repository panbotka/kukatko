# The clusters page rebuilds everything per request and never finishes

The "Skupiny obličejů" page (`/people/clusters`) does not load on the production library of
roughly 20 700 photos. Measured on the live instance: the spinner ran for several minutes, the
tab's main thread stopped answering, and the renderer process eventually crashed.

The clusters themselves are **already stored** — `face_clusters` has existed since migration
0010 and `faces.cluster_uid` points into it — so this is not about persisting a computation.
Two things are actually wrong:

- **The read rebuilds the whole view every time.** The per-cluster view is assembled per
  request in `internal/cluster`: one face-listing query per cluster **plus one HNSW vector
  search per cluster** for the name suggestion. That N+1-plus-vector-search over every cluster
  in the library is the cost the page waits on.
- **Nothing is paginated.** `web/src/pages/ClustersPage.tsx` issues a single unbounded load on
  mount and holds every cluster in component state, so even a fast response would render a
  whole library's worth of groups at once.

Separately, reclustering is triggered synchronously by an HTTP request
(`internal/processapi` handles a recluster call inline), which is the other way this work can
tie up a request for minutes.

The instance is live, so the change must be production-safe and read-only in effect: browsing
must never assign a face to anyone.

## Requirements

- Opening the page renders usable content within a few seconds on a library of this size.
- Serve the listing in bounded pages, and render it incrementally: the first groups appear as
  soon as they arrive and more load as the reader goes on. The page must never hold or mount
  the entire set at once.
- Take the expensive per-cluster work off the request path. The examples and the name
  suggestion for a cluster should not be recomputed for every viewer on every visit — cache
  them, or store them alongside the cluster, and refresh them as background work.
- Move reclustering to the job queue rather than running it inside the HTTP request that asks
  for it. Adding a job type is routine here: follow how an existing handler is registered, and
  remember the queue panel's label map and both i18n files carry a name per job type.
- While a result is still being prepared, say so in the reader's own words — for example how
  many groups are ready — instead of an unbounded spinner.
- If results cannot be produced, explain and offer a retry; never spin forever.

## Implementation notes

- If any new table is introduced, it must be classified in `internal/reset/tables.go`; an
  unclassified table makes the library reset abort with a schema-drift error and the
  integration tests fail. A new column on the existing `face_clusters` avoids that entirely.

## Edge cases

- Clustering has never run for this library.
- No unnamed faces at all — an empty state, not a spinner.
- A cluster consumed (named) by another user while the reader is paging.
