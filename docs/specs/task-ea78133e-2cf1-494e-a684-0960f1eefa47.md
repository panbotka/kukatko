# Close the anonymous login-guessing chain (SEC-001 + SEC-006)

Two findings from `docs/SECURITY_AUDIT.md`, both re-verified as still open on 2026-08-12, compose into a working online password-guessing attack. They are the only anonymous, pre-authentication findings in the whole audit, so they are fixed together.

## SEC-001 (HIGH) — a client-supplied header defeats the brute-force limiter

- `internal/server/server.go:89` — `router.Use(middleware.RealIP)` with no allow-list, so any client can set its own apparent IP.
- The rate limiter keys on that value: `internal/ratelimit/ratelimit.go:186-195`, used by `internal/auth/handlers_auth.go:50-56,78` and `internal/auth/handlers_apitoken.go:54`.
- The audit trail records the same forged value: `internal/audit/audit.go:369-375`.
- A repo-wide grep for `trusted_prox` / `TrustedProx` returns nothing — there is no allow-list anywhere.

A rotating `True-Client-IP` header therefore yields a fresh limiter bucket per request. Traefik does not strip that header by default, so the reverse proxy is not a mitigation. bcrypt cost 12 is the only remaining brake.

## SEC-006 (rated LOW, behaves worse in combination) — a timing oracle hands over valid usernames

`internal/auth/service.go:66-75` returns early for an unknown user (`:68-69`) and for a disabled one (`:73-74`), both before `CheckPassword` at `:76`. The response-time difference distinguishes real accounts anonymously — which supplies exactly the input SEC-001 lets an attacker try without limit.

## Requirements

- The apparent client IP is only taken from a forwarding header when the immediate peer is a trusted proxy; otherwise the real socket address is used. The trusted set is configurable, with a safe default, and the new key is added to the `Config` struct, `setDefaults`, `config.example.yaml`, the tests and `docs/OPERATIONS.md` together.
- Login failures are additionally counted per username, independent of IP, so a rotating header cannot reset the count.
- The audit trail and access log record the same trustworthy address.
- Login takes indistinguishable time for an unknown user, a disabled user and a wrong password — a dummy password comparison on the early branches is the usual approach.
- Tests: a forged forwarding header from an untrusted peer does not reset the limiter; a trusted proxy's header is still honoured; the three login-failure paths do not differ measurably in timing.
- Update both findings in `docs/SECURITY_AUDIT.md` to FIXED with the file:line of the fix.

## Constraints

- **No mutable operations against production data.** Do not touch, reconfigure or restart the live instance. Everything is proven locally against the test database.
- Deployment implications (whether the VPS proxy needs to be in the trusted set) belong in `docs/OPERATIONS.md`, not in a config change applied to production.
- `make check` must pass. `make check-box` runs the same gate on the build box and is much faster.
