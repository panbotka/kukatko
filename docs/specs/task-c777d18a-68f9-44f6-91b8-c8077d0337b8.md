# An editor reads the photo panel through a hedge of prompts

Open a photo whose description was never written and the info panel does not say "no
description" — it says "Co se na fotce děje a proč stojí za zapamatování". The panel an editor
reads is padded with instructions for filling it in, so the few facts the photo does carry are
buried among the ones it does not.

## Evidence (read from the code on 2026-08-12)

- `EditableField` (`web/src/components/photo/MetadataPanel.tsx:135`) already branches on role.
  A **viewer** with an empty value gets `return null` — the row is not rendered at all. An
  **editor** always gets the button, and when the value is empty its body is the `prompt`, in
  italic secondary (`:152-158`). So this is editor-only, and the read-only side is already right.
- Five fields do this: title, description, AI note, capture date and one more, all rendered at
  `:874-908`. The five `*Prompt` strings exist nowhere else in `web/src`.
- **The trap.** `startEditing` is reachable from exactly six places: those five field buttons
  and the location pencil at `:926`. Hide the empty fields and a photo with no metadata at all
  leaves the location pencil as the only entrance — a pencil next to the word "Poloha" that in
  fact opens a form editing every field. Fixing the panel without adding a way in would make a
  bare photo practically uneditable.
- `EditableField` decides emptiness with `value.trim() !== ''` (`:137`), while `MetaField` uses
  the shared `metaValue`, which also drops the importers' literal `Unknown`. The two disagree:
  a description imported as `Unknown` renders as real content here.

## Requirements

- In the panel's **reading** state, a field with no value is not rendered — for every role,
  the editor included. What is left is what the photo actually says.
- In the panel's **editing** state, every field is rendered, empty ones included, each with its
  prompt. That is where the prompts belong and where they keep earning their place; none of the
  translation strings are deleted.
- An editor keeps an obvious, always-present way into editing that does not depend on any field
  being filled in. A photo with no metadata whatsoever must be as easy to start filling in as a
  photo that already has a title — and the way in must be recognisable as "edit this photo's
  information", not inherited from the location row's pencil.
- Emptiness is decided **once**, by the rule the rest of the panel already applies: absent,
  blank and the importers' `Unknown` all count as empty. `EditableField` and `MetaField` must
  not disagree about what an empty field is.
- The location row is unaffected: it renders a map and a place lookup rather than a text value,
  and its own pencil stays where it is.
- Tests: a viewer and an editor both see an empty field omitted while reading; the editing form
  still offers every field with its prompt; the entry point into editing is present on a photo
  with no metadata at all; and a field whose stored value is `Unknown` is treated as empty.

## Out of scope

- `MetaField` and the technical-details table — they already omit empty rows, and this change
  must not alter what they render.
- The organize panel (albums, labels), the people panel and the comment thread.
- Rewording any label or prompt, and any change to what the editing form saves.

## Implementation notes

- The two states are already distinct: the editing branch returns early around `:860` with its
  own form and a portalled footer, and everything from `:872` down is the reading state. The
  split this asks for follows that seam rather than introducing a new one.
- `metaValue` lives in `web/src/lib/photoFacts` and is what `MetaField` calls; reuse it rather
  than re-implementing the `Unknown` rule beside it.
- Whatever becomes the way into editing should carry a `title` as well as an accessible name —
  the icon-only sweep in the previous release set that expectation for every icon control.
