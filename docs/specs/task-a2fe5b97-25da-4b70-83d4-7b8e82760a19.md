# The store-walking tools understand projects

## Context

Kukátko is multi-tenant. `internal/storekeys` classifies both layouts (root for the bootstrap project `v`, `projects/<uid>/` for others) and returns the project uid; derived keys follow their original's layout. `internal/project` has `Store`, `Usage`; catalogue tables carry `project_id`. Design: `docs/superpowers/specs/2026-10-11-multi-tenancy-design.md`, sections 2.6 and 5.2; read `docs/PACKAGES.md` for `internal/maintenance`, `internal/backup`, `internal/storagemigrate`, `internal/reset`. Step 32 of 40. Rule unchanged: **maintenance never deletes originals.**

## Requirements

- `internal/maintenance` scan/repair: lists the whole store once, classifies each key with its project, compares against the catalogue **per project**, and reports per project (missing originals, orphan objects, missing thumbnails…). An object under `projects/<uid>/` whose project does not exist is reported as `orphan_project`. A root-layout object while `v` already has a non-empty prefix (i.e. after the move) is reported as `legacy_layout` — a maintainer decides. The `/maintenance` page and `GET /maintenance` show the per-project breakdown.
- `internal/backup`: classification (`backup/classify.go`) covers prefixed originals, sidecars and `families.yaml`; the restore path round-trips both layouts (extend the backup/restore integration test with a prefixed project).
- `internal/storagemigrate` (fs → r2): preserves keys including prefixes (test).
- `internal/reset` (`kukatko maintenance reset`): the instance wipe deletes both layouts within Kukátko's own prefixes (and `projects/`), still never touching accounts/announcement/audit/migrations.
- New CLI `kukatko project purge <slug>`: **dry run by default** (prints the per-table row counts and the object count/bytes under the prefix it would delete, on stderr), `--yes` plus the slug typed again as `--confirm <slug>` to execute; refuses the bootstrap project unless `--allow-bootstrap`; refuses a project with an empty `storage_prefix` (it cannot delete "the root"); executes `DELETE … WHERE project_id` over the catalogue tables in FK order inside one transaction (reuse `internal/reset`'s table list, filtered to catalogue tables), deletes `project_members`, `project_invites`, then the project row, then the object-store prefix; audited (`project.purge`); writes a report.
- Tests: scan over a fake store with mixed layouts (per-project report, `orphan_project`, `legacy_layout`); backup classification; storagemigrate prefix; purge dry run vs execute on the test DB + fake storage (A purged, B intact, bootstrap refused, empty prefix refused).
- Docs: `docs/OPERATIONS.md` (`project purge`, scan report fields), `docs/PACKAGES.md`, `docs/RESTORE.md`.
