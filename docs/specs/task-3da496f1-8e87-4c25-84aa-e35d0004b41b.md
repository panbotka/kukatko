# Half the icon buttons say nothing when you hover them

An icon-only control is a guess until you click it. Roughly half of them already answer the
mouse with a native tooltip; the rest stay silent, and which is which looks random.

## Evidence (read from the code on 2026-08-12)

- 68 icon controls in `web/src` carry an `aria-label`. **38 also carry a `title`; 29 do not** —
  so the tooltip is already the house style, just applied unevenly.
- The silent ones cluster where they are most missed: `pages/PhotoDetailPage.tsx` (7, including
  back, archive/restore, the faces toggle and the edit toggle — the very icons the report names),
  `components/slideshow/Slideshow.tsx` (6: close, prev, play/pause, next, fullscreen, settings),
  plus `MetadataPanel`, `FacesPanel`, `FaceAssignPanel`, `EditPanel`, `PeoplePanel`,
  `TechnicalDetails`, `SearchCommand`, `MultiSelect`, `FilterBar`, `PeriodFilter`,
  `TimelineScrubber`, `SubjectDecadeNav` and `ToastProvider`.
- Screen readers are **not** the problem: no icon-only control was found without an
  `aria-label`. This is purely about the sighted mouse user, who gets no hover hint.
- `components/ReasonedButton.tsx` already documents the one real trap: a natively `disabled`
  button swallows pointer events, so its `title` never appears. That component works around it
  with `inert` instead of `disabled`.

## Requirements

- Every clickable control whose visible content is only an icon carries a `title` describing
  its action: `<Button>`/`<button>`, icon-only links (`<a>`, `Nav.Link`) and `Dropdown.Toggle`.
- The `title` says the same thing as the control's existing `aria-label`, from the **same**
  translation call — including the interpolated ones (`{ name }`, `{ decade }`, …) and the ones
  that switch on state (play/pause, show/hide faces, archive/restore, enter/exit fullscreen).
  No second i18n key is introduced for a string that already exists.
- The `aria-label` stays. A `title` does not replace it: on a phone the tooltip never appears at
  all, so the accessible name has to keep standing on its own.
- Buttons with visible text are left alone — a tooltip repeating the words already printed on
  the button is noise, not help.
- Where a control is currently rendered `disabled` and would therefore never show its tooltip,
  either leave it as it is or reuse `ReasonedButton`'s `inert` approach — do not invent a second
  mechanism for the same problem.
- The audit is re-derived from the source rather than trusted from this list: the 29 above are
  what a regex found today, and the sweep should end with every icon-only control covered.
- Existing component tests keep passing. Where a test already asserts on one of these controls,
  it gains an assertion that the tooltip is there; no new test file is needed per component.

## Out of scope

- A lint rule or a source-scanning guard test. This is a one-off sweep — the rule is carried by
  review from here on, not by tooling.
- Changing any label's wording, any icon, or any control's behaviour.
- Tooltip components (`OverlayTrigger`, popovers). The ask is the **native** browser tooltip.

## Implementation notes

- react-bootstrap passes `title` straight through to the DOM element, so on a `<Button>` it is
  a plain prop next to `aria-label`.
- Watch the controls whose label is computed once and used twice — bind the string to a local
  and pass it to both props rather than calling `t()` twice with the same arguments.
- `web/src/components/Icon.tsx` renders the icon decoratively (`aria-hidden`); nothing there
  needs to change.
