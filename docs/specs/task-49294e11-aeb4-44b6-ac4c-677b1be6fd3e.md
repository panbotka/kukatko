# The add-relative dialog clips its autocomplete

The suggestion list of "Add a relative" is cut off: the dialog is only as tall as its two
controls and the list falls outside it.

## Evidence

Static harness of the dialog's own markup with the built CSS (1280x852): `.modal-body` is
180 px tall with `overflow-y: auto` and a 578 px scroll height, and of the 426 px suggestion
list exactly 28 px — 0.64 of one 44 px row — is visible. On a phone it is the same single
clipped half-row, in a dialog that uses a third of the screen.

## Cause

`AddRelationModal` renders `<Modal centered scrollable>`; `modal-dialog-scrollable` gives the
body `overflow-y: auto`, which clips `AddAutocomplete`'s absolutely positioned
`.dropdown-menu` (`top: 100%`). The app already solved this: `MultiSelect` renders its list as
a fixed overlay measured off the input on desktop and in the modal's own flow on a phone, and
`BatchActionBar` dropped `scrollable` for the same reason. `AddAutocomplete` never got that
treatment.

## Requirements

- Typing in the add-relative dialog shows the whole suggestion list — as many rows as fit the
  screen, never one clipped row — with the field still visible above it.
- `AddAutocomplete` escapes a scrolling ancestor the way `MultiSelect` does: on desktop a
  fixed overlay measured off the input, re-measured on capture-phase scroll and resize, raised
  with `kk-overlay-menu`; on a narrow viewport an in-flow list inside the dialog's own scroll,
  so it stays above the on-screen keyboard.
- The two implementations must not diverge — share the positioning logic (a hook), don't copy
  it.
- The dialog gets `fullscreen="sm-down"` like the other pickers, so a phone gets the whole
  screen for the field, its list and the keyboard.
- The other three callers (`OrganizePanel`, `AttachPersonField`, `MySubjectCard`) keep today's
  behavior except that their list now also escapes a scroll container; keyboard picking, the
  create row and blur-to-close are unchanged.
- Tests mirror `MultiSelect.test.tsx`: matchMedia-driven narrow/desktop cases asserting the
  fixed overlay vs `position-static`, with the existing `AddAutocomplete` behavior tests still
  green.

## Implementation notes

- Verify with a static harness of the dialog markup + built CSS driven by agent-browser; the
  check is that the menu rect sits inside the body rect and every row is reachable (was 28 px
  of 426 px).
- The dialog is `centered` — the fix must not make it resize on every keystroke.
- Docs: `docs/FRONTEND.md` for `AddAutocomplete`, the shared hook and `AddRelationModal`.
