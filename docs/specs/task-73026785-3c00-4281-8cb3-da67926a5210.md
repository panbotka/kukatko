# Frontend: upload assignment loss and a hang-forever path

Two upload bugs.

## Issues (verified)

1. **Album/label picks made AFTER the batch completes are silently dropped.**
   `web/src/pages/UploadPage.tsx:59-63` (auto-assign effect) +
   `web/src/hooks/useUploadOrganize.ts:80,153-187`. Upload with nothing selected; batch
   finishes. User then picks album A → assigned, `assign.status='done'`. User adds album
   B → the effect's guard `assign.status==='idle'` is now false and the reset effect only
   re-arms when `!isComplete`, so B is never applied — while the green "Assigned" alert
   still shows. Silent data loss dressed as success.
   - Fix: reset `assign` to `idle` (or assign the delta) when the post-completion
     selection changes, or gate assignment behind an explicit "Apply" button.

2. **A 2xx upload response missing `results` throws inside `xhr.onload` → the upload
   hangs forever.** `web/src/services/upload.ts:159-164` (`xhr.onload`).
   `(body as UploadResponse | null)?.results[0]` guards only a null body, so a non-null
   body lacking `results` makes `undefined[0]` throw a `TypeError` inside the XHR
   callback (uncaught). The upload Promise never settles: the queue item stays
   `'uploading'` forever, a concurrency slot is permanently lost, and `isComplete` never
   becomes true.
   - Fix: check `Array.isArray(body?.results)` (and non-empty) before indexing;
     otherwise `reject(new ApiError(...))` so the item settles as an error.

## Requirements
- Fix both; preserve normal upload + assignment behavior.

## Testing
- Component/service tests: a post-completion album pick is applied (or clearly requires
  an explicit apply); a malformed 2xx body rejects the upload instead of hanging.
  `make check` must pass.
