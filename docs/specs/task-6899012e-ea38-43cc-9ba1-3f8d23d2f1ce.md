# Evaluate: concurrent requests bypass the upload-link lifetime file cap; liveness is checked once per request

A source-only security audit (2026-10-06, commit 3792f7c) produced this **unconfirmed lead**. Reproduce it with a deterministic test, then fix it if confirmed.

## The lead
- On POST /api/v1/u/{code}/upload, `ingestParts` (`internal/uploadlinkapi/public.go:214`) seeds an in-memory counter from `link.UploadCount`, which is read once when the request starts. `ingestOne` (`public.go:260`) compares only that counter with `upload_links.max_uploads_per_link` (default 2000).
- The authoritative increment `countUploadSQL` (`internal/uploadlink/uploads.go:32-35`) has no cap, `revoked_at` or `expires_at` predicate.
- So N concurrent multipart requests, each with many file parts, can each pass the cap independently.
- Rate limiters take one token per request, not per file (per-IP burst 60, per-link burst 300). The config comment at `internal/config/config.go:1559` wrongly assumes one file per request.
- Link liveness is checked only at request start (`public.go:111,155`). A request opened before revoke or expiry keeps storing and filing files into the link's albums and labels.

## Requirements
1. **Reproduce** with an integration test on the test DB.
   - Set the cap to 2. Insert a barrier in a fake ingester or store so both requests pass the link lookup before either records anything.
   - Send two concurrent requests, each with two distinct tiny valid images.
   - Assert the resulting count and album membership. Expect 4 before the fix, where the cap allows 2.
   - Add a second test that revokes the link between two parts of one request.
2. **If confirmed, fix:**
   - Enforce the cap and liveness atomically per file in the database: increment only while the link is not revoked, not expired, and under the cap (0 = unlimited). Treat "no row updated" as link full or gone.
   - Reserve the slot before the original is persisted, or roll back or not file the stored file when the reservation fails, so no photo is stored outside the cap.
   - Return the same refusal the handler gives today for a full or dead link.
   - Consider also capping file parts per request, and counting error-outcome parts toward that per-request cap. Today they do not count (`public.go:231`), so one request can stream unlimited junk parts.
   - Fix the misleading config comment.
   - Both tests become regression tests.
3. Record the outcome as a new SEC entry in `docs/SECURITY_AUDIT.md`, following its existing format.
