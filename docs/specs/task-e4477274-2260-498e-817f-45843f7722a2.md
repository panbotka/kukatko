# A project admin manages the members of their project — backend

## Context

Kukátko is multi-tenant. Roles live on `project_members`; `internal/project` has `Members`, `Membership`, `AddMember` (`ErrAlreadyMember`), `SetRole`, `Approve`, `RemoveMember` (`ErrLastAdmin`). Today `internal/auth` exposes instance-wide user management (list users, approve, change role, disable) used by the `/users` page; the maintainer's instance-level `GET /users` + `PATCH /users/{uid}` already exist in `internal/projectapi`. Foreign tenants must never learn about each other's accounts. Design: `docs/superpowers/specs/2026-10-11-multi-tenancy-design.md`, section 4.1; read `docs/API.md`. Step 24 of 40. The page is the next step.

## Requirements

- New package `internal/memberapi`, mounted under `/api/v1/p/{project}`, `RequireAdmin` (project admin; a maintainer qualifies implicitly):
  - `GET /members` → `[{user_uid, username, display_name, role, approved_at, last_login_at, has_picture}]`.
  - `PATCH /members/{user_uid}` `{role}` — own role → 409 `self`; last admin → 409 `last_admin`.
  - `POST /members/{user_uid}/approve`.
  - `DELETE /members/{user_uid}` — self only when another admin remains (else 409 `self`); last admin → 409.
  - `POST /members` `{identifier, role}` where `identifier` is an **exact** username or e-mail (case-insensitive e-mail, exact username); the response is **always** `202 {"status":"accepted"}` whether the account exists, is already a member, or does not exist — no enumeration; the audit entry records the real outcome (`added` / `already_member` / `no_such_account`). Role capped at `admin`.
- The all-authenticated name directory `GET /p/{slug}/users` (used by @mentions, comments, task participants) lists only the project's **approved** members.
- Remove the old instance-wide approve/role endpoints from `internal/auth` (grep the frontend for their paths and leave a note in the task notes for the page step); keep `disable` maintainer-only at the instance level.
- `internal/ctl`: `ctl members list|add <identifier> --role|role <username> <role>|approve <username>|remove <username>` under the context's project (the general `--project` mechanism is a later step; until then the commands build the prefixed path from a `--project` flag of their own, which the ctl step unifies).
- Approval mail (`internal/mailer`): names the project and links to `/p/<slug>/`.
- Tests: Go integration — admin of A listing B's members → 404 same shape as unknown slug; exact-add responses byte-identical for existing / member / nonexistent identifiers; last-admin; self rules; directory excludes unapproved and foreign; ctl tests.
- Docs: `docs/API.md` (members section; old routes marked removed), `docs/PACKAGES.md`, `docs/OPERATIONS.md`, `CLAUDE.md` package map line.
