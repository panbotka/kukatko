# Three rules disagree about the bottom screen edge

`--kk-bottom-edge` exists for exactly this and is spent correctly in two places; four rules still
compute the edge themselves, two of them wrongly.

## Background

`--kk-tabbar-height` (`web/src/styles/app.css:35`) is `0px` from `lg` up, because the tab bar is
`.d-lg-none` (`components/MobileTabBar.tsx:119`). It is also published from
`getBoundingClientRect().height` (`MobileTabBar.tsx:95`), so when the bar exists its measured height
**already contains** its own bottom safe-area padding (`app.css:860`). The token's own comment
(`app.css:30-34`) says so and prescribes `max()`, which is what `--kk-bottom-edge` (`app.css:39`) is.
`.kk-batch-dock` (`:644`) and `.kk-upload-rail` (`:2913`) use it correctly. These do not:

- **The timeline rail** (`app.css:1372`): `bottom: calc(1rem + var(--kk-tabbar-height))`. On an iPad
  in standalone — 1024px portrait included — there is no tab bar but there is a ~20px bottom inset,
  so the rail's oldest ticks sit in the home-indicator strip. The rail is a `touch-action: none` drag
  target, so dragging there starts the OS swipe-to-home instead of scrubbing.
- **`body`** (`app.css:186`): `padding-bottom: var(--kk-tabbar-height)`, so on an iPad PWA a long page
  reserves nothing and the footer's last row — a real anchor, `components/Footer.tsx:36` — ends inside
  the strip. `.kukatko-shell`'s `min-height` (`:505`) uses `--kk-bottom-edge` and gets the short-page
  case right, so the two rules disagree about the same edge.
- **`.kk-pwa-status`** (`app.css:2818`):
  `calc(1rem + var(--kk-tabbar-height) + env(safe-area-inset-bottom, 0px))` double-counts, because
  the measured tab-bar height already holds that inset. Its comment claims it does this "the same way
  the timeline rail does" — the two disagree and one is wrong. The offline / update note therefore
  floats about 34px higher than designed on an iPhone. Cosmetic, but it is the same fix.
- **The decade heading** (`app.css:1699`):
  `scroll-margin-top: calc(var(--kukatko-navbar-height) + var(--kk-space-3))` is the only
  navbar-relative offset in the file without the top inset, while the navbar's rendered height grows
  by it (`:419`). A decade jump therefore puts the heading 47–59px too high, behind the bar, and the
  row below reads as the one that was picked. Every sibling rule gets this right (`:611`, `:1368`,
  `:1510`, `:1513`).

## Requirements

- The three bottom-anchored rules resolve the bottom edge through `--kk-bottom-edge` instead of
  computing it, so the tab bar's presence and the home indicator are reconciled in one place.
- The decade heading's scroll margin includes the top inset, like its siblings.
- No rule adds a safe-area inset on top of the measured tab-bar height again. Leave a comment saying
  why, since this is the second time that sum has been written — and fix the comment at `app.css:2818`
  that cites the timeline rail as its precedent.
- Behaviour on a phone with the tab bar visible does not change. Only the no-tab-bar cases (iPad,
  desktop-width standalone) and the double-counted one move.

## Testing

- Extend `web/src/styles/safeArea.test.ts`, and `timelineLane.test.ts` / `shellFooter.test.ts` where
  they already own these rules: each of the three names `--kk-bottom-edge` and no longer sums the
  inset with the tab-bar height; the decade heading names the top inset.
- Measure on a static harness with literal iPad and iPhone insets: the rail's lowest tick and the
  footer's last link clear the bottom strip, and the PWA note sits where it is designed to. Report the
  numbers.
