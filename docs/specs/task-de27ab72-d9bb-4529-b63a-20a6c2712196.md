# Notification preferences per kind AND channel; admin "registration pending" e-mail becomes opt-in

The owner wants one notification system in which push and e-mail are just delivery channels of the same notification kind. Each user chooses, per kind and per channel, what they receive. The first e-mail channel is the "a new registration is waiting for approval" notice to administrators, which must be **opt-in per administrator, default OFF**.

## Current state (verified 2026-10-11 on main)
- Kinds live in `internal/notification/notification.go` (`KindTagged`, `KindRegistrationPending`, a `registry` of `{kind, def}`, both `def: true`; `Kinds()`, `Known()`, `Default()`, `Preference{Kind, Enabled, IsDefault}`, `validatePrefs`, `effective`).
- Table `notification_prefs(user_uid, kind, enabled, updated_at, PRIMARY KEY (user_uid, kind))` from migration `0087_notifications.sql`. No channel column. Latest migration is `0092_…`, so the next is `0093`.
- `internal/notification/prefs.go`: `Preferences`, `Wants`/`WantsTx(ctx, tx, uid, kind)`, `ReplacePreferences(ctx, uid, prefs, audit.Entry)` (delete all + insert via unnest + audit `notification_prefs.update` with details `preferences: {kind: bool}`).
- API `GET`/`PUT /api/v1/notifications/preferences` in `internal/notificationapi` (RequireAuth, `decodePreferences`, 400 on unknown/duplicate kind or missing `enabled`). Works even with push off.
- Registration: `internal/auth/register.go` `register()` runs, inside the account-creation transaction, `scheduleMail` (L~321) which sends `mailjob.NewRegistrationPending(recipient.Email, …)` to **every** admin/maintainer from `ListApprovalRecipients` with **no preference check**, and `schedulePush` → `notifyApprover`, which checks `WantsTx(KindRegistrationPending)` and is push-only (comment L~345-349: "a recipient who turned the kind off still gets the mail").
- Mail template `mailer.RenderNewRegistrationPending` (`internal/mailer/templates.go`) has no link; other templates carry URLs built from `cfg.Mail.BaseURL` in `cmd/kukatko/auth.go` (`signInURL`, `passwordResetURL`). The approval page is `/users` (`approvalPath` in register.go).

## Requirements
### Model
- Introduce channels: `push` and `email`. Every kind declares which channels it supports and a default per channel:
  - `tagged`: push only, default on (unchanged behaviour).
  - `registration_pending`: push (default on, unchanged) and email (**default off**).
- Migration `0093_…`: add `channel TEXT NOT NULL DEFAULT 'push'` to `notification_prefs` (existing rows are push choices), change the primary key to `(user_uid, kind, channel)`, no CHECK on channel values (same reasoning as kind: adding a channel costs no migration). Keep the table in `internal/reset/tables.go` as preserved (a column needs no new entry, but re-check `TestPreflight_schemaDriftAborts`).
- `Preference` gains `Channel`. `effective` returns one entry per (kind, supported channel) in registry order, push before email, with `is_default`. `Wants`/`WantsTx` take the channel. Validation rejects an unknown kind, an unsupported channel for that kind, and a duplicate (kind, channel).
- Audit details become `preferences: {"kind/channel": bool}` (or a nested map); keep the action `notification_prefs.update`.

### API
- `GET /notifications/preferences` → `{preferences:[{kind, channel, enabled, is_default}]}`.
- `PUT` accepts `{preferences:[{kind, channel, enabled}]}`; an entry without `channel` means `push`, so an older client keeps working. Replace semantics unchanged (left-out pairs return to default).
- Also return, per kind, whether the caller can ever receive it is NOT needed server-side; keep role gating in the frontend as today.

### Delivery
- In `register.go`, the admin "new registration pending" mail goes only to recipients for whom `WantsTx(ctx, tx, uid, registration_pending, email)` is true (read inside the same transaction/savepoint as the push path). With default off, an admin who never opted in gets **no** mail any more — this is intended.
- The push path checks the `push` channel (behaviour unchanged).
- The registrant's own "registration received" mail and all other mails are unaffected.
- Add the approval link to the admin mail: pass an approval URL built from `cfg.Mail.BaseURL` + `/users` into the registration config (like `signInURL`), add it to `NewRegistrationPendingData`, and render it as the last line of the body ("Schválit nebo zamítnout: <url>").
- When mail is off on the instance (`mail.enabled: false`) nothing changes: `mailjob.Enqueue` already skips.

### Frontend (minimal, keep it working)
- `web/src/services/notifications.ts`: add `channel` to the preference types and to `withPreference`; the existing NotificationsCard keeps showing and saving its current checkboxes as the **push** channel only (ignore email entries for now). A follow-up task builds the channel UI; do not build it here.
