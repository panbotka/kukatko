# /upload: one thing on screen at a time, and it starts by itself

Uploading from an iPhone is the test this page fails today: creating an album leaves the picker
hanging open, the upload button sits below a block the queue has already pushed off screen, and
the progress is somewhere else again. Rebuild the page as one visible stage at a time, with no
button to hunt for — the same way on a phone and on a desktop.

## Requirements

### The flow

- **Stage 1 — pick.** An empty page shows one thing: pick photos (gallery/camera on a phone,
  drag/paste/picker on a desktop). No album fields, no queue, no empty step 3 explaining itself.
- **Picking files starts the upload immediately.** There is no start button anywhere; the moment
  files are chosen the page moves to stage 2 and bytes are moving.
- **Stage 2 — uploading.** The page is the progress: how many of how many, what is left, and —
  right there, because this is the wait — the album and label pickers for the whole batch. The
  per-file list stays available but demoted (below the progress, collapsed or secondary), keeping
  today's per-file retry, remove and errors-only filter.
- **Stage 3 — done.** One sentence of outcome ("20 photos uploaded, added to Pouť 2026") and one
  primary action: show them in the library. Secondary: upload more, which returns to stage 1 but
  **keeps the chosen albums/labels** — the next batch of the same event is the common case.
- If some files failed, stage 3 leads with the failure count and makes retry the primary action.
- If the batch finished with no album chosen, stage 3 says so and offers the picker rather than
  quietly leaving the photos untagged.
- Adding more files while stage 2 runs appends them to the running batch; it never restarts or
  discards what is in flight.

### The album picker

- Creating an album or label inline **closes the suggestion list and dismisses the keyboard**,
  leaving the new name visible as a chosen chip. Today `MultiSelect` clears the query but never
  closes (`web/src/components/MultiSelect.tsx`, the `onCreate` path) — on a phone this reads as
  "nothing happened".
- The fix belongs in `MultiSelect` itself so every other user of it behaves the same way; check
  the other call sites still read correctly afterwards.

### Leaving mid-upload

- The queue lives in the browser, so navigating away loses it. With the upload now starting by
  itself, guard it: an in-app navigation away from a running upload asks first, and a tab close
  triggers the browser's own warning.

### Everywhere the same

- One behaviour on a phone and on a desktop — no separate mobile layout. The stage view is the
  same; only the picker's two fields may sit side by side when there is room.
- The primary action of the current stage is always reachable without scrolling (a bottom action
  area on a narrow screen), and the progress is in that same place — never in a different part of
  the page from the control that produced it.
- Everything translated, cs and en, and every control sized for a thumb.

## Implementation notes

- `useUploadQueue`/`useUploadOrganize` already re-run the batch assignment when the selection
  changes after completion — that is what makes "start first, choose the album while it uploads"
  work without new backend behaviour. Verify it, do not rebuild it.
- The share-target entry (`?share=<id>`, photos arriving from the phone's share sheet) must land
  directly in stage 2 with the files already uploading.
- `UploadStep`, `UploadProgressHeader` and `UploadPage.test.tsx` are all shaped around today's
  three-steps-at-once page; expect to rewrite rather than patch them.
- Use the `frontend-design` skill: this is a redesign, and "extra simple" is the acceptance
  criterion, not a nice-to-have.
- Verify on a real narrow viewport in a browser, not only in jsdom — the complaints were all
  about what is reachable on a phone screen. Record what you checked.
- Docs: `docs/FRONTEND.md` for the page and components, `docs/UX_AUDIT.md` for the decision.
