# Prevent an irreversible loss of all maintainer (operations) capability

A maintainer can demote or disable the only maintainer — including themselves —
leaving the instance with zero maintainers and NO API path to restore the role.

## Root cause (verified)
- `internal/auth/service_admin.go:99-107` (`authorizeUserManagement`) returns nil
  immediately for a maintainer actor, with no last-maintainer check; `:117-130`
  (`guardMaintainerBoundary`) authorizes the action but asserts no invariant. Handlers
  never compare actor vs target (`handlers_admin.go:127-157`).
- Once zero maintainers remain, `authorizeUserManagement` blocks every non-maintainer
  from granting `maintainer` (`newRole == RoleMaintainer` → `ErrMaintainerRequired`).
  There is no delete-user endpoint, and `Bootstrap` runs only when the users table is
  empty (`service_admin.go:71-91`) — so recovery requires direct DB surgery.

## Failure scenario
The sole maintainer demotes (PATCH `/admin/users/{uid}`) or disables (POST
`.../disable`) their own account (or the last other maintainer). Now no one can ever
grant `maintainer` through the API, so every operations surface — backup, restore,
import, maintenance, jobs, processing — is permanently unreachable. This is especially
easy on a single-account instance.

## Requirements
- Before any change that would demote, disable, or remove the `maintainer` role from an
  account, refuse the change if it would drop the count of ENABLED maintainers to zero.
  Return a dedicated, clear error the UI can surface (e.g. "cannot remove the last
  maintainer").
- The check must cover role change, disable, and (if ever added) delete paths.
- A maintainer may still demote/disable others as long as at least one enabled
  maintainer remains.

## Testing
- Integration tests: demoting/disabling the last maintainer is refused with the
  dedicated error; doing so when another enabled maintainer exists succeeds. `make
  check` must pass.
