## Goal
On the task detail page (`/tasks/{uid}`), clicking one of the two built-in review quick answers — **„Schvaluji.“** or **„Vrátit k přepracování.“** — must post the comment AND move the task to `working` (the agent's move) in one atomic request. Today the button only posts a comment and the task stays in `review`, so it still looks like it is waiting on the human.

Example from prod: task `<task uid>`. The user clicked „Schvaluji.“ and the task stayed in `review` until the agent itself closed it.

## What already exists (reuse it, don't build a new path)
- `POST /tasks/{uid}/comments` takes an optional `state` and applies it in the comment's own transaction (`internal/phototaskapi/comments.go`, `stateMove`, commit 54a1504 "send a comment and hand the task to the agent in one tap"). A viewer sending `state` gets 403.
- The discussion's „Odeslat a předat agentovi“ button already uses it (`handOver` in `web/src/pages/TaskDetailPage.tsx`, with `refreshTask` redrawing the badge, controls and participants in place).
- The quick answer buttons live in `web/src/pages/task/TaskAnswers.tsx`. They call `createComment(taskSubject(task.uid), option.text)` without a state. The fixed strings are `REVIEW_APPROVE` / `REVIEW_RETURN` in `web/src/services/tasks.ts` and `phototask.ReviewApprove` / `ReviewReturn` in Go. **The posted body must stay exactly these strings**, because the library agent (its own repository) matches on them verbatim.

## Required behaviour
1. For a **writer** (the same `canWrite` rule as `handOver`), clicking the built-in approve or return answer on a task in `review` posts the fixed string with `state: 'working'` in a single request. Afterwards the page refreshes the task (badge, controls, participants), exactly like `handOver.onDone`.
2. For a **viewer**, keep the current behaviour (comment only, no state). A viewer must never get a 403 from clicking a quick answer.
3. Leave the task's own `options` (non-built-in) unchanged: comment only. Whether they should also hand over is a separate decision. Note it in the commit message as a possible follow-up.
4. Do not close the task (`done`) on approve. Closing needs a resolution, and that stays the agent's job.
5. Make the button visible in the UI: the label or a hint should say the task moves to the agent (e.g. a small note under the pair, „předá úkol agentovi“, in cs and en i18n).

## Tests
- Vitest for `TaskAnswers`: a writer sends `state: 'working'` for both built-ins, a viewer sends no state, a task's own option sends no state, and the posted body is exactly the fixed string. The task refresh is called after a writer's answer.
- If you touch the Go side, add an integration test. No Go change is expected.
