# Show the unscheduled-steps finding on /maintenance and keep deferred places out of it

Found in the v0.30 prerelease walkthrough (staging 54a1504). Commit 3a19e7c added the `unscheduled_steps` finding to the maintenance scan and `kukatko maintenance repair --unscheduled-steps`. Two problems:

1. **The maintainer page never shows it.** `GET /api/v1/maintenance/scan` returns `unscheduled_steps: {count: 109, samples: [...]}` on staging, but `/maintenance` lists every other finding and has no row and no repair checkbox for this one. A maintainer who never uses the CLI cannot see or fix an interrupted upload — and the web is the place the 2026-10-05 incident would be noticed.
2. **It double-counts the places backlog.** 105 of the 109 staging gaps are `<uid>/places`, which is the same set as the existing `missing_places` finding (105). Reverse geocoding is deliberately deferred and paid ("převod souřadnic na jméno se platí, takže se dělá po dávkách"), so a pending `places` step without a job is the normal state, not a gap left by an interrupted upload. Repairing "unscheduled steps" would also queue the whole places backlog behind the curator's back.

## Requirements
- `unscheduled_steps` excludes steps that have their own deferred finding and repair (at least `places`; check the others the processing report can call pending). Alternatively, document precisely why one is included. The count then means "nothing will ever do this by itself".
- `/maintenance` shows the finding with the same row anatomy as the others (count, plain-Czech explanation, technical details with `<uid>/<step>` samples). It offers "Naplánovat chybějící zpracování (N)" as a repair option, wired to the existing repair option.
- i18n cs + en. Vitest for the new row and the repair option, plus a Go test that `places` (or whatever is excluded) no longer counts.
- Update `docs/API.md` (if the finding's meaning changes), `docs/FRONTEND.md` and `docs/OPERATIONS.md` (the `--unscheduled-steps` description).
