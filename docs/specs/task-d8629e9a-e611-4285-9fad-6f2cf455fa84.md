# A wrong dimension pair in the database throws face boxes off the faces, on more than one page

Wherever the app draws a face box over a full-frame photo, it sizes the wrapping element from
the catalogue row — the stored pixel dimensions plus the raw EXIF orientation — and positions
the box inside it in percentages. The wrapper *is* the coordinate system for the box. When the
row is wrong, every box is wrong, even though the image itself renders correctly, because the
browser applies EXIF orientation on its own.

That is happening in production now. Photo `phqale6fftf3a3v5tn17vtfd3d` is stored as 3000x4000
with orientation 6 while the file on disk is really 4000x3000 (PhotoPrism reported its
dimensions already oriented, so the app rotates them a second time). Measured in the live photo
viewer at a 1280x633 viewport:

```
wrapper : 695 x 521   (aspect-ratio: 4000 / 3000)
img     : 391 x 521   (natural 1440 x 1920)
=> every box's x and width are stretched by 695/391 = 1.777
```

One of the three faces ends up at `x = 1.188` — entirely off the right edge of the image.
Roughly 8.6 % of the library carries the same transposed pair.

## The two places that do this

1. **The photo viewer.** `PhotoDetailPage` (around line 797) computes
   `displayFrame(photo.file_width, photo.file_height, photo.file_orientation)` and sizes the
   figure from it; `FaceOverlay` fills that figure.
2. **The candidate review page (`/faces`).** `components/faces/CandidateFaceImage.tsx` carries
   its **own copy** of the same computation — a local `displayAspect()` that swaps width and
   height for orientations 5–8 — sets it as the wrapper's `aspect-ratio`, renders the `fit_720`
   preview inside with `object-fit: contain`, and overlays `candidate-bbox` on top. Same defect,
   reported from production by a user on
   `/faces?subject=...&threshold=50&limit=0`.

The browser already knows the truth once the image has loaded: `naturalWidth`/`naturalHeight`
are post-orientation. The frame should come from there.

## Requirements

- The wrapper a face box is positioned against must match the rendered image exactly, derived
  from the loaded image's natural dimensions rather than from the catalogue row.
- **One implementation, used by both places.** Delete the duplicate `displayAspect()` in
  `CandidateFaceImage` rather than fixing it twice. Check for any further call site that draws a
  box over a full-frame photo and route it through the same code.
- Before the image has loaded there are no natural dimensions yet. Keep the row's frame as the
  initial estimate so the layout does not jump, and switch to the measured one on load. Prefer
  not drawing boxes at all while the frame is only provisional over drawing them somewhere they
  will visibly jump from.
- A photo whose row is correct must render exactly as it does today — no regression in size,
  letterboxing or zoom behaviour, on either page.
- Tests: cover the fallback-then-measured transition, and assert for both the viewer and the
  candidate image that a deliberately wrong row (3000x4000 / orientation 6 with a 1440x1920
  image) places the box in the same spot a correct row would.

## Out of scope
No backend change, no data change.

Note what this does **not** cover: the components that crop a square tile out of a photo
(`subjectTile.ts`, `Outliers.tsx`, `OutlierCard.tsx`, `DuplicateMarkerGroupCard.tsx`,
`DuplicateMarkerCrop.tsx`, `useFaces.ts`) also compute their crop from `displayFrame()` and are
wrong for the same rows, but they scale a background rather than overlaying a box on a rendered
image, so they need the catalogue rows repaired instead. Leave them alone here.
