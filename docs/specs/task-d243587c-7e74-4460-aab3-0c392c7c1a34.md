# Showing one face should not download the whole photograph

Wherever the app shows a single detected face as a small square — the outlier section and the
candidate section on a person's page — it downloads the entire photograph and lets the browser
crop the face out with CSS.

Measured on the live instance, on one person's page:

- The "Možné chyby" section loaded 290 images, every one of them the `fit_1280` rendition.
- For a single face tile: 1280 x 960 pixels were downloaded, the `img` element was then scaled
  to about 2271 x 1703, and the reader sees a 96 x 96 window of it, clipped by a parent with
  `overflow: hidden`.
- The main photo grid on the same page is already correct — small CDN tiles, 500 px square
  painted at 140 px — so it needs no change and must not be touched.

The result is tens of megabytes for one page view, tiles that stay grey because 290 large
images cannot all arrive, and a page that is painful on a phone connection.

## The work is smaller than it looks

`internal/avatar` already does the whole job and is **not subject-specific**: its renderer takes
a photo plus a plain normalised box and knows nothing about subjects. It picks the smallest
`fit_*` rung that gives enough pixels for the crop, pads and squares the box, never upscales,
caches to local disk only (never the object store), and returns an ETag; its cache key is
already a digest of the box, precisely so one photograph can yield different crops for different
faces. What is missing is an HTTP route that asks for a crop by face rather than by subject —
the existing `GET /subjects/{uid}/avatar` handler resolves subject to photo and box, and a
per-face handler would sit over the same renderer.

## Requirements

- Expose a way to request one detected face as a small, already-cropped square image, built on
  the existing avatar renderer rather than a second implementation of the same cropping.
- Use it wherever a single face is shown as a small square: the outlier faces and the candidate
  faces on a person's page, and any other place that crops a full-size rendition down to a
  face-sized window.
- The browser must no longer receive a whole photograph in order to display one face.
- Keep the caching and validator behaviour the existing renderer provides, so a repeated view is
  cheap for the server and for the browser.
- Faces load lazily as the reader reaches them, so a section with hundreds of them does not
  request them all at once.
- Access follows the same rules as the app's other photo imagery — a face must not become
  reachable to someone who may not see the photograph it came from.
- The photo grid on a person's page keeps the rendition it uses today.

## Edge cases

- A bounding box running past the edge of the frame (the existing geometry slides it back
  inside rather than clipping — keep that).
- A very small detected face, where the crop would have to be upscaled; the existing renderer
  refuses to upscale, so decide what the smallest useful output is.
- A face whose photograph has no suitable `fit_*` rendition generated yet.
