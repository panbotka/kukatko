# Search by ID: paste a uid, get the thing

Asked for on 2026-08-03:

> chci byt schopny vyhledat pomoci ID fotky, ID alba, atp.

## What already works — check before building

`internal/query` already resolves some of this and it must not be reimplemented:

* `KeyAlbum` — "matches photos in an album by title **or UID**"
* `KeyLabel` — "by name **or UID**"
* `KeyPerson` — "by name **or UID**"

So `album:al…` already narrows the library to that album. Verify this actually works end to
end (it is documented, which is not the same thing), and if it does, the task is to cover the
gaps and make it discoverable — not to rewrite it.

The real gaps are:

1. **A photo has no uid filter at all.** There is no `uid:` key, so a photo cannot be found
   by its own id in the library search.
2. **Pasting a bare uid into search finds nothing.** `internal/globalsearchapi.handleGlobal`
   runs free text over album/label/subject names and photo full text. A uid matches none of
   those, so the most obvious gesture — copy an id out of a URL, an audit row or a log line,
   paste it into search — silently returns nothing.

## The enabler: uids say what they are

Verified against production:

| prefix | entity | length |
| --- | --- | --- |
| `ph` | photo | 26 |
| `al` | album | 26 |
| `lb` | label | 26 |
| `su` | subject | 26 |
| `st` | stack | 26 |
| `mk` | marker | 26 |
| `pt` | **PhotoPrism** photo uid (`photos.photoprism_uid`) | 16 |

Nothing collides — the prefixes are distinct and the PhotoPrism ids are a different length
(`ph7lpul2io09bcg2rvp2rljsr6` vs `pt8suk5b57jgshdz`). A uid can therefore be routed to its
entity with no guessing and no extra round trips.

## What to build

**Global search recognises a uid.** When `q` is (or contains) something shaped like a uid,
resolve it directly and return the entity as a distinct, top-of-list hit — clearly presented
as "go to this", not mixed in as if it were a fuzzy text match. Cover photo, album, label and
subject. A `mk…` marker resolves to the photo it sits on; a `st…` stack to its primary. An id
of the right shape that matches nothing must say so plainly, not fall through to an empty
free-text result that looks like a broken search.

Support `pt…` PhotoPrism uids too, matched against `photos.photoprism_uid`. That is not
gold-plating: the whole library came from PhotoPrism, external ids are stored deliberately
(`CLAUDE.md`, "Import/migration"), and the operator regularly has a PhotoPrism id in hand
while debugging the migration.

**Add `uid:` to the query language** for the photo's own uid, so it composes with other
filters and survives into a saved search. Follow how `KeyAlbum` and friends resolve
title-or-uid rather than inventing a second convention. Decide and document whether `uid:`
also accepts a PhotoPrism uid, or whether that gets its own key — either is defensible,
silently doing half of it is not.

## Decisions to make explicitly

* **Visibility.** An explicit uid is explicit intent, so a lookup should find an archived
  photo, or one hidden from the library (task `208591a9`, if it has landed), rather than
  reporting nothing. Say what state the hit is in — a photo that turns up but is archived is
  confusing unless labelled.
* **Prefix guessing.** Do not accept a bare id without a known prefix and try every table.
  That is four queries per keystroke on a search-as-you-type box for no benefit.
* **Cost.** The global search already fans out to four searches per request. Adding a uid
  branch should *replace* that fan-out when the input is a uid, not add a fifth query to it.

## Verification

Integration tests over the real test DB, one case per prefix including `mk` routing to its
photo and `pt` matching `photoprism_uid`; a well-formed uid that matches nothing; `uid:` in
the query language, alone and combined with another filter; a saved search carrying it.
Frontend: Vitest over the search UI showing the direct hit distinctly from text matches.

`make check` green. Update `docs/API.md`, `docs/FRONTEND.md`, `docs/PACKAGES.md` (query +
globalsearchapi) and whatever documents the query language keys — a filter nobody can
discover is a filter nobody uses.
