## What is wrong

A Bootstrap dialog opened from inside the immersive photo viewer renders **underneath the
viewer** and cannot be reached. The only one today is the comment deletion confirm, which makes a
photo comment impossible to delete: pressing "Smazat" on a comment appears to do nothing.

`.kk-viewer` is `position: fixed; z-index: 1080` (`--kk-viewer-z` in `web/src/styles/tokens.css`),
and Bootstrap's dialog band tops out at 1055. The layering scale in `web/src/styles/app.css` says
so on purpose — "1080 immersive viewer … owns its route" — so this is the documented consequence
of a deliberate decision, not a stray number. `web/src/components/review/review.css:646` records
the same collision for the sorting game and works around it with an in-game layer.

**Pre-existing, not a regression of the v0.25.0..6e98115 range.** At `v0.25.0` the token was
already 1080 and `CommentsPanel` already used `ConfirmModal`. Found during the pre-release
walkthrough of `6e98115` on box staging. Severity: WARN — one flow is unusable, no data is at
risk, and Esc dismisses the invisible dialog so nobody is trapped.

## Evidence (box staging, 6e981153)

With the confirm open (`document.querySelector('.modal.show')` present, text
"Smazat komentář?"), a sweep of the confirm button's rect returns `IMG.kk-viewer__image` at every
point, and a real click on it produces **no** `DELETE /api/v1/photos/{uid}/comments/{cid}` request
at all. A scripted `.click()` on the node does delete the comment, which is how the flow passes in
tests while failing for a user. The screenshot shows the viewer with no dialog visible while the

## Reproduce

1. Sign in on box staging (http://100.127.79.1:6490, `admin` / `adminadmin`).
2. Open any photo from the grid, open the **Informace** panel.
3. Write a comment and send it.
4. Press **Smazat** on that comment.
5. Observed: nothing visible happens; the comment stays. Expected: the confirm dialog appears and
   deleting works.

## What to do

Decide the mechanism rather than bumping a number blindly — the scale in `app.css` is documented
and the fix has to keep it honest:

- **Option A — raise the dialog band above the viewer while a dialog is open.** Bootstrap's modal
  and backdrop take a z-index from CSS variables; overriding them for the viewer's route (or
  globally, above `--kk-viewer-z`) makes every future dialog work, including ones nobody has
  written yet. The backdrop has to rise with the dialog or the viewer will still take the clicks.
- **Option B — lower the viewer while a dialog is open.** The viewer already knows when it has a
  dialog; dropping `--kk-viewer-z` under the dialog band for that time is a smaller blast radius
  but has to be re-done by every component that opens one.
- **Option C — an in-viewer layer**, the way `review.css` solved it for the game. Cheapest for the
  one dialog that exists, and the one that will be forgotten next time.

A is the general fix and the one worth taking unless it breaks something on the page behind.

Whatever wins, add a regression test in the shape of the existing `web/src/styles/*.test.ts`
stacking tests (`viewerStacking.test.ts` is the precedent): the rule should be checkable from the
stylesheet, i.e. "a dialog's z-index is above `--kk-viewer-z`", so the next person who changes
either number fails the gate rather than shipping an invisible dialog.

Check while you are there whether any other component can open a Bootstrap dialog from inside the
viewer's route — today `grep -rn "ConfirmModal\|<Modal" web/src/components/photo` finds only
`CommentsPanel`, so the blast radius is one flow, but that is what makes it cheap to fix properly
now.

Do not change the review game's existing workaround in the same task.
