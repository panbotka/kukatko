nothing. Read CLAUDE.md first.

Every person in a village archive has a name and, very often, the thing people actually call
them. The library can record only the name. Give each subject an optional nickname and make
it findable.

## Data

One column on `subjects`, declared the way `name` and `notes` already are there:

    nickname TEXT NOT NULL DEFAULT ''

Take the NEXT FREE migration number — run `ls internal/database/migrations/ | tail -3` rather
than assuming. 0072 is the newest at the time of writing and the family-tree epic claims 0073
for `subject_families`, so this is expected to be 0074. Verify.

No unique constraint: two men in one village are both "Bohouš" and that is normal. No length
CHECK either — `name` has none, and consistency beats a guess.

**The nickname must NOT feed `slug`.** The slug is derived from `name`, is UNIQUE and appears
in URLs; regenerating slugs would break every bookmark and every link already written into
the audit trail.

One nickname, not a list. If several turn out to be needed later, `notes` is already free
text and a migration can promote it — do not build a second table on speculation.

## Search: where a subject's name flows today, and where the nickname must follow

This list was verified against the code while the task was written, so it is complete.

1. **internal/people/search.go** — `searchSubjectsSQL` today matches only
   `immutable_unaccent(name) ILIKE immutable_unaccent($1)`. Add the nickname to the same
   predicate so it stays case- and accent-insensitive. This one query backs the grouped
   global-search endpoint, so `GET /search/global` should gain it for free — verify that it
   actually does rather than assuming.
2. **`personCond` in internal/photos/store_query.go** — today
   `s.name ILIKE $p OR s.uid = $uid`. Add `OR s.nickname ILIKE $p`, reusing the SAME pattern
   placeholder; both are text comparisons, so there is no type-deduction problem, and a
   third bind of the same value is waste.
3. **The command palette's `person:` value completion** is driven by the server's own schema
   and suggestions, so it should pick nicknames up. Verify it, and make the suggestion show
   the nickname ALONGSIDE the name, never instead of it.
4. **The subject picker used when naming a face** is where this feature earns its keep: a
   nickname is often the only handle the person naming faces has. It must match there and
   display there.
5. **The photo `fts` tsvector is out of scope and must stay out.** It is a
   `GENERATED ALWAYS` column over photo-level columns only (title, description, notes,
   ai_note, file_name) and cannot reference `subjects` at all. Free text does not find people
   by name today either, so the nickname behaves exactly like the name: reachable through
   `person:`, the subject search, the global search and the palette. Do not try to rewire
   full-text search to close a gap that is deliberate.

## Everything else that carries a subject's name

- `subjectChanges` in internal/peopleapi/handlers.go — add `changes.Add("nickname", …)`, or a
  nickname edit goes unrecorded in the audit trail.
- `SubjectUpdate`, `SubjectInput`, the decode path, and the TypeScript `Subject` /
  `SubjectInput` types, field for field.
- internal/sidecarexport's `Person` struct carries `Name` and `SubjectType`; add the nickname
  so the catalogue still holds it after losing the database, and extend its round-trip test.
- `ctl subjects` — accept a nickname on create and rename, and show it in the output.
- The subject payloads in internal/mcpapi, wherever they already expose the name.

**Do NOT add a `subject_nickname` cache column to `faces`.** `subject_name` is already
denormalised into that table and into roughly a dozen payload structs, and every copy is
another thing to keep consistent on rename. Join where a surface needs the nickname, and
revisit only on measured evidence.

## UI

- `SubjectEditModal` gains the field.
- The subject page header shows it beside the name — Bohumil Nečas („Bohouš") — not on a line
  of its own, and nothing at all when it is empty.
- The people index shows it where it helps: on a tile whose match came from the nickname, and
  in search results.
- i18n cs + en, Czech the default.

## Tests

Unit: building the search predicate.

Integration against the real test database: finding a subject by nickname with and without
diacritics; `person:<nickname>` returning the right photos; a nickname change appearing in
the audit diff; the nickname surviving a sidecar round trip; and a subject whose nickname is
empty NOT being matched by an unrelated non-empty query — an `OR` over an empty column is an
easy way to make everything match. Integration tests need `-p 1`, and run
`go vet -tags integration ./...` before the gate.

Vitest: the modal saves it, the header renders it, the header omits it when empty.
