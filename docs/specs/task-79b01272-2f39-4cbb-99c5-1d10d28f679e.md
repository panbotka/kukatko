# Admin can rename a user's username

People register with silly usernames; an administrator (role `admin`) or maintainer must be able to change another account's username from `/users`. Today the username is read-only once the account exists (`UsersPage.tsx` edit dialog renders it `readOnly`/`plaintext`, and `PATCH /admin/users/{uid}` has no username field).

## Requirements

- Backend: an admin-guarded way to change a username — either `username` added to `PATCH /admin/users/{uid}` or a dedicated `PUT /admin/users/{uid}/username`; pick whichever fits the existing handlers, document the choice.
- Who may do it: exactly the same rule as the rest of `/users` — `admin` and `maintainer`; an admin may not rename a maintainer account (the existing `canManage` boundary, 403 on the backend). Viewer/curator/editor → 403.
- The new username goes through the **same normalisation and validation as creation/registration** (`normalizeUsername`: trim + lowercase, allowed characters, max 64 runes). Invalid → 400 with the field-naming message; a username another account holds → 409 `username already taken`; renaming to the current value is a no-op 200.
- The rename is audited (e.g. `user.rename`, old and new username in the entry) **in the same transaction** as the update.
- Nothing keyed by uid breaks: the account's sessions, API tokens, passkeys, linked subject, comments, uploads and audit history stay attached. The user stays signed in. Verify sessions/tokens/passkeys really key on uid, not username, and say so in the tests.
- The `.invalid` placeholder addresses (`<username>-<uid>@kukatko.invalid`) are not rewritten — they only need to be unique and undeliverable.
- When mail is on and the address is real, the user gets a short Czech mail "your username is now X" via `mailjob.Enqueue` in the rename's transaction (a new template beside the existing ones); mail off or `.invalid` → silently nothing, the rename still succeeds. Otherwise the person cannot sign in and doesn't know why.
- Frontend: in the edit dialog on `/users` the username becomes an editable field for accounts the admin may manage (still read-only where `canManage` is false). The field shows the backend's 400/409 inline like other fields; the table/card updates after save. cs + en strings.
- Renaming one's own account works the same way (no special case beyond what the backend already enforces).

## Tests

- Integration (real test DB): success, 409 duplicate (incl. case-only difference from another user), 400 invalid/over-long, 403 admin→maintainer, 403 for a non-admin role, audit entry written, mail job queued / not queued (mail off, `.invalid`), the renamed user's existing session still works and login works with the new name only.
- Vitest for the dialog: editable for manageable rows, read-only otherwise, 409 shown on the field.
