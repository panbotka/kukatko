# A thumbnail 500 must say why

During a pre-release walk on staging, opening a photo from a "you were tagged" notification produced one `GET /api/v1/p/{project}/photos/{uid}/thumb/fit_1920` → **500** (34 bytes, 437 ms). This was seconds after a face on that photo had been assigned to a person. The access log has only the generic `http request … status 500` line. **No line says what failed.** Retrying the same URL a minute later returned 200 for fit_1920, fit_1280 and fit_720. 48 concurrent first requests to uncached fit_1920 renditions of other photos all returned 200, so the failure was not reproduced.

## Requirements

- Every 5xx from the thumbnail/media handlers logs one structured ERROR line with the request id, photo uid, size, project and the wrapped error chain: which step failed (storage read, materialize to temp, decode, encode, cache write/rename, vips, exiftool…). Expected outcomes stay non-ERROR: undecodable original → 404 at WARN, which is already the case.
- Then look for the likely race and fix it if confirmed. Candidates:
  - two writers of the same cache file: an on-demand render vs the `thumbnail` job, or the edit/sidecar jobs triggered by a curation change;
  - a reader seeing a half-written or just-replaced cache file;
  - temp-file cleanup removing a file another request still uses.
  The cache write must be atomic (temp file in the same dir + rename) and concurrent renders of the same key must not fail each other (singleflight per cache key, or tolerate "already exists"). Write a test that forces two concurrent renders of one key, plus a render racing a job regeneration, and asserts both succeed.
- If no race is found, say so in the commit message. The logging alone is the deliverable then.
- Docs: `docs/PERF.md` or `docs/PACKAGES.md` (thumb) if the caching contract changes.
