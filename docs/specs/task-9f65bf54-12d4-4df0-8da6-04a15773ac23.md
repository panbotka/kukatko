# RAW previews: extract the largest embedded JPEG, not the first

A production bug affecting every Nikon RAW in the library: they are rendered,
embedded and face-detected from a thumbnail-sized preview while a
near-full-resolution JPEG sits unused inside the same file.

## The evidence

Measured against production. `PreviewImage` is the tag currently used; `JpgFromRaw`
is never reached.

| file | catalogue | `PreviewImage` | `JpgFromRaw` | largest rendition served |
| --- | --- | --- | --- | --- |
| `_DSC0048.NEF` (D5100) | 4992x3280 | 570x375 | **4928x3264** | 570x375 |
| 7x `*.nef` (D3300) | 6016x4016 | 640x424 | **6000x4000** | 640x424 — **10%** |
| 5x `*.arw` (Sony) | 4608x3072 | 1616x1080 | *empty* | 1616x1080 |

For the NEFs, `fit_720`, `fit_1280` and `fit_1920` all return the identical 640x424,
so the cap is the source the thumbnailer was given, not the thumbnailer.

**The Sony ARW files are not affected.** They embed no `JpgFromRaw` at all, so
1616x1080 genuinely is the largest available and the current code already picks it.
They must not be "fixed" — more pixels would require a full demosaic, which this
project deliberately does not do.

## Root cause

`extractPreview` in `internal/imgconvert/raw.go` walks `rawPreviewTags`
(`PreviewImage`, `JpgFromRaw`, `ThumbnailImage`) and **returns on the first tag that
yields any bytes**. Nikon bodies populate a small `PreviewImage`, so the loop stops
before reaching the full-size `JpgFromRaw`. The function's own doc comment already
claims it extracts the *largest* available preview; the code takes the first.

## Requirements

- Pick the **largest** embedded JPEG by pixel count, whichever tag holds it.
- Ask `exiftool` for the candidate **sizes first** — that reads metadata only, no
  image data — and extract exactly one image, the winner. Do not extract all three
  and compare; a 2 MB write per loser on every RAW ingest is not acceptable.
- Preserve the existing typed errors unchanged: a missing `exiftool` still wraps
  `ErrConverterMissing`, and a RAW with no usable preview in any tag still wraps
  `ErrNoEmbeddedPreview`.
- **Still no demosaic.** The Docker image deliberately ships without dcraw/libraw and
  must keep working.
- Cover the three real-world shapes in tests, using the measured numbers above: the
  Nikon shape (small `PreviewImage`, large `JpgFromRaw`), the Sony shape (only
  `PreviewImage` plus a 160x120 thumbnail, no `JpgFromRaw`), and a file where only
  `JpgFromRaw` is present. Tests must not carry a real RAW file — drive the selection
  through the tag table, not a 21 MB fixture.

## Implementation Notes

- The blast radius is wider than thumbnails. `internal/facejob` decodes the original
  through `imgconvert.EnsureDecodable`, and `internal/embedjob` sends a thumbnail
  derived from the same pixels — so face detection and embeddings for the affected
  photos were computed from the degraded image too.
- **Do not touch production in this task.** After the fix ships, the **7 NEF** photos
  need their thumbnails, embeddings and face detection re-run through the existing
  backfills. The 5 ARW photos will be unchanged by the fix, and that is the correct
  outcome, not a failure. State this in the commit message and leave the trigger to a
  human.
