# Metrics for the video encode

Encoding a video is the most expensive thing this application does, and `/metrics` says almost
nothing about it. What is there already comes free from the generic worker instrumentation, and
it stays: jobs started per type, jobs finished per type and outcome, an execution duration
histogram per type and outcome, and queue depth by type and state — the streaming encode job
appears in all four. What is missing is the shape of the work itself: an encode job is one row in
those series regardless of whether it chewed through a six-second clip or a forty-minute one.

## Requirements

- Instrument the encode where the encoder actually runs, one observation per rendition rather
  than one per job, recording: how long that rendition took, how many bytes it produced, and
  which rendition it was. Label by rendition name and by outcome; never by photo, file name,
  uploader or anything else per-item — `/metrics` is unauthenticated and carries only
  instance-wide aggregates.
- Export how many seconds of source video have been encoded, as a counter, so that the cost of
  the pipeline — CPU time spent per minute of footage — is derivable in a query from it and the
  duration series. Do not export a pre-computed ratio: a ratio cannot be aggregated or rated.
- Export, at scrape time, how many videos have no streaming rendition at all — the backlog the
  operator alerts on. Reuse the memoised library aggregation that the other content gauges and
  the admin dashboard already share, so a scrape does not re-count the library and the gauge
  cannot disagree with the dashboard.
- Follow the naming already in use: the instance namespace, counters carrying the total suffix,
  gauges never carrying it. A failed aggregation drops its own gauges for that scrape rather
  than exporting a stale or zero value.
- The encode package must not import the metrics package. Follow the pattern the worker runtime
  already uses for exactly this: a small observer interface with a no-op default, implemented by
  the metrics package and wired together in the command layer. With no observer wired, the encode
  behaves identically and records nothing.

## Documentation

Add every new series to the metrics list in `docs/OPERATIONS.md`, in the group it belongs to
(event-driven versus sampled at scrape time). Alongside them, add example queries answering the
three questions this exists for: how many encodes are running right now, how long an encode
takes, and how much processing time a minute of video costs. Note in the same place that the
generic job series already cover the encode, so a reader does not add duplicate ones.

## Tests

Unit tests over the observer wiring and the recorded values, and a test that the metrics endpoint
exposes the new families with the expected names and labels. Verify the no-observer path leaves
the encode unchanged.
