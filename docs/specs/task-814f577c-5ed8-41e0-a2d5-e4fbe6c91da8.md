# The notification deeplink page

Tapping "You were tagged in 12 photos" has to land on exactly those 12 photos — the set as it was when the notification was made, not a live search that a thirteenth tag would quietly change. This task builds the page that deeplink opens.

## Context that already exists

The backend stores a notification record with a **frozen ordered set of photos**, read by uid and scoped to the calling account: an unknown or foreign uid is a 404, never a 403. The response carries the title, body, kind, created time, read time, the photo set shaped like the other photo payloads in this API, and a count of how many photos were **dropped** because the caller may no longer see them (a photo that has since become private, hidden or archived). A separate endpoint marks the notification read.

## Requirements

- A route for a notification by uid. Keep the path **short**, because it travels inside a push payload that has a hard size limit. Add it with the project's existing route and lazy-loading conventions.
- **It is a junction, not a destination.** With exactly one photo in the set, go straight to the photo viewer — a grid of one tile is a pointless extra tap. With more than one, render the set as a grid. With none, say so.
- The grid reuses the existing photo grid components. Do not build a second grid. Long grids here are virtualized with `react-virtuoso` — follow whatever the existing library grid does rather than choosing again.
- Mark the notification read when the page opens. Once, not on every re-render.
- The page's heading is the notification's own title and body, so the person sees what they tapped.
- If the set is short **because** photos were dropped, say it plainly — something in the shape of "2 photos are no longer available to you" — rather than silently showing ten of twelve and letting the count in the notification look like a lie.
- The loading, empty and error states all have to be real. A 404 — a notification that was purged by retention, or somebody else's uid — gets a friendly page with a way back to the library, not a raw error dump.
- **Authentication round trip:** a push tapped on a phone that has since been signed out lands on the login screen and must come back here afterwards. The login page already returns to `pathname + search` rather than the pathname alone, so this should work — verify it does for this route rather than assuming.
- Czech and English strings through i18next, Czech default.

## Verification

Component tests: one photo redirects to the viewer; several render a grid; none renders the empty state; a dropped-photo count is stated; a 404 renders the friendly page; the notification is marked read exactly once. Note that jsdom mounts no `react-virtuoso` items — the established approach in this repo is to mock the virtualizer and route through the real list. Check how the existing grid tests do it and follow that, rather than asserting on tiles that will never be in the DOM.
