# Search history records fragments nobody submitted, and never offers them back

The search box remembers what the reader was in the middle of typing, and then refuses to complete it for them. Both halves are wrong, in opposite directions.

## Evidence (observed on production, 2026-08-12, controlled)

On `/search`: clicked the box, typed `s`, `v`, `a`, paused four seconds, typed `t`, `b`, `a`. **Enter was never pressed.** Afterwards `GET /api/v1/search-history` returned:

```
["svatba", "sva", "qwert", "p", "rok", "sni", "sn", "s", "snih"]
```

Both `sva` and `svatba` are stored, as are `s`, `sn`, `sni`. The ring is capped at 20, so a few hesitant sessions fill it with prefixes of itself — and the history panel is the only thing the box offers when it is empty, so those fragments become the primary suggestion surface.

The mirror image: with `snih`, `svatba`, `sva` and `s` all in history, typing **`s`** offers `square:` and `subject:` — two English filter keys — and nothing from the history. History is only consulted when the box is completely empty (`web/src/components/search/SearchQueryInput.tsx:106-109`, `useSearchHistory(open && empty)`). The app knows what this person searched for last week and will not offer it.

## Requirements

- A query is recorded only when the reader actually submits it — Enter, a suggestion pick, or an equivalent deliberate act. Debounced keystrokes are not submissions.
- Existing prefix junk already in a user's ring is not a migration concern, but the ring must not keep accumulating it.
- Typing a prefix offers matching entries from the reader's own history alongside (or above) the filter-key completions, not instead of nothing.
- Ordering makes sense when both kinds of suggestion are present, and the reader can tell which is which.
- Tests: typing without submitting records nothing; submitting records exactly once; a prefix matching a history entry surfaces it.

## Constraints

- **No mutable operations against production data.** The evidence above was gathered against production, but this task must verify against a local instance — the search history is per-user data and must not be written to on production.
- Note this interacts with the task "Enter in the search box must not accept a filter-key suggestion". If that one has landed, honour its behaviour; if it has not, do not fight it.
- `make check` must pass. `make check-box` runs the same gate on the build box and is much faster.
