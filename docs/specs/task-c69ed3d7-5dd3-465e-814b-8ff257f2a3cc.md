# A forced rebuild must not be absorbed by a queued plain job

The rebuild endpoints added in `9ca41bd` can answer `status: "queued"` for work
that will never happen. When the backing service is offline the request falls back
to the queue, and the queue's dedup index — keyed on job type + `photo_uid` — lets
an already-queued **plain** job absorb the forced one. That plain job then takes
its idempotent skip when it finally runs. The operator saw a success and nothing
was recomputed: the exact silent no-op the rebuild endpoints were built to kill.

## Background

`POST /photos/{uid}/{reembed,redetect-faces,regeocode}` run the work synchronously
and answer `rebuilt`. When the embeddings sidecar is asleep the run returns a
deferral, `runRebuild` routes to `queueRebuild`
(`internal/photoapi/rebuild.go`), and the forced job is enqueued via
`EnqueueImageEmbedRebuild` / `EnqueueFaceDetectRebuild` / `EnqueuePlacesRebuild`.

Those all reach `enqueueForcedPhotoJob` → `enqueuePayload`, which **swallows
`ErrDuplicate`** so the call is idempotent per photo. That is right when the
existing job is itself forced. It is wrong when the existing job is plain: the
forced payload is dropped, the plain job survives, and its handler skips.

The collision is reachable from the UI. `processing.Service.Run` refuses a step
only when it can never apply — `Evidence.applies` tests for a video or a missing
coordinate and deliberately ignores whether the work is already done — so
`POST /photos/{uid}/process/{step}` queues a plain job even for a photo that
already has its evidence. That is the documented trap: it answers 200, reports the
step done, and changes nothing. `web/src/services/photos.ts` calls it. A plain job
waiting in front of a forced one is therefore the ordinary case, not a rare race.
On this instance the box is asleep most of the time, so the queue fallback that
exposes it is the normal path rather than an edge case.

Both collision states are live for these job types. `idx_jobs_dedup` (migration
`0044`) is partial on `state = 'queued' OR (state = 'running' AND type <>
'sidecar')`, so `image_embed`, `face_detect` and `places` dedupe against a
**running** job as well as a queued one — which is why the running case below needs
an answer of its own rather than falling through to the upgrade.

## Requirements

- A forced enqueue that collides with a **queued** job for the same photo and type
  upgrades that job's payload to the forced one instead of being dropped. The job
  has not been claimed, so rewriting its payload is safe, and dedup stays keyed on
  type + `photo_uid` — still at most one active job per photo per type. The
  endpoint keeps answering 200 `queued`.
- The upgrade must be race-safe: a single statement, conditional on the job still
  being queued, so a worker claiming it concurrently can neither lose the flag nor
  have it applied to a job already in flight. Do not read-then-write.
- A forced enqueue colliding with a job for the same photo and type that is already
  **running** cannot be upgraded — that run is using the old payload. Answer **409**
  from the rebuild endpoint, saying a run is in flight and the rebuild should be
  retried once it finishes. Never answer 200 for a force that will not happen.
- A forced enqueue colliding with a job that is **already forced** keeps today's
  behaviour: absorbed, 200, no second job. That collapse is correct.
- The plain enqueuers must not change. A plain request colliding with a queued
  forced job stays absorbed and must never downgrade the forced payload — a forced
  job outranks a plain one in both directions.
- The behaviour belongs in `internal/jobs` next to the enqueuers, so all three
  rebuild paths inherit it rather than each endpoint reimplementing the check. The
  outcome (upgraded / absorbed / running) has to reach `internal/photoapi` so
  `queueRebuild` can pick between 200 and 409.

## Tests

- A forced enqueue over a queued plain job upgrades the payload, and the job that
  then runs does **not** take its idempotent skip.
- A forced enqueue over a running job reports the in-flight outcome, and the
  endpoint answers 409.
- A forced enqueue over a queued forced job is still absorbed into one job.
- A plain enqueue over a queued forced job does not downgrade it.
- The upgrade leaves exactly one active job for that photo and type.
- Integration coverage against the real test DB for the conditional update, since
  the race-safety is a property of the statement, not of the Go code around it.
