A single flaky frontend test failed the `v0.1.0` release build on 2026-08-01, so the container
image was never published and the production deployment had to wait for a manual re-run. The
flake has been known for a while; what changed is the consequence.

## The failure

Run 30688957518, job `test`: 1 failed / 1565 passed.

    TypeError: Cannot read properties of undefined (reading 'then')
     ❯ src/hooks/useTimeline.ts:39:44

The same suite passes locally — 1566/1566, twice in a row on the same commit — and the same
test file passes in isolation (28/28). It only fails under the full suite.

## Known root cause

A per-file `afterEach(vi.restoreAllMocks)` overrides the global `restoreMocks` config, so React
Testing Library's cleanup flushes pending effects into mocks that have already been reset.
`fetchTimeline` then returns `undefined` and the effect calls `.then` on it. Roughly 57 test
files still carry that per-file hook.

## Why this is worth doing now

`docker-publish.yml` gates image publication on the test suite (`build` needs `test`), which is
the right design — but it means any flaky test can block a release. The image for a tagged
release is the deployment artefact, so a 1-in-N flake becomes a release outage that needs a
human to notice and re-run. Kukátko is being deployed to the VPS now, so this stops being
theoretical.

## What to do

Remove the per-file `afterEach(vi.restoreAllMocks)` where the global config already covers it,
rather than papering over the symptom with a retry setting. Sweep all the files that carry it,
not only the two that have been seen failing (`LibraryPage.test.tsx`, `SystemStatusPage.test.tsx`)
— the pattern is the bug and the failing file varies between runs.

Adding `retry` to the vitest config is explicitly NOT the fix: it would hide the next real
race just as effectively.

## Verification (mandatory)

- Run the full frontend suite repeatedly (at least 10 consecutive runs) and show that none
  fails. A single green run proves nothing about a flake.
- `make check` green.
- State in the commit message how many files the sweep touched.
