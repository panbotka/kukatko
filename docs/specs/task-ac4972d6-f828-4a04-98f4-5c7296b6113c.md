# REST surface for push subscriptions, notifications and preferences

This task only exposes over HTTP what two packages already do. Write no new business logic.

## Context that already exists

`internal/push` holds a `push_subscriptions` table — one row per browser: the account, the endpoint URL (unique), the `p256dh` and `auth` client keys, an optional user-agent, created and last-used timestamps, failure bookkeeping — plus the VAPID configuration under `push.*`, including `push.enabled` which gates the whole feature instance-wide.

`internal/notification` holds notification records (uid, account, kind, title, body, deeplink path, created, read) each with a **frozen ordered set of photos**, and per-(account, kind) preferences where an absent row means the default. Reading a notification by uid is already scoped to its owner: a foreign uid is not found, not forbidden.

## Requirements

New package `internal/notificationapi` mounted under `/api/v1`, following this repo's API conventions: chi, the RBAC middleware from `internal/auth`, the error shape the other API packages use, and `internal/apitest` as the HTTP client in the tests — never `http.DefaultClient`, whose process-wide pool a closing test server empties under a parallel test.

Endpoints:

- **Read the VAPID public key and whether push is available at all.** All authenticated roles. The frontend needs the public key in order to subscribe, and needs to know push is off instance-wide before it renders any control. The **private key must never appear in any response** — assert that in a test.
- **Register or refresh the current browser's subscription.** Body carries the endpoint, the two client keys and optionally a user-agent. Upsert by endpoint, always bound to the calling account. All authenticated roles — a viewer wants to know they were tagged just as much as an editor does.
- **Remove a subscription** by endpoint, scoped to the calling account.
- **List the calling account's subscriptions** — enough to render "this browser" against other devices in a settings page: the user-agent, when it was created, when it was last used. **Never return the client keys**; they are shared secrets for encryption, not display data. Assert that in a test too.
- **Read and replace the calling account's notification preferences.** The read returns the effective set (defaults merged with stored rows) so the frontend needs no knowledge of what the defaults are. A replace naming an unknown kind is a 400.
- **Read one notification by uid**, scoped to the calling account. An unknown or foreign uid is a **404, never a 403** — the rule `internal/savedsearchapi` follows, so a uid cannot be probed for existence. The response carries the title, body, kind, created time, read time and the frozen photo set in its stored order, shaped like the other photo payloads in this API so the frontend can render a grid straight from it — which means the thumb and download URLs go through `internal/mediaurl` like everywhere else.
- **Mark a notification read**, scoped to the calling account.

Visibility is the one rule that matters most here: **the frozen photo set must be filtered by what the caller may see now, not by what was visible when the notification was made.** A photo that has since become private, hidden or archived drops out of the response. The response must also state **how many were dropped**, so the page can honestly explain a short list instead of silently showing ten of twelve.

Do **not** build a "list my notifications" endpoint. There is no in-app notification centre and the deeplink only ever needs one record; a list is deliberately deferred.

## Edge cases

- Push disabled instance-wide: the capability response says so, and the subscription write answers 503 rather than storing a subscription that can never be delivered to.
- The same browser re-subscribing after the push service rotated its endpoint arrives as a new endpoint. That is correct; the stale row is pruned by the delivery job when it turns out to be gone, not here.
- Rate-limit the subscription write with the existing `internal/ratelimit` middleware. It is a cheap authenticated write that a loop could hammer.
