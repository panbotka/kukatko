# Stack operations leave no audit trail

Grouping photos into a stack, changing a stack's primary photo and ungrouping all change what the library shows, but write nothing to the audit trail. Close that gap.

Reported from running the Veselice library (repo `fotky`), production 0.21.0 / 555927e, with a reproduction on 14 Sep 2026: a `stacks group` followed by `stacks set-primary` both succeeded and left a hole between two `photos.bulk` entries. Confirmed in the source — `internal/stacks/`, `internal/photos/store_stacks.go`, `internal/photoapi/stacks.go` and `internal/processapi/processapi.go` contain no reference to the audit package at all, while a comparable audited path (`internal/organizeapi/labels.go`) has fifteen.

## Requirements

- All four stack mutations write an audit entry: `POST /photos/stack`, `POST /photos/{uid}/stack/primary`, `POST /photos/{uid}/unstack`, `POST /photos/{uid}/unstack-all` (routes at `internal/photoapi/http.go:371-374`).
- `POST /process/stacks` (`internal/processapi/processapi.go:295`) writes one too — it is the same gap.
- Every entry is written inside the **same transaction** as the mutation it records, per the project's audit rule. A failed mutation leaves no entry; a written entry means the change committed.
- Action names follow the existing `<entity>.<verb>` convention in `internal/audit/audit.go`, which distinguishes single-target `photo.*` from multi-target `photos.*`: `photos.stack`, `stack.set_primary`, `stack.ungroup`, `stack.ungroup_all`, `stacks.detect`. Add them to that const block.
- The `details` payload is rich enough to reconstruct the change: the stack uid, the photo uids involved, and for set-primary both the previous and the new primary. For ungroup, the uid of the photo taken out. `photos.bulk` is the quality bar.
- The entry carries the acting user, IP and user agent the way every other audited endpoint does.

## Acceptance

- Integration tests prove an entry appears after group, set-primary and ungroup. Existing patterns to follow: `TestFaceAssignAudited` (`internal/facematch/facematch_integration_test.go:449`) and `internal/organize/audit_integration_test.go`.
- A test seeds the acting user — an audit entry's actor is a foreign key and an unseeded actor fails with SQLSTATE 23503.
- `make check` passes.

## Implementation notes

- The idiom: the handler builds `audit.FromRequest(r, user.UID).Entry(action, targetType, targetUID, details)` and passes the entry **down** into an `…Audited` store method, which calls `audit.Write(ctx, tx, entry)` on the same `pgx.Tx` before the commit. See `runStateChange` (`internal/photoapi/http.go:886`) and `mutateAudited` (`internal/photos/audit.go:102`); the variant that carries details is `AttachLabelAudited` (`internal/organizeapi/labels.go:129`).
- No new transaction plumbing is needed — every stack mutation already runs through `Store.inTx` (`internal/photos/store_stacks.go:324`), so `…Audited` variants can write inside the existing closure.
- Three of the four handlers are one-liners delegating to a shared `runStackMutation` (`internal/photoapi/stacks.go:153`), which is the cheapest place to hook in. `handleStackSelection` has a different shape and needs its own.
- The awkward part is threading the entry through `stacks.Service`, whose `Store` interface (`internal/stacks/service.go:23-30`) needs the extra parameter.
- `audit.Write` takes an `Execer` satisfied by both the pool and a `pgx.Tx`.
- Beware: stamping `entry.TargetUID` inside the mutate closure is lost — the audit row then gets a NULL target. Set it before handing the entry down.
- Docs: `docs/API.md` for the endpoints, `docs/PACKAGES.md` if a package's description changes.
