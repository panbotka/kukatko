# The review game becomes about people, and starts listening to "I don't know"

Two complaints, one game. It asks about too many things that are not faces, it asks about the
same person five times running, and when the player says they do not recognise someone it
forgets that by the next restart and asks again.

## Evidence (read from the code on 2026-08-12)

- **The mix of kinds is not configured anywhere.** `internal/review/mixer.go` only *interleaves*
  kinds — `kindCost` charges a repeat and charges more for a third in a row — so the actual
  proportion of faces to labels falls out of how many candidates each source happened to
  produce. The nearest thing to a knob is the scan budget: `review.face_budget: 8` subjects
  against `review.label_budget: 6` labels per rebuild, which is why labels are so present.
- Five kinds reach the queue, not two: faces, labels, places, duplicates and outliers
  (`mat.faceQs`, `labelQs`, `placeQs`, `dupQs`, `outlierQs` in `queue.go`).
- **`maxSameEntityRun = 2` is a hard-coded constant** (`internal/review/variety.go:43`), and the
  rule it serves holds only "as long as any other entity still has a question". When one
  subject dominates the pool there is nothing to interleave with, so the run rule cannot fire —
  the likely reason five of one person get through. `review.go:184` records that two in a row
  is deliberate: a second face of the same person is easier for the player, not harder.
- **"I don't know" is not remembered.** `AnswerSkip` calls `sess.consume(questionID,
  resultSkipped, false)` — in-memory session state, and `session.go:6` says plainly that losing
  a session on restart forgets the skips. Sessions are per user and pruned on an idle TTL.
- Operationally relevant: the queue rebuild already spends its **entire 15 s deadline** and
  serves a partial queue, with the budget going on label similarity — production logs show
  `expand: kNN over a source photo` failing label after label, because
  `docs/THRESHOLDS.md:192` records that the label threshold `1 − band_min = 0.55` now admits
  **95.6 %** of the library under SigLIP 2. Asking fewer label questions relieves this.

## Requirements

### The game is about people

- Which kinds the game may ask about, and in what share, becomes **configuration rather than an
  emergent property**. The default leaves the queue to faces.
- Restoring another kind is then a config edit, not a code change — the "95 % faces / 5 %
  labels" this started as must be expressible in the new keys.
- The empty-queue reason stays truthful: when the faces run out the game says so, rather than
  quietly refilling with kinds the operator switched off.

### It stops asking about the same person five times running

- The run limit holds **in practice**, including when one subject dominates the candidate pool
  — which is the case the current rule cannot handle.
- Diagnose that before changing any number. The reported five-in-a-row is a symptom; whether
  the cause is a thin pool (too few subjects scanned per rebuild), the run rule standing down
  when no other entity has a question, or the round being refilled from one subject's tier,
  decides which fix is right. A stricter constant that still cannot fire fixes nothing.
- Whatever widens the pool is weighed against the rebuild deadline. The queue has no spare
  budget today, so a bigger face scan has to be paid for — the shrinking label share is where
  that payment comes from. Measure the rebuild before and after.

### "I don't know" is remembered, forgivingly

- A skip is counted **per (user, subject)** and survives a restart. That is new persisted state
  — a table, a migration, and a classification in `internal/reset/tables.go`.
- **Three** skips about one person mute that person for that user. Two are forgiven: an unclear
  photo is not the same as an unknown face.
- The mute is a pause, not a verdict. After a cooling-off period the game may ask once more,
  and only on a photo the player has **not** been asked about before — a different face of the
  same person deserves its own chance. Another skip re-mutes, and the pause grows rather than
  resetting to the same short wait.
- A photo that enters the library after the mute is not suppressed: a new face of that person
  is exactly what might be recognisable.
- The threshold and the cooling-off period are config keys with documented defaults, not
  constants.
- Muting is strictly per user. One player's "I don't know" must never quiet the game for
  anybody else.

### A skip is not a rejection

- Nothing about this may reach the catalogue. A skip must not become an `internal/feedback`
  rejection, must not exclude the person from `internal/candidates`, `internal/sweep` or the
  face-assignment paths, and must not change any identity. It says "don't ask *me* this",
  never "this is not that person" — conflating the two would poison recognition for everyone.

## Out of scope

- Splitting the review bands per space (`review.label_band_min` and friends), the fix
  `docs/THRESHOLDS.md` records for the label drift. It stays a separate change.
- What a yes/no answer does, the leaderboard, and the streak/breather machinery.
- Any change to face detection or clustering itself.

## Implementation notes

- The in-memory `session.skipped` set keeps its job — shelving a question for the current
  session. The persisted counter sits beside it rather than replacing it.
- A new table missing from `internal/reset/tables.go` fails `make test-integration` late, in
  `internal/reset`, with an error that does not obviously point back here.
- New config keys go into the `Config` struct, `setDefaults`, `config.example.yaml`, the config
  tests **and** `docs/OPERATIONS.md` in the same change.
- A skip is per-user game state, not a curation act, so it stays out of the audit trail — the
  audit records what happened to the library, and nothing here does.
- Tests: the kind-share selection as a unit (including a share of zero and an all-faces
  default), a test that pins the same-person run limit with a pool dominated by one subject,
  and integration tests for the skip counter — muting at the threshold, the cooling-off retry
  landing on an unseen photo, a post-mute photo getting through, and one user's mute leaving
  another user's queue untouched.
