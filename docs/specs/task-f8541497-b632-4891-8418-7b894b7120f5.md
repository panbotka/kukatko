# GET /audit answers a typo with an empty list

A misspelled filter on the audit listing returns HTTP 200 and no entries, which reads as "this person did nothing" rather than "you asked wrong". Reported from running the library: `?user=panbotka` (a username where a uid belongs) cost half an hour of looking for actions that were there all along.

The inconsistency is precise. In `parseFilter` (`internal/auditapi/auditapi.go:187`) the four filters `user`, `entity_type`, `entity_uid` and `action` are taken verbatim with `q.Get(...)` and never checked, while `since`, `until`, `limit`, `offset`, `via` and `decision` — parsed in the same function — all validate strictly and answer 400. An entirely unknown parameter (`?actor=`, `?from=`) is ignored without a word.

## Requirements

- An `action` value that is not one of the known audit actions is refused with 400 naming the offending value. The actions are a closed set of constants in `internal/audit/audit.go:52`, so an unrecognised one is always a mistake. Follow the existing `via`/`decision` pattern, which already answers 400 from this same function.
- A `user` value is resolved as either an account uid **or** a username, so `?user=panbotka` does what the caller plainly meant. A value matching neither is refused with 400; an existing account with no recorded actions keeps answering 200 with an empty list, because that is a true answer.
- An unknown query parameter is refused with 400 naming the key, rather than ignored. The allow-list must cover every parameter the two existing pages send — read `web/src/services/audit.ts` and prove with a test that both listings still work unchanged.
- **`entity_uid` is deliberately left unvalidated.** The audit trail outlives the entities it describes: an entry about a purged photo is exactly what the trail is for, so refusing a uid that no longer resolves would break the endpoint's purpose.
- **`entity_type` is left unvalidated too.** It is a free string by design (`internal/audit/audit.go:425`), not a closed set, so an allow-list would go stale the moment a new entity is audited.
- Both `GET /audit` and `GET /audit/mine` behave the same way — they share `parseFilter`.
- The 403 that `GET /audit/mine` already gives for another user's uid must keep working once `user` also accepts usernames: asking for somebody else's actions by *name* is the same refusal, not a 400.

## Acceptance

- A misspelled action, an unknown parameter and a nonexistent user each answer 400 with a message naming what was wrong.
- A username and that account's uid return identical results.
- A real user with no actions still answers 200 and an empty list.
- An `entity_uid` that no longer exists still returns its entries.
- `GET /audit/mine` still answers 403 for another user, whether named by uid or username.
- The existing audit pages in the frontend are unaffected.
- `make check` passes.

## Implementation notes

- Everything belongs in `parseFilter` and its helpers; the package is read-only over the trail and must stay that way.
- Resolving a username needs the auth store, which `internal/auditapi` does not depend on today — pass a narrow lookup function through `Config` rather than handing the package a whole user service.
- Rejecting unknown parameters is the change most likely to break a caller. Enumerate the allow-list from the handler's own parsing, and cover it with a test that sends exactly what the frontend sends.
- Docs: `docs/API.md` for the tightened filter behaviour.
