# Privacy guard in the quality gate

The repository `panbotka/kukatko` is PUBLIC, and agents have repeatedly committed private data (production hosts and IPs, private paths, live URLs, real names). Owner decision (2026-10-16): Botka task specs stay tracked in `docs/specs/` — so they are committed with every task and must be checked like any other file. Add a guard to `make check` so private data fails the gate instead of reaching GitHub.

## Requirements
- A Go test (or small checker wired into `make check`, following how `internal/tenancyguard` and `make docs-budget` are wired) that scans every tracked text file (`git ls-files`, skip binaries) — `docs/specs/` explicitly included — and fails with `path:line: <rule name>` for each hit. Also scan untracked files under `docs/specs/` (a task's own spec is synced there before it is committed), so a private value in a new spec fails the gate before the commit.
- Two rule sources:
  1. Generic, committed rules that contain no private values: an SSH-style `user@host` target, absolute home or mount paths (`/home/<user>/`, `/mnt/<...>/`), `op://` secret references, private-key headers, an IPv4 address outside the documentation ranges (192.0.2.0/24, 198.51.100.0/24, 203.0.113.0/24) and outside `_test.go` synthetic tables, `*.cloudflarestorage.com` account endpoints, e-mail addresses other than `example.org`/`example.com`/`.invalid`/`users.noreply.github.com`, Czech/international phone numbers. Keep the list short and precise; each rule has a one-line reason.
  2. Private rules read at run time from the gitignored `.secrets/privacy-patterns.txt` (one extended regex per line, `#` = comment) when that file exists; when it is absent (CI, the build box) only the generic rules run and the test says so via `t.Log` — it never fails or skips silently for that reason. Never print a private pattern itself in output — print only the line number of the rule in that file.
- An allow-list file in the repo, keyed by `path:line reason` like `internal/tenancyguard/allow.txt`, for intentionally synthetic cases; stale entries fail, as in tenancyguard.
- Tests for the checker itself (a hit, a miss, an allow-listed hit, a stale allow entry, an untracked spec hit, the missing private file). Test inputs must be synthetic (`example.org`, documentation IP ranges).
- Document the guard in `docs/OPERATIONS.md` (what it checks, how to allow-list, that specs are in scope and how to write a spec without private values) and add the package line to CLAUDE.md's package map if you add a package (keep CLAUDE.md within its 300-line budget — fold a line elsewhere if needed).
- The tree is expected to be clean already; if the guard finds real private data, fix it (save the removed text first to the private backup directory named in the pattern file's header) rather than allow-listing it.
- Stage only your own hunks; never `git add -A`.

## Done when
- `make check` runs the guard and passes; deliberately adding a line like `ssh someone@somehost` to a tracked doc, or a real-looking phone number to an untracked file in `docs/specs/`, makes it fail (verify, then revert). Committed and pushed.
