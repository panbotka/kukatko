# The face overlay has three states where two would do, and names them backwards

Raised on 2026-08-03 while looking at a photo's faces panel:

> Jaky je rozdil mezi nepojmenovany a bez osoby? […] A nebylo by lepsi vubec unassigned
> nemit. Tzn., embedding rika ze je tam oblicej a ten se muze priradit?

## What exists today

`web/src/lib/faceState.ts` classifies every face into three states, and the overlay, the
faces panel and the assign panel all colour them the same way:

| state | colour | shown as (cs) | means |
| --- | --- | --- | --- |
| `assigned` | green | the person's name | a marker names a subject |
| `unassigned` | yellow | "Bez osoby" | a marker covers the face, nobody named on it |
| `unmatched` | red | "Nepojmenovaný" | a detected face with no marker at all |

Two things are wrong with that.

**The labels are the wrong way round.** "Nepojmenovaný" is the weaker claim — it says only
a name is missing, which describes the *yellow* state. It is attached to the red one, where
the marker is missing too. The English (`detected` / `unassigned`) is no clearer, and
`STATE_KEY` in `FacesPanel.tsx` maps `unmatched -> faces.state.detected`, which is a trap for
the next reader.

**The distinction costs the user attention and buys nothing.** `internal/facematch` already
handles both in one step: `ActionCreateMarker` creates the marker *and* assigns the subject,
`ActionAssignPerson` assigns to the existing one. Naming a red face and naming a yellow one
are the same single click; only the verb the backend picks differs. The marker is
bookkeeping inherited from PhotoPrism (which has boxes) meeting Kukátko's detector (which has
vectors).

Measured on production, 2026-08-03:

```
markers of type 'face'                      21 171
markers with no face row (no embedding)        144   (0.7 %)
faces total                                115 457
faces with no marker                        94 194   (82 %)
unassigned markers with no embedding             2
```

Red is not an edge case — it is 82 % of the library, reported in the colour that means
"something is wrong".

## What to build

Collapse `unassigned` and `unmatched` into **one** not-named state, in the state machine and
in every consumer: `faceState.ts`, `FaceOverlay.tsx`, `FacesPanel.tsx`, `FaceAssignPanel.tsx`,
`PeoplePanel.tsx`, `useFaces.ts`. Name it so that it says what is missing, in cs and en. Do
not keep a third colour for "has a marker" — that is the fact nobody needs.

**Keep the backend state machine as it is.** `create_marker` vs `assign_person` is a correct
internal distinction and the API reports it; this task changes what the UI *shows*, not how
assignment works. If you find yourself editing `internal/facematch`'s actions, stop.

## The distinction actually worth surfacing

Whether the face has an **embedding**, because that decides whether automation can ever help:

* face with an embedding — the sweep can suggest it, similarity search finds it, naming it
  teaches the recogniser something;
* marker with no embedding (144 of them) — nameable by hand, but no similarity search will
  ever surface it and it is a dead end for the review game.

Surface that instead of the marker/no-marker split, if it can be done without adding a third
colour back — a small marker on the row is likely enough. Check first whether the faces
payload even carries the fact; if exposing it means a backend change, say so and scope it
rather than half-doing it.

## Timing — this gets more urgent, not less

Today most of those 94 194 marker-less faces are attached to the nameless catch-all subject
(`sunuikf1e9jdpjog5qgomsvgrb`), so the panel rarely shows many at once. Task
`bf97784c-bf48-45fd-94c1-0fcc21e70454` detaches 111 155 faces from it. After that runs, this
state becomes the overwhelming majority of what a user sees — so the colour scheme should be
right *before* the library turns red, not after.
