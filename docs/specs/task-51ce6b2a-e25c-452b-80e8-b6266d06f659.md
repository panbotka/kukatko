# The HLS transcode job

Every uploaded video gets an HLS rendition, produced off the request path by the existing job
queue. This task executes what the previous one decided; it does not revisit encoding parameters.

Depends on the HLS groundwork and encoder-plan tasks.

## Contract (shared with the follow-up tasks)

A new table `photo_hls_renditions`, keyed by photo and rendition name, holds the media playlist
ffmpeg wrote plus the numbers the master playlist needs: pixel dimensions, bandwidth, codecs
string, segment count, duration. Objects go to `hls/<file_hash>/<rendition>/`.

## Requirements

- A migration creates `photo_hls_renditions` with a foreign key that cascades on photo deletion.
- A new job type `hls_transcode` and its handler package encode one photo: run ffmpeg into a
  temporary directory, upload the init segment and every media segment to the object store, then
  write the rendition row. A re-run of the same photo replaces its rendition instead of
  duplicating it, and a failed run leaves no half-written row and no orphaned partial upload.
- Uploading a video enqueues the job in the same transaction that records the photo, exactly
  where the embedding and face jobs are enqueued today. A photo that is not a video enqueues
  nothing.
- The job type gets its **own worker pool with concurrency 1**: a batch of uploaded videos must
  serialise rather than saturate the machine and starve the rest of the queue.
- The ffmpeg run is bounded by a timeout that **scales with the clip's duration**, not a flat
  constant. Long videos are expected and must be allowed to finish.
- Configuration under `video.hls`: whether the feature is on, the segment length, and the list of
  renditions. Add the keys to the config struct, the defaults, `config.example.yaml`, the config
  tests and `docs/OPERATIONS.md` in one go.
- Tests: an integration test against the test database that encodes a short generated fixture end
  to end and asserts both the uploaded objects and the row, plus a test proving a re-run is
  idempotent.

## Implementation notes

- A new table must be classified in `internal/reset` or the reset integration test fails late,
  long after `make check` looked green.
- Generate the test fixture with ffmpeg's synthetic sources at test time and keep it a second or
  two. Follow whatever the existing video tests do when ffmpeg is not installed.
- Integration tests share one database — run them with `-p 1` or they deadlock, and the failure
  will look like your regression when it is not.
- Docs: `docs/PACKAGES.md`, `docs/OPERATIONS.md`, plus the package map line in `CLAUDE.md`.
