# Notifications in settings: this browser, the other devices, and which messages

The last piece of Kukátko's push notifications: the place a person turns them on after having said no once, sees which devices are registered, and chooses which messages they want.

## Context that already exists

`web/src/pwa/push.ts` covers support detection, permission state, requesting permission (only ever from a user gesture), subscribing with the server's VAPID public key, registering with the server and unsubscribing.

Backend endpoints exist for: the VAPID public key and whether push is enabled instance-wide; registering and removing a subscription by endpoint; listing the calling account's subscriptions (user-agent, created, last used — never the client keys); and reading and replacing the account's notification preferences, where the read already returns the effective set with defaults merged in. Two kinds exist: being tagged in photos, and a registration waiting for approval — the second only ever reaches an admin or a maintainer.

## Requirements

- A notifications section on the existing account or settings page. There are two such pages in this project — work out which one fits the split they already have rather than guessing.
- A master control **for this browser**: when off, a button that turns it on; when on, a clear statement that it is on and a way to turn it off. Turning it off unsubscribes in both the browser and the server.
- Per-kind checkboxes under it, for the kinds that apply to this account's role. The registration kind is shown **only** to an admin or a maintainer — nobody else should see a setting for a message they can never receive.
- The other registered devices listed with something a person actually recognises: the user-agent summarised readably — "Chrome on Android", not a raw UA string — and when each was last used, each removable. The browser being used right now is marked as such.
- **Make the two scopes visible in the copy.** Per-kind preferences are an account setting and apply to every device; the master control is per browser. This is the one thing people reliably get wrong about web push, so the wording has to carry it.
- When the browser has denied permission at its own level, say so and explain it has to be re-allowed in the browser's site settings. Do not offer a button that cannot work.
- When push is off instance-wide, the whole section says so rather than rendering dead controls.
- Czech and English through i18next, Czech default. Note this repo's locale-test convention: set the language **before** rendering, not after.

## Verification

Component tests: the off state turns on and subscribes; the on state turns off and unsubscribes; a per-kind toggle saves; the registration kind is hidden for a viewer and shown for an admin; a denied permission shows the blocked explanation instead of a button; push off instance-wide shows the disabled state; a listed device can be removed; the current browser is marked as current.
