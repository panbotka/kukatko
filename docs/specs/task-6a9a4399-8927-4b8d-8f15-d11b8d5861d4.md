# Grid scroll memory restores when nobody asked it to

Clicking a list in the navigation lands the reader mid-list after a burst of fetching, and a photo
opened from an outside link overwrites the library's remembered position.

## Background

Two defects in one module.

1. **No `POP` gate.** `useNavigationType` / `NavigationType` appears nowhere in `web/src`.
   `hooks/useGridScrollMemory.ts:97` reads the stored entry in a `useMemo` on the key and hands
   `restoreFrom` / `restoreScrollY` / `restoreUid` to `PhotoGrid`
   (`components/library/PhotoGrid.tsx:357-365`), which restores as it mounts — whatever brought the
   reader there. The remembered `count` is fed back as `initialCount` as well
   (`pages/FavoritesPage.tsx:56-60`, the same pattern in `LabelDetailPage`, `PlacesPage`,
   `SearchPage`, `SubjectPage`, `TaskDetailPage`), so the page eagerly re-fetches as many pages as
   were loaded last time. Clicking "Knihovna" or "Oblíbené" in the navigation — an explicit "take me
   to this list" — therefore lands mid-list.
2. **A context-free arrival stamps the library's entry.** `pages/PhotoDetailPage.tsx:366` calls
   `rememberGridPhoto(listScrollKey, uid)` in an unconditional effect. For a photo opened with no
   view params `backHref` falls through to the bare library path (`lib/detailView.ts:115`), so the
   key is the library's. `rememberGridPhoto` (`lib/gridScroll.ts:253-261`) only updates an existing
   entry, so it is silent in a cold tab — but once the library has been scrolled this session, a
   photo opened from a push notification or a pasted link overwrites the photo uid on that entry.
   The reader later taps "Knihovna" and the grid scrolls to a photo they never picked from it.

This is the same shape as the bug fixed in `757ead7`: an arrival from outside poisoning remembered
in-app state.

## Requirements

- A grid's position is restored only when the navigation was a `POP`. Closing the photo viewer
  navigates back, which is a `POP`, so returning to the grid keeps working exactly as today. A fresh
  load and a reload are also `POP` in react-router, which is wanted: a refresh keeps the reader's
  place.
- A `PUSH` navigation — a nav link, a link from another page — starts the list at the top, and does
  not seed `initialCount` from the stored entry either. The eager refetch goes with the restore.
- A photo is never recorded against a list it did not come from. A viewer opened with no view params
  has no list context and leaves every stored entry untouched.
- Everything else about the memory stays: the per-view keying, the cap on remembered views, and the
  one-shot hand-off that reveals the photo as the grid lands and then forgets it.

## Testing

- The restore path: a `POP` into a grid restores position and count; a `PUSH` into the same grid
  starts at the top with the default count. Cover the library and at least one other consumer.
- The stamping path: a viewer mounted with no view params leaves a previously stored library entry
  unchanged; a viewer opened from a list still records its photo against that list.
- Existing `useGridScrollMemory` and `PhotoGrid` tests pass, or are updated where they encoded the
  old behaviour.
- The grid is virtualized, so a jsdom test mounts no items — route assertions through the real list
  the way the existing tests do rather than asserting on rendered tiles.
