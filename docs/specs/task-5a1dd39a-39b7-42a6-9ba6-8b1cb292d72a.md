# Reverse geocoding never runs for uploaded photos

Verified on the box staging (commit 68e805e, 2026-09-06) and confirmed on production numbers. A photo uploaded with GPS coordinates never gets a place: the Places page stays empty, the photo's processing panel shows "Určení místa" as never done, and the Stav systému tile "Bez místa" counts every photo. The only things that ever create a `places` job today are manual: a location edit, the per-photo "schedule the missed step" button, the geo-estimate and the maintainer backfill `POST /process/places`.

## Root cause (verified, do not re-derive)

- `internal/ingest/ingest.go` (≈ lines 535–547) and `internal/ingest/jobs.go` enqueue `image_embed`, `face_detect`, `ocr` and `sidecar` after an upload — and nothing else. There is no call to `EnqueuePlaces`.
- `EnqueuePlaces` (`internal/jobs/enqueuer.go` ≈ line 129) is called only from `internal/bulkapi` (bulk location edit), `internal/photoapi/place.go` (manual location), `internal/processing/service.go` (the per-photo "run the missed step"), `internal/geoestimate` and `internal/placesjob` (the backfill).
- Staging: 108 of 398 photos have GPS (the map shows them), every one of them reports `places: pending` in `GET /photos/{uid}` → `processing`, and `SELECT type FROM jobs WHERE type='places'` returns **zero rows**. `MAPY_API_KEY` is configured there and the map tiles work, so it is not a missing key.
- Production (viewer credentials, `GET /api/v1/system/stats`): `photos_with_gps 2523`, `photos_geocoded 2451`, `photos_pending_geocode 72` — the 72 are the uploads since the last manual backfill.
- The credit protection already exists: `placesjob.WindowBudget` / `BudgetConfig` are wired in `cmd/kukatko/places.go`, and `internal/placesjob` is "rate-limited due to credits" by design. Enqueueing more jobs does not spend more credits than the budget allows; it only makes the queue carry the work.

## Requirements

- After a successful upload of a still or video that carries GPS coordinates, a `places` job is enqueued for it, inside the same transaction pattern the other ingest jobs use (`enqueuePhotoJob` dedup rules apply, so a repeated enqueue is harmless). Photos without coordinates get no job.
- When geocoding is not configured (no `maps.mapy_api_key`), do not enqueue at ingest; the processing panel's "Neprovádí se" wording is then correct. When it is configured, the panel must show the step as waiting, not as "not performed".
- Add a maintenance option under "Co doplnit" on the Údržba page: "Určit místo u fotek se souřadnicemi (N)" that enqueues `places` for every live photo with coordinates and no place, using the existing backfill in `internal/placesjob` (see `internal/processapi` for how the other checkboxes reach their backfills). N is the same number the Stav systému tile "Bez místa" shows for photos that actually have coordinates — make that tile a link to this option, as the other yellow tiles link to the screen where they are resolved.
- The budget must still bound the spend: enqueueing 2 500 jobs on production must not burn the mapy.com credit window; verify the `WindowBudget` defers rather than fails when exhausted, and document the behaviour.
- Tests: an ingest integration test proving a GPS upload enqueues `places` and a GPS-less upload does not; a test that ingest enqueues nothing when geocoding is unconfigured; a maintenance/processapi test for the new option counting and enqueueing only photos without a place. Frontend Vitest for the new checkbox and the linked tile.
- Docs: `docs/PACKAGES.md` (ingest, placesjob, maintenance), `docs/API.md` if the maintenance/process endpoint grows an option, `README.md` one line (places now fill in on their own).

## Out of scope

- Do not run the backfill against production and do not touch production data; the release will do it through the new maintenance option, run by the owner.
- Do not change the geocoder, the budget numbers or the place cache schema.
