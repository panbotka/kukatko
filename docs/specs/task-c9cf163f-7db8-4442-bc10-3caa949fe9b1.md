# Declaring a date unknown from the grid, and seeing it in the library

The catalogue can already hold "the date of this photo is unknown": clearing a photo's date
preserves the value it used to have, stamps `taken_at_source = "unknown"`, and the search key
`dated:no` finds every photo without a date. What is missing is the way in — the owner has a
great many of these photos and needs to mark them by the handful, not one at a time — and the
way back out, because a set-aside date is currently invisible.

## What already exists

- `POST /api/v1/photos/bulk` accepts `clear_taken_at` next to `set_taken_at {precision, value}`;
  the frontend types live in `web/src/services/bulk.ts`, driven by `hooks/useBulkEdit.ts`.
- The library grid has hover-select and a floating `BatchActionBar`
  (`web/src/components/organize/BatchActionBar.tsx`) whose "more" opens `BulkEditModal.tsx`. That
  modal already has a `takenAtMode` field with a precision picker, and a confirm step that
  already triggers on a date change or a large selection.
- `PATCH /api/v1/photos/{uid}` clears the date when `components/photo/MetadataPanel.tsx` submits
  an empty date field; the photo payload carries the preserved original.
- `components/library/FilterBar.tsx` → `AdvancedFilters` holds tri-state selects (`has_gps` via
  `TriStateSelect` is the model to copy), backed by `LibraryView` in `web/src/lib/libraryView.ts`
  and chips in `components/library/filterChips.ts`.
- `web/src/lib/takenDate.ts` formats dates by precision (`formatTakenLabel`, `formatTakenPeriod`).

## Requirements

- **`BulkEditModal` gains an "unknown" date mode.** `takenAtMode` currently chooses between
  leaving the date alone and setting one; add the third choice, which sends `clear_taken_at`.
  Picking it hides the precision picker and the value field — there is nothing to type. It goes
  through the confirm step that a date change already triggers, and the confirmation must say how
  many photos lose their date and that the current value is kept and can be put back.
- **The filter bar can find them.** Add a tri-state control to `AdvancedFilters` next to the GPS
  one — any / has a date / no date — wired to a new `LibraryView` field, a chip in
  `filterChips.ts`, and compiled to `dated:yes` / `dated:no`. Label it after the date rather than
  after the flag: "Datum" / "Date", with options reading "má datum" / "bez data".
- **The detail shows a set-aside date and can take it back.** In the info drawer
  (`MetadataPanel.tsx`), a photo with no date but a preserved one renders that value as muted
  secondary text — "původně zaznamenáno: …" / "originally recorded: …" — with an action putting
  it back as the photo's date. Restoring is an ordinary date edit through the existing `PATCH`
  path, not a new endpoint. A photo that never had a date shows nothing extra.
- **Undated photos are their own group at the end.** Where the library groups photos into date
  sections, undated photos must land in a single trailing group headed "Neznámé datum" /
  "Unknown date" instead of being silently appended to the oldest real period. First establish
  whether that grouping is computed on the frontend (the timeline hook) or handed down by the
  timeline endpoint (`internal/photos/store_timeline.go`), and put the group where the grouping
  already lives — do not build a second grouping layer. If the backend owns it, extending the
  bucket is in scope. If the grid turns out to have no date section headers at all today, drop
  this requirement and say so in the commit body rather than inventing a grouping layer for it.
- **i18n**: every new string in both `cs` and `en`. Czech is the default — write the Czech first
  and make it read naturally, not as a translation.
- **Tests.** Component tests for the modal's third mode (the payload contains `clear_taken_at`,
  the precision controls disappear, the confirm step names the count), for the filter control
  round-tripping through the URL query params, and for the drawer rendering and restoring a
  preserved date. A test that undated photos form the trailing group — an integration test
  instead, if the grouping turns out to be backend-side.

## Implementation notes

- Do not add a one-click "unknown date" button to `BatchActionBar`. Losing a date feels
  destructive enough that it belongs behind the modal with its confirmation, next to the other
  date controls.
- Reuse `formatTakenLabel` from `lib/takenDate.ts` for the preserved value instead of formatting
  it inline — the preserved date has a precision too.
- Long grids are virtualised with `react-virtuoso`; if you touch grouping, check the change in a
  real browser and not only in jsdom, where no virtualised items mount.
- Definition of Done per `CLAUDE.md`: `docs/FRONTEND.md` for the changed components and the new
  `LibraryView` field, `docs/API.md` only if the timeline response shape changes, `README.md` for
  the user-visible feature; then `make check`, then commit and push.
