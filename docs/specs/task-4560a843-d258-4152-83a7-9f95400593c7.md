# Give the system administrator the account actions the old /users page had

## Context

Multi-tenancy step 25 replaced the project's `/users` page (the old `UsersPage`, deleted, see git history before that commit) with `/p/:slug/members`, which manages memberships only. The old page also carried **account-record** actions that now have no UI: create an account, rename (`PUT /admin/users/{uid}/username`), edit profile/e-mail/note/linked person (`PATCH /admin/users/{uid}`), set a password (`POST /admin/users/{uid}/password`), **issue a password-reset link** (`POST /admin/users/{uid}/password-reset` — the only way somebody who forgot their password gets back in; there is no self-service "forgot password"), and block/unblock (`POST /admin/users/{uid}/disable`). The client functions still exist in `web/src/services/users.ts` (`createUser`, `updateUser`, `renameUser`, `setUserDisabled`, `resetUserPassword`, `issuePasswordReset`). The old components (`ResetLinkModal`, `UserActions`, `UserCard`, `UserEmail`, `UserStateBadges`, `errors.ts`) can be recovered from git history.

Accounts are instance-level (one global account, many memberships), so these actions belong to the system administrator: `/system/users` (`SystemUsersPage`, maintainer-only), today showing only the instance role.

### Role vocabulary left over from the transition (verify with rg before starting)

Step 39 removed the request-path fallbacks to the bootstrap project but left the `/admin/users` endpoints speaking the pre-tenancy five-rung vocabulary: `auth.AccountRole` (JSON `role`, `Split()` into instance role + bootstrap-project role), `User.ProjectRole`, and the `userColumns` bootstrap subqueries in `internal/auth/store.go`; creating or updating an account through `/admin/users` still writes the membership of project `v`. Every `/admin/users` route is `RequireMaintainer` and the SPA no longer calls them. The `/auth/me` top-level `subject_uid` likewise comes from the bootstrap membership (`store.go` ~48–49) while `projects[]` carries the per-membership value.

## Requirements

- On `/system/users`: per-account actions Upravit (profile incl. username, e-mail, note, person), Odkaz na heslo (the reset-link dialog with copy field and the mail-off/placeholder-address wording), Změnit heslo, Zablokovat/Odblokovat behind a confirmation, and Nový účet.
- Check which of the `/admin/users` endpoints are maintainer-gated vs project-admin-gated today and decide (document in docs/API.md) whether they should all become `RequireMaintainer` — a project admin of one tenant must not see or edit accounts of another.
- The page and the endpoints it uses speak the tenancy vocabulary only: the account record exposes `instance_role` (`user`/`maintainer`) and nothing project-shaped; "Nový účet" creates an account with no membership (memberships are added on `/p/:slug/members` or via invite), and no `/admin/users` write touches `project_members` of `v` any more. Retire `auth.AccountRole`, `User.ProjectRole` and the `userColumns` bootstrap subqueries (or, if a caller still needs them, say which and why in docs/PACKAGES.md). The linked-person field ("person") is per membership, so edit it per project on the members page, or show it read-only here per project — not as one account-level value. Make `/auth/me`'s top-level `subject_uid` consistent with that decision (keep it documented as the bootstrap membership's value, or drop it in favour of `projects[].subject_uid` and update the frontend).
- Tests (Vitest + Go if the guards or the vocabulary change), docs/FRONTEND.md, docs/API.md, docs/PACKAGES.md, README.

## Out of scope

Membership management (that is `/p/:slug/members`), invitations.
