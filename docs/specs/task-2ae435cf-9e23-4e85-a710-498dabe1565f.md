# Refuse undecodable files on the public upload-link endpoint

Found in the v0.28 prerelease walkthrough (staging, commit 4aa69a3). An anonymous visitor of an
upload link (`POST /u/{code}/upload`) can upload any bytes named `.jpg`: 5 KB of /dev/urandom was
accepted as "1 nahrána", stored as a photo (`media_type=image`, `file_mime=application/octet-stream`,
0×0), filed into the link's albums immediately (grid tile "Náhled není dostupný"), and its
`face_detect`/`image_embed`/`ocr` jobs retry and fail. Ingest has always accepted such files for
signed-in editors; the link exposes it to anyone holding the URL.

## Requirements

- An upload through a link whose content is not a recognisable image or video (sniffed content /
  probe, not the extension) is refused **before** a photo row is created: 4xx with a stable error
  code, nothing stored, no jobs enqueued, no album/label filing, counted as a failure in the
  `upload_link.upload` audit only if that is how other refusals are audited.
- The public page shows the refusal per file in Czech/English ("Tohle není fotka ani video"), not
  the raw server string; retry is not offered for it (it would fail again).
- Real formats keep working: JPEG, PNG, WebP, HEIC, RAW (e.g. CR2/NEF/DNG), MP4/MOV/WebM — cover
  with tests using fixtures that already exist in the repo.
- Decide and document whether the same check applies to the authenticated `/upload` path; if it
  is cheap and safe, apply it there too (a 0×0 octet-stream "photo" is never useful).
- Integration test: junk bytes through a live link → refused, no `photos` row, no
  `upload_link_photos` row, no jobs.

## Repro
Create a link → open `/u/<code>` signed out → upload `head -c 5000 /dev/urandom > broken.jpg`.
