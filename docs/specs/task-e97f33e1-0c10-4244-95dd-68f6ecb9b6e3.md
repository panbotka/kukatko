# Push an administrator when a registration is waiting

When somebody registers on a Kukátko instance whose registration is open, their account is created disabled and waits for an admin or a maintainer to approve it. Today the approvers only learn about it by e-mail: `scheduleMail` in `internal/auth/register.go` enqueues the `new_registration_pending` template to every account `ListApprovalRecipients` returns — the enabled admins and maintainers. E-mail can sit unread for a day, which leaves the person who registered staring at a locked account for no reason. This task adds a push notification alongside that mail.

## Context that already exists

`internal/pushjob` delivers Web Push durably: an `Enqueue` helper that runs **inside the caller's transaction**, refuses silently when push is off instance-wide or when the account has no subscriptions, and fans out one queue job per device so a retry never double-delivers.

`internal/notification` stores a notification record — uid, account, kind, title, body, deeplink path, optional frozen photo set — and per-(account, kind) preferences where an absent row means the default. The kind constant for "a registration is waiting for approval" already exists there, defaulting to on.

## Requirements

- On a successful registration, **in the same transaction that creates the account**, create one notification record per approval recipient and enqueue its delivery — but only for recipients who have not turned that kind off.
- The notification names the person: a title in the shape of "A new registration is waiting" and a body naming their display name, for example "Jan Novák has just registered." Both strings must be localised the way the existing mail templates are — look at how `internal/mailer` renders its Czech templates and follow that, do not invent a second mechanism. Czech is the default language.
- The deeplink points at the admin screen where a pending account is approved. Find that route in the frontend rather than inventing a path.
- Follow the precedent `scheduleMail` already sets in the same file: **the approvers' notification is best-effort.** A failure to schedule it is logged and the registration goes on. The registering person's own confirmation keeps its current, stricter treatment — failing to schedule *that* still fails the registration, because somebody holding an account they were never told about is worse than retrying. Do not change that balance.
- A recipient who has turned this kind off gets no push but **still gets the mail**. The two channels are configured separately and this task must not change mail behaviour at all.

## Edge cases

- No approval recipients (the only admin is disabled): nothing is sent and the registration still succeeds. That is already the mail path's behaviour — match it rather than adding a new failure mode.
- Registration is closed, or the instance approves accounts automatically: no notification. Only a registration that actually leaves somebody waiting produces one.
- Push disabled instance-wide: the enqueue helper already refuses silently, so no special case belongs in this file.

## Verification

Integration tests: registering creates one notification record per subscribed recipient and queues its delivery; a recipient who turned the kind off gets none while still getting the mail; an enqueue that fails is logged and does not fail the registration; a registration that rolls back leaves no notification and nothing queued.

## Documentation

`docs/ARCHITECTURE.md` if the registration flow is described there, and update the `internal/auth` entry in `docs/PACKAGES.md` to say it now notifies by push as well as by mail. No API shape changes, so `docs/API.md` should need nothing — check rather than assume.
