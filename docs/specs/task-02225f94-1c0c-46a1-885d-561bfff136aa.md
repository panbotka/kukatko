# A photo whose original cannot be decoded breaks the viewer and logs 500s

Some originals cannot be turned into a thumbnail (a corrupt JPEG, an unsupported or truncated RAW/DNG). Their `thumbnail` job ends dead, the library grid already shows the "Náhled není dostupný" placeholder, but the rest of the app does not cope.

## Reproduced (pre-release walk on the box staging stack, 2026-10-16; library contains a deliberately broken `broken.jpg` and a bogus `f.dng`)
- `GET /api/v1/p/<slug>/photos/<uid>/thumb/fit_720` (any size) answers **500** `{"error":"thumbnail unavailable"}` and the access log records it at **ERROR** level on every view. A missing derivative of a broken file is an expected state, not a server fault; 500s here also pollute error-rate metrics/alerts.
- Opening such a photo in the viewer (`/p/<slug>/photos/<uid>`) shows the browser's broken-image icon with the alt text "Bez názvu" inside an empty frame — no explanation, no way forward except the download.
- Pre-existing (the same code is in v0.31.0); not a regression of the tenancy work.

## Requirements
- The thumbnail route answers a non-5xx status for "this photo has no thumbnail and cannot get one" (pick the right code, e.g. 404 with a distinct error string, and document it in `docs/API.md`); a genuine I/O/storage failure still answers 500. The access log must not log the expected case at ERROR.
- The viewer shows the same "Náhled není dostupný" placeholder the grid uses (reuse the existing component/i18n), plus the existing original-download action, when the image fails to load or the photo is known to have no thumbnail. No broken-image icon anywhere (viewer, info panel "Podobné fotky", album covers, face crops).
- Other consumers of the thumbnail (featured album covers, subject avatars, upload-link page, notifications) degrade the same way.
- Tests: an integration test for the route's status on an undecodable original vs a storage error; vitest for the viewer placeholder on image error.
- Update `docs/FRONTEND.md` / `docs/API.md` accordingly.
