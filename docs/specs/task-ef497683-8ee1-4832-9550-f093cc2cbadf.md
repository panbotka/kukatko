# The position memory is built and wired, and it saves nothing

Opening a photograph and coming back drops the reader at the top of the list. This is **not a
missing feature** — the machinery exists (`lib/gridScroll.ts` and `hooks/useGridScrollMemory.ts`,
persisting to `sessionStorage` under `kukatko.gridScroll`) and every grid page already calls it.
It records the wrong number.

Measured on the live instance:

- Library, scrolled with real wheel events to `window.scrollY` 4000: the stored entry holds
  `scrollY: 0, count: 0`. Going back afterwards lands at `scrollY` 29 and the photograph that
  was open is not even mounted.
- A person's page, same test, scrolled to 1791: the stored entry holds `scrollY: 1791` and the
  return works. **That page is the working reference.**

The difference is one option. `PhotoGrid` runs react-virtuoso with `useWindowScroll`, so the
window owns the scrolling; `useGridScrollMemory` only attaches its window-offset listener when
it is given `track: 'window'`, and otherwise defaults to `track: 'virtuoso'` and relies on the
snapshot's `scrollTop`, which is 0 for a window-scrolled list. `SubjectPage` passes the option;
`LibraryPage`, `AlbumDetailPage`, `LabelDetailPage`, `SearchPage`, `FavoritesPage` and
`PlacesPage` do not.

Note that `LibraryPage` says in its own comment that "the offset alone restores it", which is
what the code was meant to do — so the intent is already recorded, only not carried out.

## Requirements

- Returning from a photograph to the list it was opened from restores the reader's position,
  with that photograph visible, on every grid page listed above.
- Fix it at the level where the mistake actually is. A page-by-page option that six of seven
  callers forget is a trap; prefer a default that is right for how `PhotoGrid` actually scrolls,
  or make the wrong combination impossible, over adding the missing option six times.
- Both ways back behave the same: the browser's back navigation and the viewer's own back
  control.
- After paging through several photographs with the arrows and then going back, the reader
  lands on the photograph they were last looking at, not the one they first clicked.
- Add a regression test that would fail on today's behaviour — the existing unit tests pass
  while the feature is broken in the browser, so a test that only exercises the hook in
  isolation is not enough.
- Do not reimplement the storage, the key derivation, or the restore path; they work.

## Edge cases

- A list whose length is not yet loaded when the position is restored (the stored `count` feeds
  `initialCount` so the document is tall enough first).
- The list changed while the photo was open (archived, or no longer matching a filter).
- A photo opened directly by URL, with no list behind it.
