# Hide a photo from the library without hiding it from albums and labels

Asked for on 2026-08-03:

> skryt z knihovny. jsou fotky, ktere chci mit ulozene, ale nechci je videt v knihovne.
> V albu nebo ve stitku at je klidne vidim, ale nechci aby byli viditelne v knihovne.
> Proste flag true/false. Defaultne vsechno viditelne.
>
> Pouzivat to chci napr. na scan nejakych dokumentu —
> https://kukatko.kotrzina.cz/photos/phvat1jm3qqmiood9cafuiovd3 — neni to uplne fotka,
> chci to mit v systemu, ale nechci to videt. Pokud to nekdo da do alba, tak tam to klidne
> byt videt muze.

That example is `tiraz_140`, a 3508x2480 JPEG — a scan, not a photograph. The library is
the firehose; this is about keeping such things out of it while keeping them addressable.

## Not `photos.private`

The `photos.private` column already exists, and it is **not** this. It hides nothing: it is
only a search filter (`private:yes` via `privateCond` in `internal/photos/store_query.go`),
its sidecar field is documented as "hides the photo from shared views", and every one of the
20 889 production rows has it `false`. It was meant for sharing, which `CLAUDE.md` puts out
of scope.

Do not repurpose it. "Who may see this" and "where does this appear for its owner" are
different questions, and merging them means a future sharing feature inherits a column that
already means something else. Add a new one; leave `private` alone.

## The column

Migration: `photos.hidden_from_library BOOLEAN NOT NULL DEFAULT FALSE`. The name is
deliberately long — it must be impossible to confuse with `archived_at`, which is a
different state entirely (on the way out, purged after retention). A hidden photo is a
permanent resident that simply does not appear in the firehose. Say that difference plainly
in the migration comment; the two will otherwise be confused forever.

No new table, so `internal/reset/tables.go` needs no entry — confirm by reading its contract
rather than assuming.

## Where it hides, and where it must not

`internal/photos/store_list.go` already has the pattern. `stackClauses` documents it: a pure
`photos.*` predicate added there "propagates to List, Count, Search, FilterUIDs, YearBuckets
and TimelineBuckets at once". Write `hiddenClauses` as its sibling, plus an `IncludeHidden`
escape hatch on `ListParams`.

**Lift the filter automatically when the listing is scoped to an album or a label** — that
is, when `AlbumUIDs` or `LabelUIDs` is non-empty. That single rule is the feature as asked
for, and it keeps every caller from having to remember a flag.

Hidden:

* the library grid and its counts;
* `YearBuckets` / `TimelineBuckets` — the timeline must agree with the grid it scrolls, or a
  year will claim photos that are not there;
* map and places (`store_location.go`, `store_places.go` — they carry their own
  `archived_at IS NULL`, so they need the predicate adding by hand);
* the slideshow;
* the review game — a document scan is precisely what nobody wants to be asked about;
* search by default, with a `hidden:` filter in the query language as the sibling of
  `archived:` so the photos remain findable. Follow `archivedClauses`' precedent: an explicit
  `hidden:` in the query must win over the default, or `hidden:yes` would match nothing.

Not hidden:

* the photo detail by direct URL (`GetByUID`, unaffected — the linked URL above must keep
  working);
* album and label galleries;
* favourites — favouriting is explicit intent, the same class of act as filing it in an album;
* duplicate detection, maintenance, backfills, backup, import verify. These are about data
  integrity, not browsing, and silently dropping rows from them would be a bug.

## Carry it in the sidecar

`internal/sidecarexport` writes the metadata sidecar so the catalogue survives losing the
database. This flag is curation the user set by hand — it must round-trip, or a restore
un-hides everything. Add it to the format and to `build.go`, and bump/handle the format
version the way that package already does.

## UI

* A toggle on the photo detail, next to archive/favourite, with a clear label — it says
  "hidden from the library", not "private" and not "archived".
* A bulk action through `internal/bulk`, because the real use is fifty scans at once, not one.
  A one-at-a-time-only implementation does not solve the stated problem.
* Some visible way back: `hidden:yes` in search is enough, but make sure it is discoverable
  (mention it wherever the toggle lives). A flag you cannot list is a flag you cannot undo.

Strings via i18n (cs + en), icons only through `Icon`.

## Check the plan does not regress

Every library listing gains a predicate. On 20 889 rows that should be free, but confirm
rather than assume: `EXPLAIN (ANALYZE, BUFFERS)` the main library query and the timeline
bucket query before and after, against a realistic row count, and say in the commit message
what you measured. If the planner stops using the `taken_at` ordering index, the column
belongs in that index — do not leave that discovery to production.

## Verification

Integration tests over the real test DB: a hidden photo is absent from List/Count/Search and
from both bucket queries; present when the listing is scoped to its album or its label;
present in favourites; reachable by uid; excluded from the review queue; found by
`hidden:yes` and by nothing else. Round-trip through the API, and through sidecar export and
re-read. Frontend: Vitest over the detail toggle and the bulk action.

`make check` green. Update `docs/PACKAGES.md`, `docs/API.md`, `docs/FRONTEND.md` and — since
the query language gains a key — whatever documents it.
