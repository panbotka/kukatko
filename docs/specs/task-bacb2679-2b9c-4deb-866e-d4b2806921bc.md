## What is wrong

The library timeline rail renders a year band for **9009**. One photo carries a nonsense
`taken_at` and the rail faithfully turns it into its own band, sitting above 2026 at the top of
the scrubber. A user scrolling the rail meets a year that cannot exist.

Found during the v0.25.0 pre-release walkthrough on box staging (mobile viewport, iPhone 12).
**Pre-existing — not introduced by the v0.24.0..52e5de4 range** (that range touched metrics,
hybrid-search wording and `<html lang>`; nothing date-related). Severity: NIT — cosmetic, no
functional breakage, nothing else misbehaves.

## Evidence (box staging, ~397 photos)

```
ctl photos search "year:9009" --mode fulltext
  -> total 1, uid phvhmhnqh1ikqnacsg1o96fo7t, taken_at "9009-03-10T00:00:00Z"
```

Staging's library is a copy of production's originals, so **production very likely carries the
same photo**. Check before assuming this is staging-only.

3. Observed: the topmost band reads `9009`, above `2026`.

## What to do

**This task is the UI guard only — do not edit the photo's stored date.** Library content
(dates, titles, captions) is settled manually with the user, never by an autonomous task. The
photo's `taken_at` stays exactly as it is; only the rail's presentation changes.

Decide the behaviour rather than jumping to code:

- **Option A — clamp the rail's domain.** Fold years outside a plausible window into one
  end band. Needs a defensible window; derive it from the data (e.g. the earliest plausible
  capture year in the library through the current year) rather than hard-coding a literal.
- **Option B — a separate "unknown date" bucket.** Group implausible years with the photos
  that have no date at all, so the rail's real span stays proportional and the odd photo is
  still reachable. `/system` already counts „Bez data pořízení" (25), so the concept exists.

**Option B is likely the better default** — it keeps the rail honest about the library's real
span without inventing a cutoff, and it matches how the app already talks about undated photos.
Weigh it against A; if A wins, the window must be derived, not invented.

Check while you are there whether anything else presents such a year unguarded: the year
filter/facets, `/stats`, and the `year:` search key (`year:9009` currently returns the photo,
which is arguably correct for an explicit query and should probably stay).

## Done when

- The timeline rail no longer offers an impossible year band.
- Photos with an implausible date are still reachable somehow (not silently dropped from the
  library).
- The photo's stored `taken_at` is unchanged, and no data migration is introduced.
- Tests cover the implausible-year case (the rail's bucketing is a pure function — unit-test it).
- `make check` passes; `docs/FRONTEND.md` updated if the rail's contract changed.
