# Photo Comments — Backend

Per-photo comment threads to make the library social: family members discuss who is on a photo and share memories around it.

## Requirements
- New comment storage: a comment belongs to a photo and an author (user), has a plain-text body (trimmed, 1–2000 chars), created/edited timestamps, and supports soft deletion (deleted rows are kept but never listed).
- Endpoints under the photo API:
  - List a photo's comments (chronological, oldest first) with the author's display name. Every authenticated role, including read-only viewers, can read.
  - Create a comment: **deliberately allowed for ALL authenticated roles, including viewer.** Commenting is social participation, not library curation — document this explicit exception to the read-only rule in docs/API.md.
  - Edit and delete own comments (author only); admins can delete any comment.
- The payload the frontend uses for the photo detail must expose the photo's comment count cheaply (no N+1 queries).
- All writes are audited in the same transaction (actor, photo uid, action). MCP must NOT expose comment writes.
- Apply a modest per-user rate limit on comment creation, reusing the existing rate-limit middleware.
- Purging a photo removes its comments (FK with ON DELETE CASCADE).
- Integration tests: RBAC matrix (viewer can create, author-only edit, admin delete any), body validation, count correctness, soft-delete behavior, cascade on purge.
