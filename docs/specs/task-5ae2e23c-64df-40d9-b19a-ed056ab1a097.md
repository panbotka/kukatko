# Viewer applies a saved rotation twice

Found on the box staging (commit 68e805e) on 2026-09-06 and verified end to end. A photo whose saved edit contains a 90° rotation is shown **lying on its side** on every fresh load of the viewer, because the rotation is applied twice: once by the server, which bakes the saved edit into the renditions, and once more by the viewer as a CSS transform. Immediately after saving, in the same tab, it looks upright only because the browser still holds the *old* landscape rendition in cache — and then the quarter-turned image is not refitted to the stage and overflows the viewport.

## Root cause (verified, do not re-derive)

- The thumbnailer renders the **saved edit into the rendition**: `internal/thumb` is wired `WithEdits(EditResolver)` (see `docs/PACKAGES.md`, "the photo's saved edit is rendered in"), and a changed edit forces a rebuild through the `thumbnail` job. Measured on staging photo `DSC_0487.JPG` (`phuo4jd4ud6du03a2pegp1t5ir`): after `kukatko ctl edits set <uid> --rotate 90` and the thumbnail job, `GET /api/v1/photos/{uid}/thumb/fit_1920` returns **1279×1920** (before: 1920×1279) and `fit_1280` returns 853×1280.
- The viewer applies the rotation **again**: `web/src/pages/PhotoDetailPage.tsx` computes `previewEdit = editDraft ?? state.edit` (≈ line 390, i.e. the *saved* edit when there is no draft) and puts `editTransform(previewEdit)` from `web/src/lib/photoEdit.ts` into the still image's `transform` (≈ line 1043), and hands `previewEdit.rotation` to `FaceOverlay` (≈ line 1162).
- Fresh browser, saved rotation 90: the `kk-viewer__image` has `naturalWidth 1279 / naturalHeight 1920` **and** computed `transform: matrix(0, 1, -1, 0, 0, 0)` — rendered 788×525, sideways. Screenshot: `/mnt/nas-botka/kukatko-stage-test/77-rotation-fresh-load.png`.
- Same tab right after saving (cached landscape rendition): natural 1920×1279 + the transform → upright but 671×1008 px on a 900 px viewport, rect top −54 / bottom 954, head and feet cut off. Screenshots `13-rotated.png`, `15-rotated-after-reload.png` in the same folder.

## Requirements

- The viewer must never apply the **saved** edit as a CSS transform: the rendition already carries it. CSS may carry only the **unsaved delta** — what the draft in the Úpravy panel changes relative to the saved edit — so the preview still works while editing.
- When a draft preview rotates the picture by a quarter turn, the fit must treat the rotated box as the thing to fit (swap width/height in the fit computation) so the preview never overflows the stage on any viewport. Cover phone portrait too.
- After the user saves an edit, the viewer must show the rebuilt rendition: decide how it learns the thumbnail job has finished (the per-photo processing state in `GET /photos/{uid}` is one source, a cache-busting query on the rendition URL another) and until then show something honest — the old rendition with the delta preview correctly fitted, or a short "rendering" state. A stale, wrongly rotated picture is not acceptable in any window.
- `FaceOverlay` boxes must align with whatever frame is displayed, in both states (saved edit only; saved edit plus draft). Read `web/src/lib/faceGeometry.ts` (`rotateBbox`, the documented invariant that boxes are stored against the upright original) and decide where the saved rotation is applied to boxes now that the rendition is pre-rotated; do not leave boxes drifting on rotated photos.
- Keep crop and brightness/contrast consistent with the same principle: saved → rendition, draft → CSS delta. Check `editPreviewStyle` for the same double application.
- Tests (Vitest, `PhotoDetailPage` and `photoEdit`): a saved rotation renders **no** transform; a draft rotation on top of a saved one renders only the delta; after a successful save the image source is refreshed / the transform is dropped once the rebuilt rendition is in; a draft quarter-turn fits inside the stage. Note that jsdom gives images no natural size — mock what the fit reads.
- Docs: `docs/FRONTEND.md` for the viewer's edit-preview contract (saved vs draft), and a sentence in `docs/PACKAGES.md` next to the `WithEdits` paragraph pointing out that the client must not re-apply the saved edit.

## Out of scope

- Do not change server-side rendering or the thumbnail job; the rendition being pre-rotated is the intended design.
- Do not run anything against production. Production is live (kukatko.kotrzina.cz) and any photo edited there with a rotation currently displays sideways after its renditions rebuild, which is why this is the top priority — the fix ships through a release, not through a data change.
