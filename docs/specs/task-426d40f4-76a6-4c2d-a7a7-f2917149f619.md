# Unknown date: a cleared date is preserved, and undated photos are searchable

Many photos in the library carry a date that is simply wrong — a scan stamped with the day it
was scanned, an import that fell back to the file's mtime. The owner often does not know the
real date and wants to say exactly that: the date is unknown. Today that is only half
possible. `PATCH /api/v1/photos/{uid}` with an explicit `taken_at: null` clears the date and
stamps `taken_at_source = "unknown"`, but the wrong date is then gone for good; the bulk API
cannot clear a date at all; and nothing in the search language matches a photo without a date.

This task is the backend half plus the search key. The grid/bulk UI and the detail affordances
are a separate follow-up task — **do not build them here**.

## What already exists (read before changing anything)

- `photos.taken_at` is nullable (`0003_photos.sql`) and sorted `NULLS LAST` by
  `idx_photos_live_taken_at` (`0015`), so an undated photo already falls to the end of every
  date-ordered listing. Reuse that. Do **not** invent a parallel "unknown" boolean that every
  query would then have to special-case.
- The date already carries provenance: `taken_at_source` (`exif`/`filename`/`manual`/`unknown`),
  `taken_at_estimated`, `taken_at_note`, `taken_at_precision` (`day`/`month`/`year`/`decade`).
  Model in `internal/photos/models.go`.
- `internal/photoapi/update.go` — `applyTakenAt` stamps `manual` when a date is set, `unknown`
  when it is cleared, and resets precision to `day`.
- `internal/bulkapi/request.go` accepts `set_taken_at {precision, value}` and `clear_location`,
  but has no `clear_taken_at`.
- `internal/query/query.go` is the filter registry; `internal/photos/store_query.go` holds the
  condition builders. `geoCond` and `hiddenCond` are the two closest models to copy.

## Requirements

- **Migration `0066`** adds a column to `photos` preserving the date a photo held at the moment
  it was declared unknown. Nullable, no default, no index — no listing filters on it. Write the
  decision into the migration header the way `0029` and `0049` do: this column is provenance,
  never a sort or filter anchor, and it exists so that declaring a date unknown is reversible.
- **Clearing a date preserves it.** Whenever `taken_at` goes from a value to `NULL` through an
  explicit clear, the outgoing value moves into the new column first. This must hold on **both**
  write paths — the single-photo `PATCH` and the new bulk operation — so the rule belongs in the
  photos store, not in one of the two callers.
- **Setting a date discards the preserved one.** Once the owner states a real date, the
  previously set-aside value is no longer "the date we put away" and the column is cleared in the
  same statement.
- **A clear that follows a clear must not overwrite** an already-preserved value with `NULL`, and
  clearing an already-`NULL` date is a no-op rather than a write.
- **New bulk operation `clear_taken_at`** (boolean, mirroring `clear_location`) in
  `internal/bulkapi/request.go` and `internal/bulk`. It behaves exactly like the `PATCH` clear:
  preserves the outgoing date, stamps `taken_at_source = "unknown"`, resets `taken_at_precision`
  to `day`, runs inside the batch's single transaction and produces the same audit entry shape as
  the other bulk operations. Sending it together with `set_taken_at` in one request is a `400` —
  the two contradict each other.
- **New query key `dated:`** (`KindBool`, `yes`/`no`) in `internal/query/query.go` plus its
  condition builder in `internal/photos/store_query.go`. `dated:no` matches every photo with no
  `taken_at`, deliberately including photos that never had one — that is the useful worklist.
  `dated:yes` is its complement. Follow the note in `query.go` verbatim: a row in `specs`, a
  builder in the store, and a line in the `docs/API.md` grammar.
- **Mirror the key in the frontend registry only** — `FILTER_KEYS` in
  `web/src/lib/queryLanguage.ts`, an id in the `QueryHelpRowId` union, a row in
  `QUERY_HELP_ROWS`, and the `search.help.desc.*` string in both locales, so `dated:no` is
  typeable and documented in the `?` reference. **No filter-bar control and no bulk-modal option**
  — those belong to the follow-up task.
- **The metadata sidecar carries the preserved date.** `internal/sidecarexport` must write it, so
  "this date was set aside as unknown" survives losing the database. Bump the sidecar format the
  way the package already does, and note in the commit body that this implies a library-wide
  sidecar rewrite.
- **Tests.** Store-level tests for all four transitions (value → cleared, cleared → cleared,
  cleared → new value, never-dated → cleared); an HTTP integration test for the `PATCH` clear and
  for `clear_taken_at`, including the `400` on the contradictory combination; a parser test for
  `dated:`; and an integration test proving `dated:no` finds both a photo whose date was cleared
  and a photo that never had one, and finds neither once a date is set.

## Implementation notes

- Do not touch how undated photos sort or group in listings. `NULLS LAST` is already correct, and
  the visible "unknown date" grouping is the follow-up task's job.
- `taken_at_estimated` and `taken_at_note` are orthogonal and must survive a clear untouched —
  "date unknown, but grandma says it was a wedding" is a legitimate state.
- Definition of Done per `CLAUDE.md`: docs first (`docs/API.md` for the request bodies and the
  search grammar, `docs/PACKAGES.md` for the changed packages, `README.md` if you judge `dated:`
  user-visible), then `make check`, then commit and push.
