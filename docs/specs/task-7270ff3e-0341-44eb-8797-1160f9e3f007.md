# Ask for notification permission after the first sign-in

Nobody finds a notification setting buried in a settings page, so Kukátko should ask once — after the first successful sign-in — whether the person wants notifications. It has to ask **politely and exactly once**: a refusal is remembered and never raised again, and turning it on later is possible from the settings page.

## Context that already exists

`web/src/pwa/push.ts` covers permission state, support detection, requesting permission, subscribing with the server's VAPID public key, registering the subscription with the server, and unsubscribing. It never throws — an unsupported browser, a denied permission and a failing request all resolve to a reported state. A backend endpoint says whether push is enabled instance-wide.

Browsers only allow `requestPermission()` **from a user gesture**, so nothing may request permission on mount. A button has to do it.

## Requirements

- A modal shown after the first successful sign-in. One or two sentences on what the notifications are for — that Kukátko will tell them when somebody tags them in a photo — and two choices: not now, and turn on. Only the "turn on" button reaches the permission request.
- **Ask at most once.** A dismissal, a refusal and a browser-level denial are all remembered per account and per browser, and none of them is ever asked again. The settings page is the only way back.
- Do not show the modal at all when: push is disabled instance-wide; the browser does not support push; permission is already granted and a subscription exists; permission was already denied at the browser level; or this account has already answered in this browser.
- **iOS in a browser tab cannot receive push at all** — only an installed PWA can (Safari 16.4 and up, added to the home screen). There, either do not show the modal, or show one that says adding Kukátko to the home screen is what enables notifications. Pick one and make it honest. Do **not** show a button that silently fails.
- On success, confirm briefly through the existing toast mechanism. On a browser-level denial, say plainly that the browser blocked it and that it has to be re-allowed in the browser's own site settings — once denied, the page cannot ask again, and pretending otherwise wastes the person's time.
- Mount it where it actually reaches a freshly signed-in person. Be careful with layering: in this project the review game and the photo viewer both sit at a higher z-index than Bootstrap's dialogs, which has already made one modal unreachable. **Verify this one is reachable** rather than assuming it is.
- Czech and English through i18next, Czech default.

## Verification

Component tests: shown after a first sign-in; not shown when the account already answered; not shown when push is off instance-wide; not shown when the browser is unsupported; "not now" records the answer and closes; "turn on" requests permission and subscribes; a denial shows the blocked message and records the answer. Where the component depends on a real gesture, drive it with a real user event rather than a synthetic click.
