# The album index is effectively unusable on the real library

`GET /api/v1/albums` on production (https://kukatko.kotrzina.cz, 437 albums,
20 197 visible photos, 40 459 album memberships) takes **32.8 seconds** to return
151 kB, and requests that do not finish in time fail outright. Four `status:500`
lines are in the production log from 2026-08-02 11:27, with durations of 1.9 s,
20.6 s, 1.3 s and 3.4 s — a real user clicking "Alba".

## Root cause, measured

`EXPLAIN (ANALYZE, BUFFERS)` of `listAlbumsSQL` (`internal/organize/albums.go:207`)
on the production database:

```
Sort                                        actual time=34323 ms  rows=437
  Buffers: shared hit=16265977
  -> Nested Loop Left Join                  actual time=186..34297
       -> Hash Left Join (albums+members+photos)   actual time=77..141   Buffers: 2531
       -> Memoize                           loops=40471  Hits: 40034  Misses: 437
            Buffers: shared hit=16263687
            -> Limit                        actual time=79.697  loops=437
                 -> Incremental Sort        Presorted Key: p2.taken_at
                      -> Nested Loop        rows=3  loops=437
```

**16 265 977 buffer hits to produce 437 rows, and 16 263 687 of them — 99.99 % —
are the LATERAL cover subquery.** Everything else in the statement costs 2 531
buffers and 141 ms; the join, the counts and the MIN/MAX are not the problem.

The subquery is:

```sql
SELECT ap2.photo_uid FROM album_photos ap2
JOIN photos p2 ON p2.uid = ap2.photo_uid
WHERE ap2.album_uid = a.uid AND p2.archived_at IS NULL
  AND (p2.stack_uid IS NULL OR p2.stack_primary)
ORDER BY p2.taken_at DESC NULLS LAST, ap2.photo_uid
LIMIT 1
```

The planner satisfies the `ORDER BY … LIMIT 1` by walking the **global**
`photos.taken_at` order (note `Incremental Sort`, `Presorted Key: p2.taken_at`) and
probing each row for membership of this one album. For an album whose newest photo
is old, that walks most of the library before it finds its first hit — 437 times
over. Memoize caches per `a.uid`, so it runs 437 times rather than 40 471, but each
run averages **79.7 ms**.

The albums average ~93 photos each (40 459 memberships / 437). Sorting 93 rows per
album is trivial work; the plan does something else entirely.

This could not show in development: with a few hundred photos the global walk is
cheap, which is exactly why it shipped.

## What to build

1. **Make the cover lookup proportional to the album, not to the library.** The
   obvious shape is a single pass — e.g. `DISTINCT ON (album_uid)` over
   `album_photos` joined to `photos`, ordered by `album_uid, taken_at DESC NULLS
   LAST, photo_uid` — computing every album's fallback cover in one scan instead of
   437 ordered probes. An index that makes the per-album sort attractive is another
   route. Choose by measurement, not by preference, and put the resulting plan in the
   commit message.

   Whatever shape you pick, the current contract must survive exactly:
   - the fallback cover is the album's **newest visible** photo, unknown capture time
     sorted last, `photo_uid` breaking ties, so the same album returns the same cover
     on every request;
   - a hand-picked `a.cover_photo_uid` still wins (`COALESCE`);
   - "visible" means `archived_at IS NULL AND (stack_uid IS NULL OR stack_primary)`,
     the same predicate the album grid uses, so the badge count and the cover agree
     with what the album actually shows.

2. **Check the sibling listings for the same antipattern** before you call this done
   — `internal/organize/labels.go` builds a comparable summary (`labels.go:139`), and
   anything else that picks a cover or a newest-member per group is suspect. Report
   what you checked, including the ones that turned out fine.

3. **Log the cause of a 500.** The production log carries `status:500` and nothing
   else — the handler discards the error, so an operator learns only that it broke.
   Whatever the handler does with the error, the reason has to reach the log.

## Verification — a small dataset proves nothing here

- Seed a realistic fixture: on the order of 400 albums, 20 000 photos and 40 000
  memberships, with the same skew (albums whose newest photo is old are the slow
  case — an album full of 2011 photos is what makes the global walk long).
- Assert the improvement as a **plan property, not a wall-clock number**: buffer hits
  (or rows read) must scale with the album's own membership count, not with the size
  of the library. A timing assertion will be flaky on shared CI.
- Report the same three figures as above for the new query: total time, total buffer
  hits, and the share attributable to the cover lookup.
- `make check` **and** `make test-integration` must pass.

## Production constraints

Kukátko is live and this endpoint is user-facing and currently broken.

- **Migrations run automatically at startup, each inside its own transaction.**
  `CREATE INDEX CONCURRENTLY` cannot run inside a transaction, so it is not available
  to you. A plain `CREATE INDEX` on `album_photos` (40 k rows) is fast and acceptable;
  anything that would hold a long lock on `photos` (20 k rows and growing) is not.
- **Never write a migration that drops or rewrites originals or R2 objects.**
- **Do not touch the production instance, its database or its bucket.** Do not run
  `EXPLAIN` against production; the numbers above are already gathered for you.
- **Do not run `make dev`** — it binds the port of the developer's own instance.
- The deployed image is pinned (`ghcr.io/panbotka/kukatko:0.1.1`) and there is no
  auto-updater, so merging does not deploy. The operator ships this with the next
  release.
