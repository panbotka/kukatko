# Imported photos get no pHash, and a cold cache makes the backfill re-upload everything

**Kukátko now runs in production** at https://kukatko.kotrzina.cz against the real
library. Read "Production constraints" at the bottom before you design anything —
it changes what an acceptable fix looks like.

## The two defects

### 1. `ppimport` never produces a pHash

Measured on production on 2026-08-02, mid-import: `photo_phashes` held **0 rows for
10 479 photos**. The job queue holds only `image_embed` and `face_detect` — no
`thumbnail` job is ever enqueued for an imported photo.

The reason is that `ppimport` thumbnails inline (that is where the
`ppimport: thumbnails failed` warnings come from), while the perceptual hash is
computed by the *thumbnail job* alongside the thumbnail. No job, no pHash.

Consequences:

- `internal/duplicates` is dead for the whole imported library — banded-LSH over
  pHash has nothing to band.
- `internal/thumbjob`'s narrow backfill predicate is "has no pHash"
  (`ListPhotosMissingPhash`, documented at `thumbjob.go:84-87`). Every one of the
  ~20 670 imported photos matches it, so the "narrow" backfill is a full-library run.

### 2. `Generate` decides "already done" from the local disk alone

`internal/thumb`'s contract is that a size already present in the local cache is
never re-encoded (package doc, `thumb.go:15-16`), and `publishSize`
(`thumb.go:377-399`) uploads each freshly encoded size to R2 under the same
relative path — deleting the local file when the upload fails, so the invariant
"every cached file is also in the bucket" holds.

What is missing is the other direction: nothing asks whether the object **already
exists in the bucket**. So a cold local cache means a full re-encode *and* a full
re-upload of objects that are already there.

This is not hypothetical. The production import runs with a pruner that deletes
cache files older than ten minutes, because eight sizes cost ~2.76 MB per photo —
57 GB for the library against 20 GB of free disk. Without pruning the import dies
around photo 7 200. So on production the cache is cold by construction, and the
pHash backfill from defect 1 would re-encode and re-upload all ~20 670 photos:
roughly a second twenty-hour pass and ~57 GB of pointless R2 writes.

## What to build

Both defects have to go together — fixing only the pHash gap schedules the
expensive run; fixing only the cache check leaves duplicates broken.

1. **Give imported photos a pHash.** Either compute it on the inline path
   `ppimport` already takes, or have `ppimport` enqueue a `thumbnail` job per photo.
   Prefer whichever keeps a single code path for "a photo entered the catalogue";
   two paths that must both remember to hash is how this bug happened. State which
   you chose and why in the commit message.

2. **Let `Generate` treat a published object as done.** A size whose object is
   already in the bucket must not be re-encoded or re-uploaded. Mind the cost of
   the check itself: a HEAD per size per photo is 8 round-trips per photo and could
   easily be slower than the encode it saves — prefer one listing per photo's shard
   prefix, or a cheaper signal, and measure before you commit to a shape.
   Keep the existing invariant intact: a failed upload must still leave the size
   counting as ungenerated.

3. **Make the backfill's cost legible.** `BackfillThumbnails` should be able to say
   how many photos it would schedule before it schedules them, so the next operator
   does not discover a twenty-hour run by starting it.

## Verification

- Unit tests for the "object already in the bucket" path, including the failed-upload
  case that must still un-cache the size.
- An integration test against the real test DB proving an imported photo ends up with
  a row in `photo_phashes`.
- `make check` **and** `make test-integration` must both pass. The gate alone is not
  enough — `make check` does not run the integration suite, and that gap has already
  shipped a hang to CI once.

## Production constraints — read before designing

Kukátko is live and holds the real library. Development is no longer free:

- **Migrations run automatically at startup** and against a populated database. A
  migration must be safe on ~20 000 photos and must not lock the catalogue for long.
  No destructive DDL on a populated table.
- **Never write a migration or a maintenance path that drops or rewrites originals
  or R2 objects.** The bucket is the library.
- **A restart is a real outage.** Do not add work that must run at startup.
- **Do not run `make dev`** — the dev server binds the same port as the developer's
  own instance and would kill it. Verify against a throwaway instance on the test DB.
- **Do not touch the production instance, its database or its bucket.** This task is
  code only; the operator deploys it with the next release.
- Assume a background import may be running while your change is reviewed: anything
  you add must be correct when the catalogue is being written to concurrently.
