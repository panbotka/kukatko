# `make test-integration` takes ~30 minutes, and almost all of it is password hashing

Measured on the Pi on 2026-08-02, `CGO_ENABLED=1 go test -race -p 1 -timeout 30m
-tags=integration ./...`, first 41 packages:

```
internal/auth            640.7 s   <- more than half of everything
internal/announcementapi  77.8 s
internal/ingest           70.1 s
internal/bulkapi          68.4 s
internal/facematch        68.2 s
internal/jobsapi          59.1 s
internal/clusterapi       49.3 s
internal/duplicatesapi    49.2 s
internal/auditapi         49.2 s
internal/dirimport        35.5 s
                        ————————
                        1213 s across 41 packages
```

The other ~30 packages finish in 1–2 s each. A package like `internal/auditapi`,
whose integration test is a handful of assertions about a read-only listing, takes
49 seconds.

## Why

`internal/auth/password.go:13`:

```go
// bcryptCost is the bcrypt work factor used for all password hashes. Cost 12 is
// a deliberate security choice (slow enough to resist offline brute force on
// modern hardware) and is fixed so every stored hash is consistent.
const bcryptCost = 12
```

Every `*api` integration test seeds accounts through the real auth path to exercise
RBAC, so each seeded user costs a cost-12 hash, and `-race` multiplies it. The work
is not incidental to those tests — it is nearly all of their runtime. `internal/auth`
itself seeds enough accounts to spend ten minutes.

## The insight that makes this safe

**A bcrypt hash records its own cost.** The cost is encoded in the hash string, and
`CompareHashAndPassword` reads it from there — so hashes made at different costs
verify correctly side by side. The existing comment's "fixed so every stored hash is
consistent" is a statement about what *production* mints, not a correctness
requirement of verification.

That is what makes a test-only cost sound. It is also the thing to get wrong, so:

**Production must keep cost 12, and a test must prove it.** Whatever knob you add
has to be impossible to trip from a running server — not merely "we do not call it".
A package-level `var` that any importer can assign is weaker than a hook only the
test build can reach; weigh it and say which you chose and why.

## What to build

1. **Make the work factor tunable for tests only**, defaulting to 12 everywhere else.
2. **Use it in the seeding helpers** the integration tests share, not one test at a
   time — the cost is spread across ~15 packages.
3. **Assert the default.** A test that fails if the production path stops using
   cost 12 is the point of the exercise; without it this change quietly becomes a
   security regression the next time someone touches it.

Optional, only if the numbers justify it after step 1: the suite also runs with
`-p 1` because every package shares one test database (`Makefile:67-70`). Giving each
package its own schema would let packages run in parallel. That is a bigger, riskier
change — measure first and do not attempt it in the same commit.

## Verification

- Report the suite's total wall-clock time before and after, on the same machine,
  with the same command. Include the per-package table for the ten slowest so the
  improvement is attributable, not just smaller.
- `make check` and `make test-integration` must both pass — and the second is now
  the thing you are changing, so run it to completion, twice if the first run is the
  one that populates caches.
- The cost-12 assertion must fail if someone changes the default. Prove it by
  changing the default locally, watching it fail, and changing it back.

## Constraints

Kukátko is live at https://kukatko.kotrzina.cz.

- **This must not weaken production password hashing.** That is the whole risk of
  this task; everything else is convenience.
- Do not touch the production instance, its database or its bucket.
- **Do not run `make dev`** — it binds the port of the developer's own instance.
- The Pi has 16 GB of RAM shared with everything else; do not solve this by making
  the suite more parallel until the cost is fixed.
