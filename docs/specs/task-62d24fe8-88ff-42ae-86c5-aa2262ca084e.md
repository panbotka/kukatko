# The query language barely knows videos exist

The search language can select a media type and a codec, and that is the whole video vocabulary.
Meanwhile the catalogue already stores a video's duration, frame rate and whether it has sound,
and whether it has been encoded for streaming is knowable too. None of it is reachable from the
search bar, so questions a person actually has — "the long clips", "the ones with no sound", "what
still has not been prepared for playback" — have no answer short of a database query.

## Requirements

Add these filters to the query language, following the shape and the parsing conventions the
existing filters already use:

- **duration** — how long the clip runs, as a range as well as a single value, so both "longer
  than a minute" and "about ten seconds" are expressible. Accept the units a person would type
  rather than raw milliseconds: seconds and minutes at least.
- **sound** — whether the clip has an audio track, as a yes/no filter.
- **frame rate** — a numeric filter and range, for finding slow-motion and high-frame-rate footage.
- **streaming** — whether the clip has been encoded for smooth playback, as a yes/no filter. This
  is the one that turns "which videos are still waiting" into something a person can type, and it
  should read naturally in both directions.

Beyond that:

- Each filter applies only to items where it means something. A still has no duration and no sound
  track; asking for them must exclude stills rather than matching them as zero.
- An unparseable value degrades the way the language already degrades unknown tokens, rather than
  erroring — that behaviour is deliberate and must not change.
- The filters are usable together and alongside the existing ones, and they compile into the same
  single query, with no extra round trip.
- The search-language help screen gains each new filter with an example, in Czech and English, in
  the same voice as the entries already there.

## Also

The orientation filters — portrait, landscape, square, panorama — read the catalogue's stored
dimensions, which for videos are recorded without any rotation handling. Do not try to fix that
here; it is a separate question about how video dimensions are read. Just do not make the new
filters depend on it.

## Documentation

The query language reference in the API documentation gains every new filter, with the accepted
value forms and what each one does to a still.

## Tests

Parser tests for each filter, including ranges, units and rubbish input; store tests asserting the
compiled SQL and the rows returned against the test database, with a still, a silent video, a
video with sound, an encoded video and an unencoded one.
