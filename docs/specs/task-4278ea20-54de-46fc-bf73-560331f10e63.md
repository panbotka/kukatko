# The map on a phone spends 45 percent of the screen before the map begins

`/map` still wears the layout the library page was cured of: its controls eat nearly half the viewport, leaving the map itself a minority of the screen.

## Evidence (observed on production, 2026-08-12, 390x853)

Above the map, in order: three style tabs, two date pickers, an archive select, and a two-line coverage sentence — **382 px, 44.8 % of the viewport**. The map gets roughly 417 px before the tab bar starts.

This is the same disease that finding N19 in `docs/UX_RESEARCH.md` diagnosed for the library, and that commit `4794d8a` cured **for the library only**: controls folded into a Filters drawer, first photo row at 150 px. The map page never received it.

## Requirements

- On a phone, the map is the majority of the screen on arrival.
- The controls (style, date range, archive) remain reachable — folded into a drawer or equivalent, following the pattern the library already uses rather than inventing a second one.
- The coverage sentence ("Na mape je X z Y fotek...") survives in some form; it is genuinely useful and is the one thing on this page that tells the reader the map is partial.
- Desktop layout is unchanged.
- The existing scroll-gesture handling in `web/src/lib/mapGestures.ts` (one finger scrolls the page, two fingers pan the map) is correct and must keep working — do not regress it.

## Constraints

- **No mutable operations against production data.** Read-only browsing of production is allowed for verification; writes of any kind are not.
- The map proxies tiles through the backend and the mapy.com key stays server-side — do not move any part of that to the client while reworking the page.
- `make check` must pass. `make check-box` runs the same gate on the build box and is much faster.
