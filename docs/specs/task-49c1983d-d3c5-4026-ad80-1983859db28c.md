The task queue works in both directions: an agent (account `panbotka`, via `kukatko ctl`) asks a human, and a human hands work to the agent or to another user. The second direction is clumsy today:

- The web create dialog (`components/tasks/NewTaskModal.tsx`) has neither a "who" field nor a state; every task opens as `question`, which by convention means "a human is on turn". A human handing work to the agent wants `working`, and wants the agent on the task from the start. Assigning is a second step on the task page (`TaskParticipants`), and the ctl needs `tasks create` followed by `tasks assign`.
- A task must have at least one photo (`photo_uids is required`). Agenda that is about the library but not about particular photos ("rename the wf: labels", "which albums should the recruits go to?") does not fit, so it ends up in chat or in a markdown file and gets lost. The frozen photo group stays the normal case; an empty group is the exception this task allows.

## API and store

- `POST /tasks` accepts `participants` (array of user uids; each is added as **asked** by the creator, i.e. `added_by = creator`, in the same transaction, audited as the existing assign action). Unknown user → 404 as elsewhere.
- `POST /tasks` accepts an empty `photo_uids` (absent or `[]`). `cover_photo_uid` is then null, `photo_count` 0. `MaxPhotos` (1000) unchanged; photos can be added later.
- Nothing else changes in the state machine.

## ctl

- `kukatko ctl tasks create --assign <user-uid>` (repeatable) alongside the existing `--state`.
- `tasks create` with no photo arguments: if stdin is not a terminal it reads uids from stdin as today and an empty input means no photos; if stdin is a terminal, no photos. Print "no photos" in the result so an accidental empty pipe is visible.
