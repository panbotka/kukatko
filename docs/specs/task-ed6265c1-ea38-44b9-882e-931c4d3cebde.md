# Tenancy guard: project_id must appear in a predicate

The guard accepts any statement over a root table that mentions `project_id` anywhere, so a SELECT that merely returns the column passes. The gate therefore gives false assurance.

## Context (verify with rg before starting)
- `internal/tenancyguard/scan.go` (~line 236) decides "scoped" with `strings.Contains(stmt, RootTables[table])`-style matching on the column name.
- `internal/tenancyguard/allow.txt` lists reasoned exceptions; `make check` runs the guard.
- Known unscoped statements without an allow-list entry today: `internal/vectors/store.go` (`getEmbeddingSQL`) and `internal/vectors/faces.go` (three statements). Another task scopes them; if that has not landed, allow-list them with a reason here.

## Requirements
- A root-table statement counts as scoped only when `project_id` appears after `WHERE`, in a `JOIN … ON` condition, in an `INSERT` column list, in an `UPDATE … SET` list, or in an `ON CONFLICT` target — i.e. in a position that constrains or writes the row — not in a bare select list. Unit tests cover each accepted position and the rejected select-list-only case, plus a CTE and a subquery where the predicate sits inside the inner query.
- Running the strengthened guard over `main` is green: every newly flagged statement is either fixed (scoped) or allow-listed with a reason; stale allow-list entries fail as before.
- `docs/PACKAGES.md` (tenancyguard) describes the predicate rule; `CLAUDE.md` is touched only if the rule's wording there changes.

## Out of scope
- Full SQL parsing; a token-position heuristic is enough as long as the tests above pass and the false-negative class (select-list only) is closed.
