## Do not confuse this with the third photo

`pteek3u9kw8oxi7y` ("Vyznačení míst po zrušených domech") also failed to map, and is **not**
a bug: PhotoPrism held two entries for that picture, this one was deleted on 2026-05-02, and
Kukátko has the survivor `pteeyll4s1lu324o` as `ph85tlr6gp0clvdsk9jqgjrqm7`. The photo book
simply points at the dead uid. Use it as the control case — whatever you change must keep
treating that one as correctly skipped.

## What to find out

Start from the two uids and answer, with evidence, **why the importer never wrote them**. The
candidate explanations are not equally likely and should be told apart rather than guessed:

* they were never returned by the source listing — check what
  `photoprism.ListPhotos` actually yields for them (paging, `merged=true`, any filter);
* they were returned and skipped — `internal/ppimport` swallows some outcomes. The known
  precedent is `ErrFileHashTaken` folded into `(false, nil)` with no log and no
  `import_failures` row (task `e67607af`, already fixed — confirm whether that fix covers this
  or whether a second path does the same);
* they were written and later removed — check `import_failures` and the audit log before
  concluding.

Reproduce against the test DB with a fixture in the same shape before changing anything. A
fix whose only evidence is "the two photos now appear in production" is not verified.

## The second, larger half: verify must be able to see this

A reconciler that reports COMPLETE while two source photos have no catalogue row is not doing
its job. This is the third blind spot found in that command in two days — the others were
album types it skipped and marker identities it never counted.

`sourceCoverage` (`internal/importverify/importverify.go`) clamps to 1 whenever
`catalog >= source`, so `coverage=100.0%` compares **totals, not sets**. Totals can match while
the sets differ. Make the photo reconciliation set-based: name the source ids that have no
catalogue row and no alias, and fail `complete` on them.

While you are there: the `ListPhotos` doc comment at `importverify.go:38` claims the listing
pages "until a short page". The loop actually breaks on an empty page, which is correct — but
the comment describes precisely the bug that once made an import catalogue ~900 photos and call
itself complete. Fix the comment.

## Verification

report it by uid and refuse `complete`; a source photo present only via `photoprism_aliases`
still counts as present (the dedup case, 13 of them in production); a source photo deleted in
PhotoPrism is not reported as missing. Plus whatever regression test the importer defect
itself needs.
