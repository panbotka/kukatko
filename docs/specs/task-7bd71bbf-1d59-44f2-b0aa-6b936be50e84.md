# Durable push delivery: internal/pushjob

Kukátko never sends e-mail inline — it goes through the persistent job queue. `internal/mailjob` owns a `mail_send` job whose payload is a template plus data plus a recipient, rendered when it is sent, and an `Enqueue` helper that refuses to queue anything while mail is off. This task is that same thing for Web Push. Read `internal/mailjob` before starting; this package should look like its sibling.

## Context that already exists

`internal/push` is the only way to send a Web Push message. It exposes a `Sender`, a typed notification payload (title, body, deeplink path, kind, collapse tag), configuration under `push.*` including `push.enabled`, and a store over a `push_subscriptions` table holding one row per browser: the account, the endpoint URL (unique), the `p256dh` and `auth` client keys, a user-agent and failure bookkeeping. Its sender reports a gone-forever endpoint (HTTP 404/410) distinctly from a transient failure (429, 5xx, network) and refuses an oversized payload with a typed error.

## Requirements

- New package `internal/pushjob` with a `push_send` job type and its worker handler, registered in the worker runtime's per-job-type pools and wired in `cmd/kukatko`.
- **One job per device, not per account.** The job's payload names a single subscription plus the notification to deliver. The `Enqueue` helper does the fan-out at enqueue time: it reads the account's subscriptions and queues one job each. This is what makes a retry safe — a queue retry re-sends only to the device that actually failed, and a person with a phone and a laptop never gets the notification twice on the phone because the laptop's endpoint was briefly unreachable.
- `Enqueue` must run **inside the caller's transaction** — the queue supports this, see how `internal/mailjob` does it — so a notification is scheduled if and only if the mutation that caused it commits.
- `Enqueue` refuses, **without returning an error**, when push is disabled instance-wide or when the account has no subscriptions at all. Nothing queued is the correct outcome in both cases; a queued job that can never deliver is not.
- A subscription the push service reports as gone (404/410) is **deleted** by the handler, and the job completes successfully — there was nothing wrong with the notification, only with the device. This handler is the only place dead subscriptions are pruned.
- A transient failure is recorded on the subscription (failure count and timestamp) and makes the job fail, so the queue retries it with its normal backoff.
- A subscription whose failure count passes a threshold is deleted as hopeless, so a permanently broken endpoint does not keep a job retrying until the queue gives up on it over and over.
- An oversized payload is a **terminal** failure, not a retry — the queue supports terminal failure and a payload that is too big will be too big forever.

## Edge cases

- The subscription is gone at claim time (the person unsubscribed between enqueue and run): complete the job successfully, there is nothing to do and nothing is wrong.
- The account was deleted: the foreign key cascade already removed its subscriptions, so this reduces to the case above.
- Push was disabled instance-wide after the job was queued: complete without sending rather than failing. An operator turning push off should not fill the queue with failures.

## Verification

Integration tests against the real test database with a fake sender: a successful delivery records the send; a 410 deletes the subscription and completes; a 500 records a failure and fails the job for retry; repeated failures past the threshold delete the subscription; an oversized payload fails terminally; `Enqueue` with push off or with no subscriptions queues nothing and returns no error; `Enqueue` inside a transaction that rolls back queues nothing.
