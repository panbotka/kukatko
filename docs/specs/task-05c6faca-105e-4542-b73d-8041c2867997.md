## Migration 0073_subject_families.sql

Exactly the DDL in section 3.2. It was executed against the test database in a rolled-back
transaction and is known to be accepted as written (see section 3.5, Evidence). Match the
house style of 0067_passkey_credentials.sql: a long `--` prose header arguing why the table
exists, why each constraint is there and what it prevents, then aligned DDL.

Load-bearing, verified, none of it optional:
- `COLLATE "C"` in the ordered-pair CHECK. The Go side normalises pairs by byte order; the
  database default collation is locale- and version-dependent and is not byte order.
- `NULLS NOT DISTINCT` on the unique pair index — one couple is exactly one family, one lone
  parent exactly one family.
- The unique index on `subject_family_children (child_uid)` — a person is a child in at most
  one family. This is what keeps the descendant walk a tree rather than a general graph.

Add BOTH tables to `catalogueTables` in internal/reset/tables.go, kept alphabetical near
`subjects`. Omitting them makes internal/reset's integration test fail late — do it in the
same commit as the migration.

## Package internal/family

A new package, not more files in internal/people (which already has fifteen and owns the
faces name cache). Follow people's conventions: package-level `const ...SQL` strings, a
`scanX(pgx.Row)` helper, sentinel errors, every wrapped error prefixed "family: ".

Types and Store methods exactly as listed in section 5. Writes go through the existing
generic `mutateAudited(ctx, pool, entry, func(tx) (T, error))` so the audit row lands in the
mutation's own transaction.

Cycle prevention (section 3.3): before attaching a child, walk the prospective parents'
ancestors and refuse with ErrCycle if the child is among them. Every recursive walk also
carries a `depth < 20` guard.

The descendant walk is section 4 verbatim. `UNION`, not `UNION ALL` — cousins marry in a
village, the same person is then reachable by two paths, and UNION ALL both duplicates rows
and explodes combinatorially.

## Traps that will cost you the task if ignored

- `mutateAudited` copies the audit entry. Stamp `entry.TargetUID` BEFORE the call, never
  inside the closure, or the audit row gets a NULL target.
- Integration tests that write an audit entry must seed the acting user — the audit actor is
  a foreign key, otherwise SQLSTATE 23503.
- Integration tests need `-p 1`. They share one test database and deadlock in parallel.
- Run `go vet -tags integration ./...` before the gate: an interface change compiles green
  under `make check` and fails only under the integration tag.
