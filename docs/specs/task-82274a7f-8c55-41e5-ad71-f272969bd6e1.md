# An account can say which person in the library it belongs to

Kukátko knows 20 900 photos and the people in them, and it knows who is logged in, but it has
no idea those are the same person. Say once "this is me" and the library can answer questions
it currently cannot: which of these am I in, what is new with me, and whose face belongs to
this comment.

## Evidence (read from the code on 2026-08-12)

- `auth.User` (`internal/auth/models.go:61-78`) carries uid, username, display name, email,
  role, disabled flag and an admin note. Nothing points at a subject.
- `people.Subject` (`internal/people/models.go:131`) has `UID`, `Slug`, `Name`, `Type`,
  `Private` and a **nullable** `CoverPhotoUID` — so a linked person may well have no face to
  show, and every use of one has to survive that.
- `person:` already exists in the query language, matching by name or UID
  (`internal/query/query.go:57`), compiled to SQL by `personCond`
  (`internal/photos/store_query.go:187`). But `internal/query` is by contract a **pure parser**
  that knows nothing about the caller — so `me` cannot be resolved inside it.
- `InitialAvatar` draws letters, and `CommentItem.tsx:71` is where they appear next to what
  somebody wrote.
- The two surfaces that would set this already exist: `web/src/pages/AccountPage.tsx` for
  oneself and `web/src/pages/UsersPage.tsx` for an admin.
- `User` is embedded **verbatim** in the login and `/auth/me` payloads — the model's own comment
  says that is exactly why `Note` is excluded from JSON. A new field is therefore a deliberate
  decision about what the client may see, not an incidental one.

## Requirements

### The link itself

- A user account may name one subject as "who this account is". It is optional, and an account
  without it works exactly as it does today.
- **Several accounts may name the same subject** — a shared family account and a personal one
  are both legitimately that person.
- Deleting a subject clears the link. A login, a session or an account page must never break
  because a person was removed from the library.
- A user sets it for themselves on their account page. An admin sets it when creating an account
  and can change it afterwards, from the user administration.
- An admin changing somebody else's link is a change to another person's account and is audited
  the way the rest of user administration is. A user changing their own follows whatever the
  account page already does for self-service changes.

### "My photos"

- A navigation entry opens the photos the linked person appears in. It is offered only when the
  link is set — an entry that leads nowhere is worse than no entry.

### `person:me`

- `person:me` resolves to the caller's linked subject, so it composes with everything else
  (`person:me year:1998`) and can be saved as a smart album.
- It is resolved where the caller is known, **not** in `internal/query` — that package stays a
  pure parser, which is the rule that keeps the language testable.
- A caller with no link who searches `person:me` gets an empty result and an honest reason. It
  must never silently degrade into "everything" or into free text.
- A subject genuinely named "me" collides with the token. Decide which wins, write the decision
  down, and make sure the loser is still reachable somehow.

### A face instead of letters

- Where a user's avatar is drawn — the comment thread first — the linked subject's cover photo
  is used instead of initials, falling back to initials when the subject has no cover photo,
  which is the common case.
- Linking a face to an account **publishes that face** next to everything that account has
  written. Say so where the link is set, so nobody discovers it afterwards. Check what the
  subject's `private` flag actually gates today before publishing a private person's face.

### "New photos of you"

- The "since your last visit" digest gains a section for new photos the linked person appears
  in, shown only when the link is set and only when there is something to show. An empty section
  is noise.

## Out of scope

- Changing what `private` means on a subject, and any change to who may see which person.
- Bending the review game towards the people a user might know — plausible, unproven, and it
  would make the game's choices unexplainable.
- Notifications of any kind, and letting one user see another's link beyond what user
  administration already shows.
- Face recognition using the link as a seed.

## Implementation notes

- A nullable column on `users` with a foreign key that clears on delete is the shape this wants;
  no new table, so no `internal/reset/tables.go` entry — but check that the reset's "never
  touches accounts" guarantee still holds with the new column.
- Whether the field belongs in the `/auth/me` payload is a deliberate call: the frontend needs
  it to render the nav entry and the avatar, so it likely does — write down why, next to the
  comment that explains why `Note` does not.
- The subject picker should be the same shape as the app's other subject pickers rather than a
  new one; look at how existing components search subjects before writing another.
- Tests: the link surviving subject deletion, two accounts sharing one subject, `person:me`
  resolving for a linked user and returning empty with a reason for an unlinked one, the query
  package staying free of any notion of a caller, the avatar falling back to initials without a
  cover photo, and the nav entry and digest section appearing only when linked.
