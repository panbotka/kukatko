# Passkey Backend (WebAuthn)

Add passkeys as a sign-in method alongside passwords. Registration is open (behind a shared secret), so stronger, phishing-resistant sign-in is newly relevant. This task is backend + API only; the UI comes in a separate change.

## Requirements

- New migration: a passkey credentials table — user FK (ON DELETE CASCADE), credential ID, public key, sign count, transports, a user-chosen name, created_at, last_used_at. A user can have multiple passkeys.
- Ceremony endpoints under /api/v1: begin/finish passkey registration (any authenticated role, registers a passkey for the acting user) and begin/finish passkey login (anonymous, rate-limited with the same limiter pattern and budget as password login). A successful passkey login creates the same sliding session as password login.
- Endpoints to list the acting user's passkeys (name, created, last used) and to delete one. Deleting the last passkey is allowed — the password always remains as a fallback.
- Passkey registration, login, and deletion are audited like other auth events (internal/audit, in the mutation's transaction).
- Config: relying-party ID and origin(s) via new config keys, with sensible defaults derived from existing config where possible; document them in config.example.yaml and docs/OPERATIONS.md. When not configured, the feature is cleanly off: endpoints respond with a clear "not available".
- Expose availability through the existing GET /capabilities payload so the frontend can show/hide passkey UI.
- Pure Go only (CGO_ENABLED=0) — github.com/go-webauthn/webauthn is the expected library choice.
- Unit + integration tests (real test DB) covering both ceremonies, rate limiting, credential listing/deletion, and the not-configured state.

## Implementation notes

- Known repo gotcha: every new table must be classified in internal/reset/tables.go, or the integration suite fails late in internal/reset.
- Sessions and users live in internal/auth; extend its patterns rather than building a parallel auth path.
