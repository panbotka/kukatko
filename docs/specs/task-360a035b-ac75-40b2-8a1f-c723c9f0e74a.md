# `project_id` on the catalogue root tables

## Context

Kukátko is becoming multi-tenant; every catalogue root row must know its project. Design: `docs/superpowers/specs/2026-10-11-multi-tenancy-design.md`, sections 2.4 and 2.5. Step 03 of 40. Already in the tree (verify): `projects` with the bootstrap row `pj0000000000000000veselice`, `internal/project` (`BootstrapUID`), `project_members`.

This step is **schema plus the minimum Go to keep the app green**. Query scoping (adding `WHERE project_id`) is done package by package in later steps. To keep every intermediate state deployable, each new column gets `DEFAULT '<bootstrap uid>'`, so every existing INSERT keeps working; a final step drops the defaults. Production: ~21k photos, ~21k faces/embeddings; the migration runs at startup in one transaction per file — keep it to `ALTER TABLE … ADD COLUMN … DEFAULT <constant>` (metadata-only in PostgreSQL ≥ 11), index creation and constraint swaps, all of which finish in seconds at this size. Make it idempotent (`IF NOT EXISTS`, `DROP CONSTRAINT IF EXISTS`).

## Requirements

- One migration (next free number) adding `project_id TEXT NOT NULL DEFAULT 'pj0000000000000000veselice' REFERENCES projects(uid) ON DELETE CASCADE` to exactly these tables: `photos`, `subjects`, `albums`, `labels`, `face_clusters`, `subject_families`, `photo_tasks`, `upload_links`, `import_runs`, `saved_searches`, `notifications`, `embeddings`, `faces`. Then `UPDATE <table> SET project_id = DEFAULT WHERE project_id IS NULL` as a belt-and-braces guard (no-op).
- `search_history`: primary key becomes `(user_uid, project_id, query)` with the same column definition.
- `instance_settings` and `announcements` (today one row keyed by `id BOOLEAN PRIMARY KEY CHECK (id)`): add `project_id` with the same definition, drop the boolean key, make `project_id` the primary key. The existing single row becomes the bootstrap project's row. `internal/settings` and `internal/announcement` stores: every method takes `projectUID string` right after `ctx` and filters by it; the API packages (`settingsapi`, `announcementapi`) and every other caller pass `project.BootstrapUID` for now with a `// TODO multi-tenancy: project from context` comment (there is one `rg "TODO multi-tenancy"` sweep at the end of the programme).
- `audit_log`: `project_id TEXT NULL` (no FK; indexed). `audit.Entry` gains `ProjectUID string` written into that column when non-empty.
- `photoprism_aliases`: add `project_id` (same definition); primary key becomes `(project_id, photoprism_uid)`.
- UNIQUE constraints/indexes replaced: `photos(file_hash)` → `UNIQUE (project_id, file_hash)`; `subjects(slug)`, `albums(slug)`, `labels(slug)` → `UNIQUE (project_id, slug)`. Check `\d` of each table on the test DB first: find the actual constraint/index names in the migrations (`rg -n "UNIQUE" internal/database/migrations`) and any FK that references `photos(file_hash)` — recreate dependents. `import_runs`' "latest run per source" partial index becomes per `(project_id, source)`.
- Indexes: for each root table, add a composite index with `project_id` leading that mirrors the main listing index (e.g. if `photos` lists by `taken_at DESC`, add `(project_id, taken_at DESC)`); do not invent new orderings — copy the existing ones.
- Denormalised columns on `embeddings` and `faces`: the writers in `internal/vectors` and `internal/people`/`internal/facejob` set `project_id` from the photo's row (`(SELECT project_id FROM photos WHERE uid = $n)` inside the INSERT is fine). Add an integration test asserting an inserted face and embedding carry their photo's project.
- Repository sweep: `rg -n "INSERT INTO (photos|subjects|albums|labels|face_clusters|subject_families|photo_tasks|upload_links|import_runs|saved_searches|notifications|embeddings|faces|search_history|instance_settings|announcements|photoprism_aliases)"` and `rg -n "SELECT \*"` — fix anything that breaks (positional scans with `SELECT *` are the risk; explicit column lists are safe). Run the **full** integration suite (`-tags integration -p 1`, host DSN — see `docs/DEVELOPMENT.md`).
- `internal/reset`: the wipe must still work with the FKs to `projects` (the catalogue tables keep their classification). Run its integration test.
- Docs: `docs/ARCHITECTURE.md` data model — a table listing which tables carry `project_id` directly and which are scoped through a parent FK; note the transitional DEFAULT.

## Out of scope

Adding `WHERE project_id` to any read, the jobs dedup indexes, the `users` table, HTTP routes, UI.
