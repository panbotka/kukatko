# Set up a project for somebody else in one step

A system administrator regularly sets up a project **for another person**, who will then run it alone. Today that takes several disconnected steps: create the project (`POST /api/v1/projects`, where the creator becomes its admin), create an account (`POST /admin/users`, which needs a password the administrator then knows), add the membership, and send a password-reset link. Make it one form: project name + the first admin. The new admin gets an e-mail with a link to choose their own password and lands in their project.

## Requirements

- On the system administrator's project creation screen (`/system/projects`, the create form/modal), add an optional section **"První správce projektu"** (first project admin) with: e-mail (required in this section), display name (optional), username (optional, derived from the e-mail's local part when empty, made unique).
- When the section is filled, one request (extend `POST /api/v1/projects` or add a dedicated instance-level endpoint, the implementer's choice) does, **in one transaction**:
  - creates the project (slug + name as today, limits optional);
  - creates the account **without a usable password**, instance role `user`, email as given;
  - adds it as the project's approved **admin**;
  - does **not** add the calling system administrator as a member. The administrator keeps instance-wide access anyway, and the new owner should see themselves as the only member;
  - mints a one-time **set-password link** (reuse the existing password-reset token machinery and its 7-day validity) and enqueues the mail through `mail_send` in the same transaction;
  - writes the audit entries (project create, user create, member add, password link issued).
- **The e-mail:** a new Czech template (not the generic "reset your password" text): "Byl pro vás založen projekt „<project name>“ v Kukátku. Nastavte si heslo: <link>". Mention the link's validity. After setting the password the person is signed in (or sent to the login page) and lands in `/p/<slug>`. The set-password page reuses the existing `/password-reset/<token>` page, but its wording fits a first password ("Nastavte si heslo", not "Obnova hesla") when the token was issued for a new account.
- **An e-mail that already belongs to an account:** do not create a second account. Add that existing account as the project's admin and send a mail announcing the new project (link to `/p/<slug>`, no password link). Tell the administrator in the form's result which of the two happened.
- **Mail off or unsendable** (`mail.enabled: false`, `.invalid` address): still create everything, and show the administrator the set-password link to pass on by hand, as the existing reset endpoint already answers it.
- The result screen shows: project link, the admin's username, "e-mail odeslán" or the copyable link, and the link's expiry. From the project detail page (`/system/projects/<slug>`) the administrator can re-send the set-password mail while the account still has no password. Re-sending invalidates the previous link.
- Without the first-admin section the form behaves exactly as today (the creator becomes the admin).
- Validation: invalid e-mail → field error; slug taken → existing error; any failure rolls back everything (no project without an admin, no orphan account).
- `kukatko ctl projects create` gains matching flags (`--admin-email`, `--admin-name`, `--admin-username`) and prints the result, including the link when mail is off.
- Tests: Go integration tests (new account path, existing-account path, mail-off path returns the link, rollback on failure, the caller is not a member, audit entries, the mail job is enqueued with the new template). Mailer template test. Vitest for the form and the result screen. ctl test.
- Docs: `docs/API.md`, `docs/FRONTEND.md`, `docs/OPERATIONS.md` (ctl flags), `README.md` (user-visible feature).

## Privacy

Use only placeholder data (`example.com` addresses, invented names) in tests, docs and commit messages.
