# Make AVIF handling consistent and refuse truncated images at ingest

Found in the v0.28 prerelease walkthrough (staging, commit b32f870). The content check from
71bff1b works for junk, but two cases still produce a "photo" that can never get a thumbnail and
whose face/embed/OCR jobs fail until they die.

## 1. AVIF is inconsistent across the upload paths

- The public link page's picker `accept` list offers `.avif`, but `POST /u/{code}/upload` refuses it
  as `unsupported_type` ("Tento typ souboru se nenahrává") because `imgconvert.IsSupportedFormat`
  does not know AVIF.
- The signed-in `POST /upload` **accepts** AVIF (`image/avif`, 640×480), then warns
  `phash_failed: imgconvert: unsupported format … .avif` and `thumbnail_failed`; its `face_detect`,
  `image_embed` and `ocr` jobs fail repeatedly.

## 2. A truncated JPEG passes the content check

- `head -c 2000 photo.jpg > trunc.jpg` has a valid JPEG signature, so it is accepted (`created`,
  warning `phash_failed: invalid JPEG format: short Huffman data`) and its jobs fail.

## Requirements

- Pick one AVIF policy and apply it everywhere: **either** support it end to end (decodable for
  thumbnails/pHash/blurhash/sidecar ML, e.g. via an existing shell-out tool available in the
  Docker image, still `CGO_ENABLED=0`) **or** refuse it on every path (`/upload`, upload links,
  `import dir`) with the stable `unsupported_type` code and drop `.avif` from every client `accept`
  list. Document the choice in docs/API.md and the README's format list.
- The client `accept` lists (upload page, upload-link page) and the server's accepted set must be
  derived from or tested against one source, so they cannot drift again.
- A still image whose data cannot be decoded (truncated/corrupt beyond the header) is refused at
  ingest as `not_media` (or a new stable code, translated cs/en) before any row, original or job
  exists — but only when decoding is actually possible for that format; a format Kukátko cannot
  decode in-process (HEIC/RAW) must not be refused for that reason alone.
- Do not regress what passed the walkthrough: PNG, GIF, TIFF, BMP, WebP, HEIC (real iPhone), RAW,
  MP4, MOV, AVI, MKV, MPG, MTS, 3GP, FLV, WMV still ingest; byte-identical duplicates still return
  `duplicate`.
- Tests: ingest unit/integration cases for AVIF (per the chosen policy), truncated JPEG, truncated
  PNG; a frontend test that the accept list matches the server's set.

## Repro
Staging: `ssh box` stack, upload `f.avif` (ffmpeg libaom still picture) via `/upload` and via a
link; upload a truncated JPEG via either. Prerelease shots: scratchpad `63-avif.png`.
