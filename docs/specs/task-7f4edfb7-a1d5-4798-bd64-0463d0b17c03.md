## Context
Round-2 review of the multi-tenancy programme (2026-10-14, main 672357f6). Report: `<backup dir>/multitenancy-review-2/fixes-review.md` §C5, §C6, §E1. Verify with `rg` each still holds.

Findings:
- C5 (`internal/auth/store_user_audit.go`): disabling an account does not take the per-project lock the last-admin guard uses. A maintainer disabling admin B while admin A demotes themselves can leave a project with no working admin and no `stranded_projects` note.
- C6 (`handlers_admin.go` ~47 + `web/.../AccountFormModal.tsx` ~111): every edit of an already-disabled last admin records `stranded_projects` again; it should be noted only on the enabled → disabled transition.
- E1 (`AccountFormModal.tsx` ~105-113, `setUserDisabled` in `web/src/services/users.ts`): the edit PUTs the whole record as loaded; a name change can silently re-enable or re-promote an account another maintainer just changed.

## Requirements
- Disable/enable takes the same locks (in the same order) as the membership role changes for every project the account administers; the stranded check runs inside that transaction. Concurrency integration test (two goroutines) that fails on current code.
- `stranded_projects` recorded only on the transition.
- Account edit sends only changed fields (PATCH semantics) or uses optimistic concurrency (an `updated_at`/version precondition → 409 with a "changed meanwhile, reload" message). Vitest + API test.
- Docs: API.md, FRONTEND.md, PACKAGES.md.

New admin features.
