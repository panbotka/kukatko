# The nameless catch-all subject is still first in /people, and only SSH can remove it

Reported from production on 2026-08-03, **after** v0.3.0 was deployed (the container
has been running `ghcr.io/panbotka/kukatko:0.3.0` since the merge of
kozaktomas/vps#63):

> https://kukatko.kotrzina.cz/people — Tady stale vidim osobu bez jmena s 16531 fotkama.

This is expected behaviour of the current code and still a bad end state. Commit
`7dd2c55` (`fix(people): a nameless face must not resolve to a catch-all subject`)
changed the *find-or-create* key so no new nameless face joins that subject. It
deliberately did not touch the rows already written, because detaching them is
irreversible unless a snapshot is taken first.

Measured on production the moment the report came in:

```
uid        sunuikf1e9jdpjog5qgomsvgrb
name       ''            (empty string, type=person, slug='subject')
created_at 2026-08-02    (inside import run 2)
markers    16 531        <- the number the UI shows
photos      6 767        distinct photos those markers fall on
faces     111 155        of 115 457 in the whole library = 96 %
```

Real people for comparison: Miloslav Novotny 982, Tomáš Kozák 427, Lubomír Němec 293.

## The gap this task closes

The repair exists as `kukatko maintenance nameless-subjects` (`cmd/kukatko/namelesscmd.go`,
backed by `people.ListNamelessSubjects` / `DetachSubject` / `RestoreSubject`, documented
in `docs/OPERATIONS.md`). It reports by default; `--apply` requires `--undo-file`, and
`--undo` replays the snapshot.

The problem is reachability: the operator can only run it over SSH into the production
container. Everything else about this class of problem — the maintenance scan, the
repairs, the job queue — is on the admin **Údržba** page. This is the one thing that
is not, and it is the one the user is actually looking at.

Surface it there:

* a card that runs the **report** (read-only, safe to click) and shows what it found —
  the subject's uid, its marker/photo/face counts, and that its name is empty;
* an **apply** action behind a confirmation that makes the irreversibility explicit and
  **hands the undo snapshot to the browser as a download** — the CLI's `--undo-file`
  contract must not be quietly dropped just because the caller is now HTTP. If the
  snapshot cannot be delivered, the apply must not happen;
* the matching **undo**, taking that file back.

Reuse the existing `people` functions and the existing audit path; do not write a second
implementation of the detach. RBAC: maintainer, like the rest of `/maintenance`.

## Do not

* Do not hide nameless subjects from `/people` in the frontend as a shortcut. The row is
  real, it owns 96 % of the library's faces, and hiding it would make a data problem
  invisible instead of fixing it.
* Do not run the repair against production as part of this task. Ship the capability;
  the operator decides when to pull the trigger. Note in the task result that it is then
  a one-click step.

## Watch out

Detaching ~111 155 faces sets `subject_uid = NULL` on them, which moves every one of those
rows **into** the partial HNSW index that migration 0047 created (`WHERE subject_uid IS
NULL` — it matches 4 rows today). That is ~111 k HNSW graph insertions of index maintenance
in one go; expect minutes, and make sure the HTTP handler does not sit on a request
timeout waiting for it. Consider doing the work through the job queue rather than inline
in the request.
