# Evaluate: CSRF protection rests solely on SameSite=Strict cookies

A source-only security audit (2026-10-06, commit 3792f7c) produced this **unconfirmed lead**. Its exploitability depends on deployment (sibling hosts on the same registrable domain) and browser facts. This task **evaluates, documents and proposes; it does not change behaviour.**

## The lead
- The /api/v1 router (`internal/server/server.go:111-124,150`) has no Origin, Referer, Sec-Fetch-Site or Content-Type gate for unsafe methods.
- `auth.decodeJSON` (`internal/auth/handlers_auth.go:45-53`) decodes JSON whatever the Content-Type. A `text/plain` HTML form whose field name and value join with `=` into valid JSON is therefore accepted.
- The session cookie is HttpOnly and SameSite=Strict (`internal/auth/cookie.go:21`), so truly cross-site requests carry no cookie. A page on a **same-site** sibling origin (another subdomain of the same registrable domain, or XSS there) does carry it.
- The strongest blind write is POST /api/v1/admin/users (`internal/auth/handlers_admin.go:126`) against an admin victim: an account with a chosen role, created without reading any response.
- Login CSRF (POST /auth/login, which is public) works only if browsers store a Strict Set-Cookie from a cross-site top-level POST response.
- `web.allowed_origins` exists in config but is never read.

## Requirements
1. List every cookie-authenticated unsafe route under /api/v1 that uses a JSON decoder ignoring Content-Type, and every route that accepts form or multipart bodies. Check whether the shared decoders outside internal/auth behave the same.
2. Add httptest-level tests showing that a `text/plain` JSON body with a valid session cookie is accepted today on a representative mutation (for example the admin user create).
3. Do not change behaviour in this task.
4. Write a new SEC entry in `docs/SECURITY_AUDIT.md` covering:
   - the confirmed behaviour and the precondition (a same-site sibling origin)
   - which hosts the owner must check under the production parent domain
   - concrete fix options, with impact on the SPA, `kukatko ctl` (Bearer, unaffected) and the public /u/{code} upload page: an unsafe-method middleware that rejects `Sec-Fetch-Site` values other than same-origin/none, with an Origin-vs-configured-host fallback; requiring `Content-Type: application/json` on JSON routes; wiring or removing the dead `web.allowed_origins` and `web.session_secret` keys
   - a recommendation
