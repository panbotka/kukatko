# Rework /system into a library & health dashboard

Give the admin page a dashboard at the top that answers "what is in the library and is it
healthy", move the announcement box to the bottom, and stop presenting job counters as if they
described the library.

## Requirements

### Layout

- The dashboard comes first on the page; the **announcement box moves to the bottom**.
- The existing quick actions (dead-letter requeue, backup trigger, maintenance) keep working.

### Library

- Photos in the library (excluding archived), of which videos; in trash (`archived_at`); hidden
  (`hidden_from_library`); private (`private`).
- Uploads in the last 24 h / 7 days / 30 days / 365 days.
- Albums, labels, subjects (people), faces, embeddings.
- **Storage from the catalogue**: sum of `file_size`, reported separately for the library, the
  trash and derived media, in GB. The VPS disk figures (`free_bytes`/`total_bytes`) may stay only
  if clearly labelled as the server disk — today they read as the library's storage while
  `originals_bytes` reports 0, because prod keeps originals on R2 (really ~77 GB).

### Job queue

- Break the queue down by **type x state** (queued / running / failed / dead / done) instead of
  one lifetime total per type.
- Offer **per-type requeue of dead jobs**, alongside the existing requeue-all.
- Lifetime counters either disappear or are explicitly labelled as "jobs ever run". Today's
  `image_embed: 41 594` against 20 930 photos (a re-embedding migration) is the main source of
  confusion.

### Health

- Age of the last backup, last import, embeddings-sidecar reachability, mapy.com geocode budget.

### Remaining work

- Faces with no subject + clusters awaiting a name.
- Photos without `taken_at`, without GPS, without a place, without OCR.
- Duplicate groups and duplicate markers.

### General

- Every number that has a matching view links into it (library with a filter, trash, clusters,
  duplicates); a tile with nowhere to go stays static.
- Aggregates must not full-scan on every page load. Use the existing partial indexes, aggregate
  in SQL, cache if needed; the endpoint stays responsive at 20k+ photos and 130k+ jobs.
- Backend: extend `internal/system` and `GET /system/status` (stays maintainer-only, auth
  unchanged). Frontend: `SystemStatusPage`.
- i18n for cs + en on every new string; no hardcoded text.
- Tests: Go integration tests for the new aggregates against the real test DB; Vitest for the
  dashboard including a zero/empty state.
- Docs: `docs/API.md`, `docs/FRONTEND.md`, `docs/PACKAGES.md`.

## Out of scope

- Changing who may see the page.
- Any time-series/history storage of these metrics — current state only.
- Redesigning the rest of the app.
