## 1. Why the crop is mush — measured, not guessed

`OutlierCard.tsx` already does the two things that matter conceptually: it crops from
`fit_720` (correct — `tile_*` is centre-cropped square and would put the bbox in the wrong
place) and grows the box by 30 % on every side, with the comment "a tight crop of a face you
are asked to judge is unjudgeable".

The problem is resolution, and `fit_720` is a **constant**. Measured on production for the
subject in that URL (Tomáš Kozák, 289 assigned faces):

```
average box width          4.9 % of the frame
smallest box width         1.17 %
narrower than 5 %          198 of 289  (69 %)
narrower than 3 %          116 of 289  (40 %)

width in a fit_720 thumbnail:   average 35 px, smallest 8.4 px
```

A 35 px face rendered into a 16rem (≈256 px) card is a 7x upscale. The 8 px one is nothing at
all. That is the whole complaint: it is not a cropping bug, it is asking a 720 px thumbnail
for detail it never contained.

The thumbnailer offers `fit_720`, `fit_1280`, `fit_1920`, `fit_2560`, `fit_3840`. **Choose
the source per face from the box's relative size** so the face lands at a usable pixel width
in the rendered card, rather than always taking the smallest. Do not simply switch the
constant to `fit_3840` — that makes every card pull a multi-megabyte image for faces that were
fine at 720, on a grid that shows dozens at once. Pick the smallest size that clears the bar,
and say in the commit message what bar you chose and why.

Check whether the chosen sizes are actually generated for the whole library before relying on
them; if some are missing, the card must degrade to what exists rather than showing a broken
image.

## 2. Column count, like the library

The library already has this and it must be reused, not reinvented: `web/src/lib/gridDensity.ts`
(`GRID_COLUMNS_MIN` 1, `GRID_COLUMNS_MAX` 10, `GRID_DENSITY_DEFAULT` 5, persisted under
`kukatko.grid.density`, plus `gridTemplateColumns(density)` and the width-aware
`initialColumnsForWidth`).

`/outliers` currently hardcodes `repeat(auto-fill, minmax(16rem, 1fr))`. Give it the same
control and the same persistence.

Decide deliberately whether outliers share the library's stored density or keep their own key.
They are different jobs — the library is for browsing, this is for judging faces — so a shared
setting may fight the user. Whichever you choose, say why in the commit message.

The sibling grids (`CandidateResults.tsx`, `PersonSweepCard.tsx`) hardcode the same 16rem. If
the control generalises cleanly, they are the obvious next users — but do not fold them into
this task unless it is genuinely free.

## 3. The marker must always be visible

The outline exists (`boxStyle`, a 3 px `--bs-warning` border, `data-testid="outlier-bbox"`),
but the ask is that it stays legible **at every column count**. Once the user can choose 10
columns, a card is a fraction of its current width and a 1 %-wide box becomes sub-pixel.

Requirements:

* the outline is never clipped by the card's `overflow-hidden` — the context crop must keep
  the whole grown box inside the visible area at any tile size;
* the outline never degrades below a legible stroke, so it does not vanish at high density;
* if a box is so small that the outline would be bigger than the box, the card must still make
  the location obvious. Say what you chose (a minimum apparent box, a marker glyph, something
  else) rather than letting it silently disappear.

Take a screenshot at 1, 5 and 10 columns for a face in the 1–3 % size band and confirm by
eye. `see docs/ARCHITECTURE.md` for how the project verifies visual work; there is prior art
for driving the real UI in a browser rather than trusting jsdom.
