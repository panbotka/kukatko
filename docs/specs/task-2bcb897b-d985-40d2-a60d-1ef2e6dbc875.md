# OAuth 2.1 nad MCP — rozhodnutí a návrh, ne rovnou implementace

Cíl uživatele: *„aby si to lidi klidně mohli přidat jako MCP v UI (Claude, ChatGPT)."*
Dnes to nejde a je to jediná věc, která tomu brání — nástroje samotné jsou v pořádku.

**Tenhle task má skončit návrhem a doporučením, ne hotovou implementací.** Je to rozhodnutí
o novém bezpečnostním povrchu nad živou rodinnou fotoknihovnou; ať se o něm rozhodne vědomě.
Až bude návrh schválený, založí se implementační task(y).

## Proč to dnes nejde (změřeno 2026-09-12)

Throwaway instance s `KUKATKO_MCP_ENABLED=true`:

- `POST /api/v1/mcp` bez auth -> `401 {"error":"authentication required"}`, **bez**
  `WWW-Authenticate`
- `/.well-known/oauth-protected-resource*`, `/.well-known/oauth-authorization-server`,
  `/.well-known/openid-configuration`, `/register` -> **200 text/html** (SPA fallback)
- OAuth v repozitáři **není vůbec** — je to vědomé rozhodnutí, zapsané v
  `docs/superpowers/specs/2026-07-09-api-tokens-and-ctl-design.md`: „no OAuth support at all —
  no RFC 9728 protected-resource metadata, no token verification"

Autentizace dnes: session cookie nebo `Authorization: Bearer kkt_…` (API token), guard
`auth.API.RequireAuth`.

## Co klienti vyžadují (ověřeno v oficiální dokumentaci)

**MCP spec** (https://modelcontextprotocol.io/specification/draft/basic/authorization):
- „MCP servers **MUST** implement OAuth 2.0 Protected Resource Metadata (RFC 9728)"
- 401 musí nést `WWW-Authenticate: Bearer resource_metadata="…"`, volitelně `scope="…"`
- autorizační server musí mít RFC 8414 nebo OpenID Connect Discovery metadata
- server **MUST** ověřovat, že token byl vydán pro něj jako audience (RFC 8707 `resource`)

**Claude** (https://claude.com/docs/connectors/building/authentication) podporuje typy:
`oauth_dcr` (RFC 7591 Dynamic Client Registration), `oauth_cimd` (Client ID Metadata Document),
`oauth_anthropic_creds` (přes `mcp-review@anthropic.com`), `custom_connection`,
`static_headers` (**beta**, zadává org admin), `none` (authless).
- CIMD si Claude vybere, jen když AS inzeruje **obojí** `"client_id_metadata_document_supported": true`
  **a** `"none"` v `token_endpoint_auth_methods_supported`
- PKCE S256 je povinné, AS musí inzerovat `code_challenge_methods_supported: ["S256"]`
- redirect URI hostovaných klientů: `https://claude.ai/api/mcp/auth_callback`;
  Claude Code používá loopback na náhodném portu (RFC 8252) a musí se mu tolerovat libovolný port
- `resource` v protected resource metadata musí **přesně** odpovídat URL, jak ji uživatel zadá
- timeouty: 10 s na discovery/registration/token, 30 s na refresh
- egress Anthropicu: `160.79.104.0/21`
- `/token` musí přijímat `application/x-www-form-urlencoded`; `/register` naopak `application/json`
- refresh tokeny se u public klientů musí rotovat; neplatný refresh -> `invalid_grant`

**OpenAI** (https://developers.openai.com/api/docs/guides/developer-mode,
https://developers.openai.com/api/docs/guides/tools-connectors-mcp):
- ChatGPT developer mode: **OAuth / No Authentication / Mixed**; CIMD s `none` nebo `private_key_jwt`
- Responses API umí `authorization` s holým access tokenem — **tudy Kukátko funguje už dnes**
- transport: Streamable HTTP i SSE

## Co už funguje bez jakékoli změny (uvést v návrhu jako baseline)

- **Claude Code:** `claude mcp add --transport http kukatko https://fotky.kotrzina.cz/api/v1/mcp --header "Authorization: Bearer kkt_…"`
- **OpenAI Responses API:** `mcp` tool + `authorization: kkt_…`

Návrh musí odpovědět, jestli to nestačí — tj. jestli „lidi" znamená pár lidí kolem knihovny
(pak stačí zdokumentovat tohle) nebo veřejné UI konektory (pak OAuth).

## Co má návrh rozhodnout

1. **Kdo je autorizační server.**
   - (a) Kukátko samo — vlastní `/authorize`, `/token`, `/register`, discovery, PKCE S256,
     rotace refresh tokenů, consent screen. Plná kontrola, ale je to skutečný AS se vším,
     co k tomu patří, a `CGO_ENABLED=0` + jeden binárka + žádné nové závislosti navíc je tvrdé
     omezení projektu.
   - (b) externí IdP před tím (Authentik/Keycloak/Auth0/…) a Kukátko jen jako resource server,
     který ověřuje JWT a audience. Míň kódu v Kukátku, ale nová provozní komponenta na VPS.
   - Doporučit jednu s odůvodněním; uvést, co to znamená pro `vps` repozitář a pro `make check`.
2. **Registrace klienta:** CIMD vs DCR. Anthropic doporučuje CIMD (DCR registruje nového klienta
   při každém připojení). Ověřit, co z toho ChatGPT reálně umí.
3. **Mapování identity.** Kukátko má vlastní uživatele a role (viewer/editor/admin/maintainer)
   a MCP z nich odvozuje, jestli se vůbec zaregistrují zapisovací nástroje. Návrh musí říct, jak
   se OAuth subjekt mapuje na `users.uid` a co se stane s existujícími API tokeny (zůstanou
   platné? oba mechanismy vedle sebe?).
4. **Scopes.** Minimálně dělení čtení/zápis, ať jde přidat konektor jen pro čtení. Mapovat na
   `Role.CanWrite()`. Rozhodnout, jestli se scope vrací i ve `WWW-Authenticate` (spec to
   doporučuje) a co do `scopes_supported`.
5. **Audience / RFC 8707.** Server musí odmítnout token vydaný pro jinou resource. Popsat, jak.
6. **Bezpečnostní rozvaha — tohle je jádro rozhodnutí.** Otevřít OAuth znamená, že kdokoli
   s účtem může odkudkoli napojit agenta na rodinný archiv. Co to dělá s rate limitem, s audit
   trailem (dnes se každý zápis loguje proti tokenu — jak se loguje proti OAuth klientovi?),
   a jestli má jít zapnout jen pro vybrané uživatele.

## Vstupní podmínka

Návrh počítá s tím, že je hotový task **„MCP: return a proper 401 challenge and stop the SPA
swallowing OAuth discovery"** — bez něj SPA fallback sežere i budoucí `/.well-known/*` metadata
a OAuth by nešlo nasadit, ať se udělá jakkoli dobře.
