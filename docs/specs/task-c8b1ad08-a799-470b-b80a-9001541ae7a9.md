# Tenancy deploy safety: no pre-migration under a running 0.31.0, runner advisory lock

The multi-tenancy chain 0100–0114 is not compatible with the old binary: 0.31.0 served against a migrated schema fails every login with 500 (`column "subject_uid" does not exist`, proven on a production copy 2026-10-13). The docs still recommend running `kukatko migrate` ahead of a deploy, and five CLI subcommands migrate as a side effect.

## Context (verify with rg before starting)
- `docs/OPERATIONS.md` recommends "Run `kukatko migrate` ahead of the deploy if that downtime matters" (around line 28).
- `cmd/kukatko/maintenancecmd.go`, `dirimport.go`, `namelesscmd.go`, `familyexportcmd.go`, `restore.go` call `db.Migrate` before their work.
- `internal/database/migrate.go` applies files without any advisory lock or `lock_timeout`.
- `docs/migrations-rollback/0106_down.sql` and `0108_down.sql` rebuild unique indexes keyed on `(type)` alone; the "only the bootstrap project exists" guard lives in `0102_down.sql`, which runs after them.

## Requirements
- `docs/OPERATIONS.md` upgrade runbook and `docs/MIGRATION_SAFETY.md` release-day checklist state explicitly: for the 0.31.0 → multi-tenant release, do NOT run `kukatko migrate` (nor `maintenance scan`, `import dir`, `maintenance nameless-subjects`, `family export`, `restore`) with the new binary against production while the 0.31.0 container is still running; the only safe order is stop the old container → start the new one (it migrates on start). The general "pre-migrate to shorten downtime" advice is qualified as valid only for releases whose migrations are backward compatible.
- The migration runner takes a session- or transaction-level `pg_advisory_xact_lock` (one fixed key) around the whole run so two concurrent migrators (a `serve` start plus a CLI subcommand) serialise instead of racing `CREATE TABLE IF NOT EXISTS`; the second one finds the schema up to date. Covered by an integration test running two `Migrate` calls concurrently against the test DB.
- The CLI subcommands that migrate as a side effect print one line to stderr before doing so when the database is behind (e.g. "applying N pending migrations"), so an operator sees that the command is about to change the schema. No behaviour change otherwise.
- `0106_down.sql` and `0108_down.sql` carry their own guard (refuse, with a clear message, when more than the bootstrap project has queued jobs of that type, or cancel those queued jobs the way `0107_down.sql` does) so the hand-run rollback chain does not stop half-unwound. Document the chosen behaviour in `docs/MIGRATION_SAFETY.md` Rollback.
- `0110_down.sql` note: document (in the script header and MIGRATION_SAFETY Rollback) that an account with no membership comes back approved, mirroring the forward rule.

## Out of scope
- Changing the deploy mechanism (compose restart) or adding blue/green.
- `lock_timeout` in the runner (would turn a queued ALTER into a restart loop); mention it as a considered-and-rejected option in the runner's doc comment.
