Part 1 of 4 of a notification feature the user asked for. **This one must land first.** Tasks 2–4 (tags per album, featured album, task assignment) build on it.

## Goal
A third notification channel, **in-app**, next to e-mail and Web Push. Each channel is set the same way, per kind, in the existing preferences grid (`components/account/NotificationsCard.tsx`, kinds × channels). **Every kind × every channel is OFF by default**, including the existing kinds. That is the user's explicit decision.

## Current state (mapped 2026-10-11)
- `notifications` (+ `notification_photos`, `notification_prefs` keyed `(user_uid, kind, channel)`) come from migrations 0087/0093. Kinds and their defaults live in the registry in `internal/notification/notification.go`. A missing row means `Kind.Default(channel)`.
  - Today: `tagged` push defaults ON; `registration_pending` push defaults ON, email OFF.
  - Channels: `ChannelPush`, `ChannelEmail`.
- A `notifications` row is written only on the **push** path (producer → `WantsTx(push)` → `CreateTx` → `pushjob.Enqueue`). The e-mail path (`mailjob.Enqueue`) stores no row. Producers are `internal/tagnotifyjob/service.go` and `internal/auth/register.go` (`notifyApprover` / `mailApprover`).
- The store has `Get`, `MarkRead`, `Photos` and `Purge` (retention 30 days read / 90 days unread, **not scheduled anywhere**). There is **no List and no unread count**.
- `internal/notificationapi` says outright, "There is deliberately no 'list my notifications' route". That is now changing. Update that doc comment.
- The frontend has no bell and no inbox. `/n/:uid` (`pages/NotificationPage.tsx`) is the deeplink target and marks the notification read.

## What to build
1. **`ChannelInApp`** (`"in_app"`) in `internal/notification`, plus defaults: **every kind returns false for every channel** (update `registry`; tests pin it). Users who already saved an explicit row keep it. Only the absent-row default changes. Mention this behaviour change in the release notes / README.
2. **Decouple "record" from "push".** Introduce one delivery helper used by every producer, for example `notification.Deliver(ctx, tx, user, kind, payload)`. It:
   - writes the `notifications` row when **in-app OR push** is wanted;
   - enqueues push when push is wanted (and push is on);
   - enqueues mail when e-mail is wanted (and mail is on).
   Producers stop hand-rolling the channel checks. Move `tagnotifyjob` and `auth/register.go` onto it. Rows that exist only for push and are not wanted in-app must not appear in the inbox: add an `in_app` boolean column, or decide inbox visibility another way, and document the choice.
3. **E-mail for every kind**, so all three channels really are "set the same way". The `tagged` kind has no mail template today; add one (Czech, `internal/mailer` templates). Keep the `.invalid` recipient refusal. The daily task digest stays as it is; it is a separate feature.
4. **API** (all-authenticated, owner-scoped, foreign uid = 404):
   - `GET /notifications` — paged, newest first, with `unread` filter;
   - `GET /notifications/unread-count`;
   - `POST /notifications/read-all`;
   - keep `POST /notifications/{uid}/read`.
   Update `docs/API.md`.
5. **Retention:** schedule `Purge` (daily is fine, through the job queue like the other schedulers).
6. **Frontend:**
   - A **bell in the navbar** with an unread badge. Mind the navbar width budget (memory: the bar exists from 992px; check the mobile drawer too). Update `navItems.test` and `MobileNavDrawer.test` if a nav entry is added.
   - The unread count polls modestly (e.g. 60 s while visible) and refreshes on focus.
   - Clicking opens a dropdown/offcanvas list of the latest notifications: title, body, relative time, unread marker, link → the existing `/n/:uid` or the notification's `link`. Add a "mark all read" button and a "show all" page with an infinite list (react-virtuoso when long).
   - Add an **In-app** column to the preferences grid (`notificationKinds.ts` `CHANNELS`). Unlike push, it needs no device subscription.
   - i18n cs + en; icons only via `Icon` (bootstrap-icons `bell` / `bell-fill`); colours only from palette tokens.
7. Tests:
   - Go unit tests for the defaults and `Deliver` channel fan-out (in-app only, push only, mail only, all, none);
   - integration tests for the list / count / read-all endpoints and owner scoping;
   - vitest for the bell, inbox and preferences column.
8. Docs: `docs/PACKAGES.md`, `docs/API.md`, `docs/FRONTEND.md`, `docs/OPERATIONS.md` (any new config key: none expected; retention values may become config keys `notifications.retention.*`), `README.md` (user-visible feature).
