# Face detection sends XMP-only-orientation photos to the detector sideways

A production bug, diagnosed end-to-end on 2026-08-25 against the live library. Nine photos of
one import batch had their face boxes drawn in the wrong place, and two of them found no faces
at all, because the detector was handed the picture lying on its side.

**The affected photos have already been purged from production** and the owner will re-upload
them once this fix ships. So there is nothing to repair and nothing to look for in the live
database — the rows, the album membership and the face rows are all gone. This task is the
code fix and its regression tests, and those tests are the verification.

## Root cause (verified, do not re-derive)

The affected files are **JPEGs misnamed `.dng`**. They carry **no EXIF block at all** — there
is no `Exif\0\0` APP1 segment in the file — and their orientation lives **only in XMP** as
`tiff:Orientation="8"`.

Kukátko has two orientation readers and they disagree on such a file:

- **Ingest** (`internal/ingest/ingest.go`, via `meta.Orientation` from the exiftool-based
  metadata extractor) understands XMP and stored the correct `photos.file_orientation = 8`.
- **`internal/exif.FileOrientation`** (goexif) parses **EXIF only** and returns `0`.
- `internal/thumb` renders from the catalogue value, so the picture displays upright.
- `internal/facejob`'s `StorageSource.uprightFrom` re-reads the orientation **from the file**
  with `exif.FileOrientation`, gets `0`, takes the `orientation <= 1` branch, streams the
  bytes unrotated and reports the raw frame. `face_detections.detect_width/height` was then
  `6048x4032` while the display frame was `4032x6048`.

Measured with the production code against a real original: `DetectFormat` = `jpeg` (magic
correctly beats the `.dng` extension, so `imgconvert` passes the file through untouched),
`exif.FileOrientation` = `0`, while `exiftool` on the same bytes reports
`[XMP-tiff] Orientation: Rotate 270 CW`.

The frontend neither compensates nor should: `web/src/lib/faceGeometry.ts` `faceBoxStyle`
paints the bbox as plain percentages over the rendered image, and its doc comment states the
invariant that was violated — "face detection runs on the upright original and its boxes are
stored against it". `rotateBbox` exists for the *editor's* rotation only.

Consequences measured on one affected photo: the box was painted at 84.4 % / 55.9 % while the
face actually sat at 55.9 % / 6.5 %, and the detected box was 550x481 px — wider than tall,
i.e. a face seen sideways. Two of the nine photos detected **0 faces**, so faces are missed
outright, and the stored embeddings belong to rotated faces, which degrades recognition and
clustering. Both failures are why a client-side box transform is not an acceptable fix.

## Why the current code trusts the file over the catalogue

The doc comment on `OpenUpright` says the rotation is decided from the file being sent and
never from the catalogue, because an `imgconvert` intermediate may already have the rotation
baked into its pixels and re-applying the original's tag would turn the picture twice. **That
reasoning is correct, but it only holds when `imgconvert` actually converted.** On the
JPEG/PNG/WebP/BMP/GIF/TIFF passthrough path `EnsureDecodable` returns the input path
unchanged — the bytes being sent *are* the original — and there the catalogue value is
authoritative. Preserve the existing rationale for the converted case; do not simply start
trusting the catalogue everywhere.

## Requirements

- **The upright decision must know whether the bytes are the untouched original.** Give
  `StorageSource` that fact rather than inferring it loosely; if you determine it by comparing
  the path `EnsureDecodable` returned against the path it was given, say so explicitly at the
  call site, and keep the injectable `Decoder` seam usable from the tests. When the file is the
  untouched original and its own tag yields nothing, fall back to `photo.FileOrientation`.
  When `imgconvert` produced an intermediate, keep today's behaviour exactly.
- **Teach the file-level reader XMP.** `internal/exif.FileOrientation` must read
  `tiff:Orientation` out of an XMP packet when there is no EXIF orientation, so it stops being
  weaker than the reader the ingest path uses. Handle both serialisations — the attribute form
  `tiff:Orientation="8"` and the element form `<tiff:Orientation>8</tiff:Orientation>`. EXIF
  keeps precedence when both are present. Stay pure Go: the build is `CGO_ENABLED=0` and this
  runs per job, so do not shell out to exiftool here.
- **Report the frame that was actually sent.** Whatever branch is taken, the returned
  `UprightImage.Width/Height` must describe the bytes handed to the detector, and the
  `face_detections` row must record that same frame. Note that `facejob.go` already writes
  `Orientation: photo.FileOrientation` into the `faces` row while the bbox was measured on a
  frame chosen by the other reader — close that inconsistency so one photo cannot carry a
  detection frame and an orientation that describe different pictures.
- **Do not touch the frontend.** Re-detection at upload is the fix; transforming boxes
  client-side would paper over misplaced boxes while leaving the missed faces and the rotated
  embeddings.
- **Tests.**
  - A regression test for the reported class: a JPEG fixture with **no EXIF segment** and an
    XMP packet carrying `tiff:Orientation="8"`, proving `exif.FileOrientation` now reads 8 and
    that `OpenUpright` returns rotated bytes with a portrait frame. Build the fixture
    programmatically in the test rather than committing a binary blob.
  - A test that a file carrying its **own** EXIF orientation is still rotated from the file and
    **not** double-rotated when the catalogue also says so.
  - A test that for a converted intermediate (the decoder returns a *different* path) the
    catalogue is **not** consulted, protecting the original design decision.
  - A test that an untagged, genuinely upright original with `file_orientation = 0` is still
    streamed untouched — the common case must keep paying nothing.
- **Docs**: `docs/PACKAGES.md` for the changed behaviour of `internal/exif` and
  `internal/facejob`. Mention the two-readers hazard so the next reader of `source.go`
  understands why the fallback is conditional.

## Explicitly out of scope

- **Do not run anything against production**, and do not go looking for the nine photos — they
  were purged on 2026-08-25 and the owner re-uploads them after this ships. A fresh upload on
  the fixed code is what proves the fix in the field; this task ends at a green `make check`
  and a pushed commit.
- **Do not "fix" the other sideways findings.** `maintenance scan` permanently reports about
  20 photos of PhotoPrism-import provenance whose stored dimension pair is already the oriented
  one; they are query false positives, not unfixed photos, and a blind transform would corrupt
  them. They are a separate, known, documented issue and untouched by this change.

## Implementation notes

- The purged batch was `Rodáci*.dng`, all `file_orientation = 8`, all detected on a
  `6048x4032` frame that should have been `4032x6048`. Those numbers are the shape of the
  regression test, not rows to query.
- `image/jpeg` in the standard library discards APP segments, so reading the XMP packet means
  walking the JPEG markers yourself and picking the APP1 whose payload begins with the Adobe
  XMP namespace URI. Guard against a truncated or malformed segment — a bad packet must return
  "no orientation", never panic.
- Definition of Done per `CLAUDE.md`: docs first, then `make check` (`make check-box` is the
  fast accelerator), then commit and push.
