Found while sizing the full-library import (docs/READINESS_AUDIT.md). Not a correctness bug —
a throughput ceiling that will dominate the cutover.

## The situation

- `KUKATKO_WORKER_COUNT=1` in .secrets/db.env. The comment says why: "image_embed/face_detect
  are heavy even for the RTX 3070, so the sidecar gets a single request at a time (this
  serialises ALL job types)."
- `internal/worker` polls with ONE shared concurrency setting for every job type
  (worker.go:173,193,249). There is no per-type pool.

So the knob that exists to protect the GPU also serialises `thumbnail`, `metadata`, `places`
and `sidecar`. A full import of 20 670 photos runs those one at a time on an ARM Raspberry Pi.

## Why it matters now

The cutover plan keeps the GPU box OFF during the import (the vectors arrive 1:1 from the
photo-sorter feeds, so nothing needs recomputing). While the box is off, `image_embed` and
`face_detect` defer immediately without touching the sidecar — the constraint that justifies
the single slot does not bind at all. Yet thumbnail generation for 20 670 photos still runs
single-file behind it.

## What to build

Per-job-type concurrency, so CPU-bound work can run several at a time while sidecar-bound work
stays serialised. Keep the safe default: whatever is chosen must not let `image_embed` /
`face_detect` run concurrently against the sidecar unless explicitly configured.

Simplest shape that fits the codebase wins — either separate pools per type, or a per-type
semaphore in front of dispatch. Do not add a second queue.

## Verification (mandatory)

- Unit tests proving the sidecar-bound types stay serialised while another type runs
  concurrently.
- A measurement, not a guess: time N thumbnail jobs before and after on this hardware, and put
  the numbers in the commit message. The point of the change is throughput; unmeasured
  throughput claims do not count.
- New config keys into the struct, setDefaults, config.example.yaml, tests and
  docs/OPERATIONS.md together.
- `make check` green.
