# The slideshow asks how you want to watch, and then says what it is showing

Starting a slideshow today is a leap: one click and it plays, at whatever speed was left over
from last time, with no way to say "shuffle these", "loop it", or "and tell me what I'm looking
at". The photos arrive with no title, no description and no date, so a show of family pictures
is a stream of faces nobody in the room can put a year to.

## Evidence (read from the code on 2026-08-12)

- `SlideshowStart.tsx` is a plain `<Link>` to `slideshowHref(scope, view)` — clicking navigates
  straight into the player. All four call sites (library, search, album, label) already pass
  `count={total}`, a prop the component documents as **accepted but deliberately unused**: its
  doc records that the running-time estimate was *moved out* of the start button and into the
  player on purpose. This report reverses that decision, so the reversal must be deliberate and
  written down, not silently undone by the next reader.
- Settings today are `effect` (`fade`/`slide`/`kenburns`/`none`) and `intervalMs`, in
  `lib/slideshowSettings.ts`: persisted to localStorage, sanitised on read, with the interval
  *snapped* to the nearest offered value so a retired option migrates instead of breaking the
  picker. Any new field has to join that same discipline.
- The running player already has a settings card — effect select, interval select and a
  remaining-time readout (`Slideshow.tsx:291-320`). The new options belong in that surface too,
  not in a second one that drifts from it.
- `total` is the **server's** count for the query and may exceed the photos loaded so far —
  pages stream in while the show runs. The estimate can therefore be honest from the first frame.
- **Shuffle has a backend dimension.** There is no random sort: `internal/photoapi/params.go`
  offers newest / oldest / taken_at / added / title / size / rating and nothing else. Shuffling
  only what has loaded over-represents the first page, and paging on a random order needs a seed
  that is stable across requests or pages will overlap and drop photos.
- The control bar does **not** auto-hide — the component's own doc calls it "always-available".
  Nothing about captions may therefore be built on the assumption that chrome disappears.

## Requirements

### A dialog before the show

- Starting a slideshow opens a settings dialog first, every time, pre-filled with the settings
  last used. It offers the transition, the per-photo duration, repeat, shuffle and the three
  caption toggles, and starts the show on confirmation.
- It states **how long the show will take** at the chosen speed, for the photos in this list,
  and the figure updates as the speed changes. With repeat on, it says what one pass takes and
  makes clear it then begins again rather than showing a number that is not true.
- The dialog lives in the one shared component, so all four entry points get it and none can
  drift.
- Dismissing it starts nothing and changes nothing.

### Repeat and shuffle

- Repeat restarts the show at the first photo when the last one has played, without a pause or
  a flicker that reads as a fault.
- Shuffle plays the list in a random order. Whichever way it is implemented, the **whole** set
  must be reachable, not just the pages that happened to load first, and no photo may be shown
  twice before every other has been shown once. If that needs a random order on the server, the
  seed must be stable for the life of the show so paging stays consistent.
- Toggled mid-show, shuffle reorders what is still to come and never replays what has already
  been seen in this pass.

### The photos say what they are

- Title, description and capture date each have their own toggle, and each appears over the
  photo only when it is switched on and the photo actually has that value — an empty field
  shows nothing at all, not a blank line or a placeholder.
- They stay legible for the whole slide, and they belong to the picture rather than to the
  chrome: they are not part of the control bar, and if the controls ever learn to fade out, the
  captions must not go with them.
- Legible over any photo: a white caption on a snow photograph is the case to design for. And
  discreet — this is secondary to the picture, so it must not become a lower third that competes
  with it.
- A long description must not grow to cover the photo. Decide a bound and hold to it.

### Changing your mind mid-show

- The running player's settings menu offers everything the start dialog does.
- Changing any of it **resumes rather than restarts**: the current photo stays on screen, the
  position in the list is kept, and a new speed applies from the current slide onward. Turning a
  caption on shows it on the photo already displayed.

## Out of scope

- The wider UI/UX pass over the player — controls, transitions, phone behaviour, the empty and
  error states. That is its own task and runs after this one; do not start reshaping the player
  here.
- Music, captions burned into an export, casting to a TV, and any sharing of a slideshow.
- Changing which photos a scope selects, or the filters and sort the view carries in.
- The photo detail page's own viewer.

## Implementation notes

- New settings fields follow `sanitizeSettings`: every field validated on read, a documented
  default, and a stored value from an older version resolving to something usable rather than
  breaking the picker.
- The captions need the photo's title, description and `taken_at` in whatever payload the show
  already loads; check before assuming they are there.
- The estimate is a pure function of count and interval — put it beside `slideshowRemainingMs`
  and unit-test it, rather than inlining arithmetic into the dialog.
- Tests: the dialog's estimate against a known count and speed (and with repeat on), the
  settings round-tripping through localStorage including the new fields, captions rendering only
  when toggled on **and** present, a mid-show settings change keeping the current index, and
  shuffle covering the whole set without repeating.
