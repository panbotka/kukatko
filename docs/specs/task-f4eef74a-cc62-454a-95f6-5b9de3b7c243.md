# Project membership

## Context

Kukátko is becoming multi-tenant (one global account per person; a membership row per project with a per-project role). Design: `docs/superpowers/specs/2026-10-11-multi-tenancy-design.md`, sections 2.2 and 2.3. Step 02 of 40. Already in the tree (verify with `rg` first; if missing, end as `needs_review` with a note instead of building it): the `projects` table, `internal/project` with `Store`, `BootstrapUID = "pj0000000000000000veselice"`.

Today the per-user catalogue state lives on `users`: `role` (viewer/curator/editor/admin/maintainer), `approved_at`, `subject_uid` ("this is me"), `last_seen_at`, `visit_reference_at` (what's new), `task_digest_at`. All of these become per-project in `project_members`. **In this step the `users` columns stay and keep being read by the existing code**; later steps move the readers and a final step drops the columns. Production: the migration must be idempotent and fast on 14 users.

## Requirements

- Migration (next free number) creating `project_members`:
  - `project_uid TEXT NOT NULL REFERENCES projects(uid) ON DELETE CASCADE`
  - `user_uid TEXT NOT NULL REFERENCES users(uid) ON DELETE CASCADE`
  - `role TEXT NOT NULL CHECK (role IN ('viewer','curator','editor','admin'))`
  - `approved_at TIMESTAMPTZ NULL`
  - `subject_uid TEXT NULL REFERENCES subjects(uid) ON DELETE SET NULL`
  - `last_seen_at`, `visit_reference_at`, `task_digest_at` TIMESTAMPTZ NULL
  - `created_at TIMESTAMPTZ NOT NULL DEFAULT now()`
  - `PRIMARY KEY (project_uid, user_uid)`, index on `user_uid`.
- Same migration, backfill: `INSERT … SELECT` one row per existing user into the bootstrap project: `role = CASE users.role WHEN 'maintainer' THEN 'admin' ELSE users.role END`; the five other columns copied 1:1 from `users`; `ON CONFLICT DO NOTHING`.
- Same migration: `ALTER TABLE users ADD COLUMN IF NOT EXISTS last_project_uid TEXT NULL REFERENCES projects(uid) ON DELETE SET NULL`, backfilled to the bootstrap uid for every user.
- `internal/project` additions:
  - `Role` type with constants `RoleViewer`, `RoleCurator`, `RoleEditor`, `RoleAdmin`; `ParseRole(string) (Role, error)`; strict ladder predicates `CanCurate()` (curator or above), `CanWrite()` (editor or above), `IsAdmin()` (admin). Mirror the doc comments of `internal/auth/role.go` but **no maintainer** here.
  - `Member` struct (project uid, user uid, role, approved_at, subject_uid, the timestamps, plus joined `Username`, `DisplayName`, `LastLoginAt` from `users`).
  - `Members(ctx, projectUID) ([]Member, error)` ordered by display name; `Membership(ctx, projectUID, userUID) (*Member, error)` with typed `ErrNotMember`; `MembershipsOf(ctx, userUID) ([]MembershipSummary, error)` returning `{ProjectUID, Slug, Name, Active, Role, Approved bool}` ordered by project name (this feeds the project chooser later).
  - `AddMember(ctx, actorUID, projectUID, userUID, role, approved bool)` (idempotent: an existing row is left unchanged and returns typed `ErrAlreadyMember`), `SetRole(ctx, actorUID, projectUID, userUID, role)`, `Approve(ctx, actorUID, projectUID, userUID)`, `RemoveMember(ctx, actorUID, projectUID, userUID)`, `SetSubject(ctx, actorUID, projectUID, userUID, subjectUID *string)`, `TouchLastProject(ctx, userUID, projectUID)` (not audited).
  - Guards: `SetRole` and `RemoveMember` return typed `ErrLastAdmin` when the change would leave the project without an `admin` member. (Self-removal rules belong to the HTTP layer later; the store only enforces last-admin.)
  - Audit actions: `project.member.add`, `project.member.role`, `project.member.approve`, `project.member.remove`, `project.member.subject`; `TargetType: "project_member"`, `TargetUID` = user uid, `details` holds `project_uid` and the role.
- `internal/reset/tables.go`: `project_members` is **preserved**. Reset wipes `subjects`; `project_members.subject_uid` references it, so `internal/reset` must handle this FK exactly like it handles `users.subject_uid` today (look at `reset.go` around the users FK drop/re-add and the memory-style note "TRUNCATE blocked by an outside FK" in `docs/`). Extend the reset integration test to seed a membership with a subject and assert the reset succeeds and the subject link is nulled.
- Tests: integration tests for every store method and typed error; the backfill test (seed users with each of the five roles, run the migration, assert the rows, the maintainer→admin mapping and the copied columns); idempotency (migrate twice).
- Docs: `docs/PACKAGES.md` (`internal/project`), `docs/ARCHITECTURE.md` data model (members, and the explicit note that `users.*` columns are transitional).

## Out of scope

Changing `users.role` values or its CHECK, any reader of the `users` columns, auth middleware, HTTP routes, UI.
