# Evaluate: 200 MP pixel cap allows ~0.8–1.6 GB per ~1 MB upload, with no limit on concurrent decodes

A source-only security audit (2026-10-06, commit 3792f7c) produced this **unconfirmed lead**. Measure it first, then bound it if confirmed.

## The lead
- An anonymous upload-link holder can POST /api/v1/u/{code}/upload, and so can curators through the normal upload.
- Each file is ingested synchronously in its request goroutine (`internal/uploadlinkapi/public.go:267` → `internal/ingest/ingest.go:251`).
- `verifyPixels` (`internal/ingest/pixels.go:55-65`) runs `imgconvert.EnforcePixelBound`. That compares only width×height against `thumb.max_pixels`, which defaults to 200,000,000 (`internal/config/config.go:1410`). It ignores bit depth (`internal/imgconvert/decode.go:57`). An image under the cap then goes to a full `image.Decode`.
- A single-colour 14142×14142 PNG is about 1–2 MB on disk but decodes to 800 MB as NRGBA, or 1.6 GB as 16-bit.
- The bitmap is reused by `hashPixels`/`storeBlurhash`, and `Orient` copies it when orientation ≠ 1 (`ingest.go:456,492`).
- `generateThumbnails` (`ingest.go:438`) then decodes the stored original a second time in `thumb/resize.go:30` `decodeAndOrient`.
- Nothing in ingest, uploadlinkapi or thumb limits concurrency or memory. The public route has only request-rate token buckets (per-IP burst 60, per-link burst 300).
- `docs/PERF.md:873-876` says production previously ran with no container memory limit.

## Requirements
1. **Measure locally.**
   - Write a Go test or benchmark harness. It generates the 8-bit and 16-bit single-colour PNGs just under the cap, then calls `verifyPixels` followed by the thumbnail decode for one upload, and for 3 concurrently.
   - Record peak memory (`runtime.MemStats`, or VmHWM from /proc/self/status). Stop early if it passes about 3 GB.
   - Do not run this inside `make check`: gate it behind a build tag or env var.
   - Never test against production.
2. **If peak memory per upload is in the GB range and grows with concurrency (confirmed):**
   - Add a process-wide bound on in-process full decodes on the upload path, for example a semaphore or a byte budget computed as width×height×bytes-per-pixel before decoding.
   - Make the bound account for bit depth.
   - Consider whether the 200 MP default is still right. Document any threshold change with its measurement in `docs/PERF.md` (or the docs CLAUDE.md routes it to).
   - New config keys go into the Config struct, `setDefaults`, `config.example.yaml`, the tests and `docs/OPERATIONS.md`.
   - Add a regression test proving that N concurrent decodes stay within the budget.
3. **If the measurement does not support the lead:** make no behaviour change, and record the numbers.
4. Record the outcome as a new SEC entry in `docs/SECURITY_AUDIT.md`, following its existing format, with the measured numbers.
