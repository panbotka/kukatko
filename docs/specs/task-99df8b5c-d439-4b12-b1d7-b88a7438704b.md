# Offline in the PWA must not look like a wrong password

Cold-launching the installed app with no network drops the reader on a login form that cannot succeed, and then blames their credentials for it.

## Evidence (observed on production, 2026-08-12, network genuinely offline via CDP)

- The service worker serves the app shell from cache, then the app redirects to `/login`.
- Submitting **correct** credentials returns: "Prihlaseni se nezdarilo. Zkuste to prosim znovu."
- A reader with no signal will retype a password they have not forgotten.

Two causes:

- `web/src/auth/AuthProvider.tsx:32-38` treats an unreachable backend as signed-out (its comment: "Treat an unreachable backend as signed out so the UI can recover").
- `web/src/pages/LoginPage.tsx:46-56` — `errorKeyFor` branches only on 401 and 429, so a fetch failure falls through to the generic credentials message.

Compounded by the already-known `autoFocus` at `LoginPage.tsx:129`, which pops the keyboard for a form that cannot succeed.

## Second, smaller defect in the same area

With the app already open, going offline shows a correctly placed banner: "Jsi offline. Kukatko zobrazi jen to, co ma ulozene." But the service-worker cache holds only `index.html`, one JS bundle, one CSS file and two fonts — no photos, albums or library data. Every page under that banner fails to load ("Alba se nepodarilo nacist"). The copy promises something the app cannot deliver.

## Requirements

- A login attempt that fails because the backend is unreachable says so, distinctly from a rejected password.
- An unreachable backend is not reported to the reader as "signed out" when the difference is knowable.
- The offline banner's wording matches what the cache actually holds — the app shell opens, the library needs a connection.
- Both Czech and English strings updated.
- Tests cover: fetch failure on login produces the network message, 401 still produces the credentials message, 429 still produces the rate-limit message.

## Implementation Notes

There is an open question the implementer should answer rather than assume: whether the offline notice reaches a **cold-launched** login screen at all. Under CDP emulation `navigator.onLine` read `true` in a document created after the network was cut, so `usePwaStatus` initialised wrong; on a real phone in airplane mode it would likely read `false`. `web/src/App.tsx:172-174` says the status component sits outside the auth gate specifically so the offline notice can reach the login screen — verify that it does.

## Constraints

- **No mutable operations against production data.** Read-only browsing of production is allowed for verification; writes of any kind are not.
- `make check` must pass. `make check-box` runs the same gate on the build box and is much faster.
