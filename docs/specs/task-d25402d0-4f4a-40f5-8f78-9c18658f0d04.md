# Self-service registration waiting for approval

People in the community should be able to create their own account instead of asking an
administrator to do it. A shared secret keeps complete strangers out; an administrator
still has to approve every account before it can be used.

What already exists: the instance settings hold whether registration is enabled and the
shared secret; `users` carries an approval timestamp where `NULL` means "waiting"; and
mail is sent by enqueueing it on the job queue.

## Requirements

- `POST /auth/register` — no authentication. Body: username, display name, e-mail address,
  password, and the shared secret.
- The endpoint is refused outright when registration is disabled in the instance settings.
- The submitted secret is compared with the stored one using a **constant-time**
  comparison. A wrong secret is rejected and rate-limited.
- The endpoint is rate-limited per client address using the existing rate-limit
  middleware, at least as strictly as sign-in is.
- A successful registration creates an account with the lowest role (viewer), **not**
  approved. The password goes through the same hashing as any other account.
- Username and e-mail are validated exactly the way the admin user API validates them. A
  username already taken is rejected with a clear message. Two accounts may share an
  e-mail address.
- Signing in with an account that has not been approved fails with its **own** outcome —
  "waiting for approval" — distinct from wrong credentials and from a blocked account, so
  the sign-in screen can say something useful. It must not create a session.
- On success two mails are enqueued:
  - to the person: the account was created and is waiting for approval
  - to every enabled account with the admin or maintainer role: somebody registered and is
    waiting, naming the username, display name and e-mail
- The registration is written to the audit trail, in the same transaction as the account
  creation.

## Edge cases

- Registration enabled but the secret is empty: refuse to register anybody. An open door
  with no lock is never what the administrator meant.
- No admin or maintainer has a deliverable address: the registration still succeeds. The
  person's own mail is what matters; the notification is best-effort.
- A rolled-back registration must send no mail.

## Definition of done

- Integration tests against the real test database cover: a successful registration, a
  wrong secret, registration disabled, a duplicate username, both mails being enqueued,
  and a sign-in attempt with an unapproved account.
- `docs/API.md` documents the endpoint and the new sign-in outcome.
- `make check` passes.
