# /audit: make the edited thing reachable from the row that records the edit

Asked for on 2026-08-03:

> https://kukatko.kotrzina.cz/audit — Chci tam mit proklik na tu vec, kterou clovek
> zeditoval. Napr. pokud nekdo edituje fotku, tak photo_uid at je proklikavaci na tu
> fotku. Obdobne s alby/stitky.

Today the Target column is dead text — `web/src/pages/AuditPage.tsx:218-224` renders
`record.target_type` and prints `record.target_uid` underneath as plain muted text. Reading
an audit entry therefore means copying a uid and hand-building a URL.

## The mapping

Routes that exist (`web/src/App.tsx`):

| `target_type` | link to |
| --- | --- |
| `photos` | `/photos/<uid>` |
| `albums` | `/albums/<uid>` |
| `labels` | `/labels/<uid>` |
| `subjects` | `/people/<uid>` |
| `users`, `api_tokens`, `announcement` | no detail page — leave as text |

`markers` is the interesting one: a marker uid addresses nothing on its own, but every
marker entry's `details` carries the photo it sits on. Real rows from production:

```
face.unassign | markers | mt8rdjbfhgma1zfg |
  {"action":"unassign_person","photo_uid":"phakulc72calcifi6immisvfl4","marker_uid":"..."}
face.assign   | markers | mk3rq71npuo1h9a4burkdqhjmi |
  {"action":"create_marker","photo_uid":"ph8qpckcoo1vnesecdaqs3f5pv","subject_uid":"suht2a...","subject_name":"Jiří Fabiá..."}
```

So route `markers` through `details.photo_uid` → `/photos/<photo_uid>`. The photo detail
already accepts `?person=<subject_uid>&info=1`, so a face entry can land on the photo with
that person's marker in view — do that where the details give you a `subject_uid`.

## Also link the uids inside Details

The target is not always the useful destination. `label.reject` targets the label but its
details carry the photo the label was rejected on:

```
label.reject | labels | lblo4dqa41lj9fa29i3i5ap5u7 | {"via":"review","photo_uid":"ph9e3e2uluvsukb4h93b0vbpt9"}
```

In the expanded details view, render the known uid keys (`photo_uid`, `subject_uid`,
`album_uid`, `label_uid`, `marker_uid`) as links by the same mapping. Bulk actions
(`ActionPhotosBulk` and friends) leave `target_uid` empty and list their targets in
Details — those lists are exactly where a link earns its keep.

Drive it from **one** table of `type -> path` used by both the Target column and the
details renderer. `web/src/lib/auditView.ts` is the natural home; a second copy in the page
component will drift.

## The thing that makes this non-trivial

**The audit log outlives what it audits.** It is the record of a deletion, so a link to a
purged photo, a removed album or a detached subject is normal, not exceptional — and a
plain `<Link>` will hand the reader a 404 with no explanation of why. Decide this
deliberately and say what you chose in the commit message:

* cheapest honest option: still link, and make the destination pages say "this no longer
  exists" rather than failing blankly;
* or resolve existence for the visible page of rows and render the dead ones as plain text
  with a hint that the target is gone.

Do not pretend the problem away by only linking recent rows.

## Constraints

* Icons only via the `Icon` component, `bootstrap-icons`, decorative ones `aria-hidden`.
* All new strings through i18n, cs + en.
* Keep the row scannable — the uid is already small muted text and the table is dense.
  A link, not a button; do not add a second column.
* `/audit` is admin-only and read-only. This task adds no endpoint and no backend change;
  if you find yourself editing `internal/auditapi`, stop and re-read the ask.
