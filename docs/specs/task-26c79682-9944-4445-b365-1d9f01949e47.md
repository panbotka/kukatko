# /review: let the operator exclude labels, and stop asking only hard questions

Reported on 2026-08-03 against v0.3.0 in production — that is, **after** the variation
work (`10c1481`) and the source selector (`7c5c936`) shipped:

> Stale to neni ono. Chtel bych si byt schopen vybrat, zda stitek bude soucasti review.
> Proste kazdy stitek bude mit boolean hodnotu, jestli se bude taky vyhodnocovat.
> Taky by to melo byt nekonecne a hlavne variabilni, aby to ty lidi bavilo. Obcas stitek,
> obcas oblicej. A hlavne at to vetsinou je kliknuti na ano. Takze at to bere fotky, kde
> je velka sance prirazeni obliceje nebo stitku.

Two of those are already done and must not be redone: faces and labels are interleaved
(`interleave`/`spread` in `internal/review/queue.go`), and no entity may take more than
`review.max_per_entity` (4) questions per batch or appear twice running while another
waits. Do not "fix" variation again — measure it first and say what you found.

## 1. The real cause of "mostly hard questions"

`internal/config`:

```
review.band_min = 0.45
review.band_max = 0.75
```

The queue keeps **only** the uncertainty band and pushes it into the search as a distance
window (`sweep.Params{Threshold: 1 - bandMin, MinDistance: 1 - bandMax}`). Everything above
75 % confidence — exactly the candidates whose answer is almost certainly "yes" — is
excluded by design, to maximise information per answer.

The goal is different from what that optimises for. What matters is **confirmed
assignments per minute of human attention**, plus the game staying bearable. A 90 %-confident
candidate answered "yes" in one click is real work done; it is merely unsurprising.

**Decided with the operator: roughly 70 % of a batch from the confident tier, 30 % from
today's uncertainty band, and the ratio configurable.** New keys, defaults in this shape:

* `review.sure_min` (0.80) — the floor of the confident tier;
* `review.sure_share` (0.70) — the fraction of a batch drawn from it.

Both need the `Config` struct, `setDefaults`, `config.example.yaml`, config tests and
`docs/OPERATIONS.md` in the same commit.

Do not push the share higher on your own initiative. A game that is 95 % "yes" turns the
player into a rubber stamp who stops looking, and wrong assignments then enter the data
through the very feature meant to clean it. The minority of hard questions is load-bearing.

### Infinite means degrading, not stopping

The queue must never come back empty while any unconfirmed candidate exists at any
confidence. When the confident tier is exhausted for the current window, fill from the
band; when that is exhausted, rotate the window (`sweep.Scan` already does bounded rotation)
rather than reporting "nothing to do". Whatever reason string survives must describe a
genuinely empty library, not an empty tier.

## 2. Watch out — widening the band upward is exactly how the box fell over

`MinDistance` was not put into that search for tidiness. Commit `d0d6518` added it because
`candidates.Find` reached **10.9 GB anon-rss** and the host OOM killer took the whole VPS
down, photoprism and mariadb included; pushing the band's far edge into the search stopped
it hydrating confident matches it would then throw away. Raising the ceiling to include the
confident tier gives that back.

So: the tier bound may move, but the **memory** bound may not. `candidates.max_exemplars`,
`candidates.max_candidates` and the cut-before-hydration order must keep doing the work.
`internal/candidates/memory_test.go` measures TotalAlloc per `Find` — extend it to cover the
widened window and treat a regression there as a failure, not a surprise.

## 3. The per-label switch

Migration: `labels.review_enabled boolean NOT NULL DEFAULT TRUE`. A column on an existing
table, so `internal/reset/tables.go` needs nothing — but re-read that file's contract before
concluding it.

**Decided with the operator:**

* default **TRUE**, so behaviour is unchanged until something is switched off;
* the toggle lives **only on the labels page** — deliberately *not* an action inside the
  game. Do not add "don't ask me about this label again" to the question UI;
* **labels only.** Subjects get no equivalent flag in this task. Do not add one for symmetry.

The queue's label source must honour it: a label with `review_enabled = false` produces no
questions and is not scanned (the point is partly to stop paying for it). Existing label
rejections (`internal/feedback`) keep working as they do — this flag is about the label as a
whole, not about one photo.

API: expose the field on the label payloads and let a writer set it. Follow whatever
`internal/organizeapi` already does for label mutations rather than inventing a new endpoint
shape, and audit the change like other curation writes.

## 4. Context you need before you start

Face questions come from *unassigned* faces. In production there are currently **4** of
them: 111 155 of 115 457 faces are attached to a nameless catch-all subject
(`sunuikf1e9jdpjog5qgomsvgrb`), pending the repair tracked separately as task
`bf97784c-bf48-45fd-94c1-0fcc21e70454`. So "sometimes a face" cannot be observed against
production today, and that is not this task's bug to fix.

Consequence for you: **do not measure the face half against a library that has none.** Plant
unassigned faces in the test fixtures and prove the mix there. If you report "faces work
now", say what data you proved it against.
