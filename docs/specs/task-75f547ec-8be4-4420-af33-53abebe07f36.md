# Approve a waiting account

Accounts created by self-service registration wait until an administrator approves them —
`users` carries an approval timestamp where `NULL` means "waiting". Give the administrator
the action, and tell the person when it happens.

Mail is sent by enqueueing it on the job queue.

## Requirements

- `POST /admin/users/{uid}/approve` — admin only. Stamps the account's approval timestamp
  with the current time and returns the updated account.
- Approving an already-approved account changes nothing and is **not** an error. An
  administrator clicking twice must not see a failure.
- Approving does not change the account's role. The account was created with the lowest
  role, and raising it is a separate, deliberate act through the existing user-update
  endpoint.
- Approving a **blocked** account is refused: unblocking is the existing action, and
  conflating the two hides which one the administrator meant.
- On approval a mail is enqueued telling the person the account is now active, with a link
  to sign in.
- The approval is written to the audit trail in the same transaction as the update.
- The admin user listing accepts a filter returning only accounts waiting for approval, so
  the administrator can find them without reading the whole list.
- The maintainer boundary guarding the other user-management endpoints applies here too:
  whatever an actor may not otherwise do to an account, approval must not become a way
  around it.

## Definition of done

- Integration tests against the real test database cover: approving a waiting account,
  approving twice, approving a blocked account, the enqueued mail, the audit entry, and
  the listing filter.
- `docs/API.md` documents the endpoint and the filter.
- `make check` passes.
