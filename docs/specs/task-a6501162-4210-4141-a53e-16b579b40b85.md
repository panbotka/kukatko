# Face detection is broken for photos with a quarter-turn EXIF orientation

Two production reports, one cause. On `phed5phccdsi9p51gvo4gc6er6` the face boxes sit nowhere
near the faces; on `ph9dlnhc0to2asf4soci7dgd0o` no face was found at all. Both are iPhone JPEGs
with `file_orientation = 6`, both were **uploaded** (not imported), and both were detected on
2026-08-17 by the current code.

This is not the bug fixed in `6c09313` (task `720683cd`). That one was the *dimension* boundary
in the importers, and it also shipped `maintenance scan` / `repair --dimensions`. The invariant it
established still holds here: `photos.file_width/file_height` are the raw frame, `file_orientation`
is the raw tag. What is wrong now is one boundary further out.

## The evidence gathered on production

- Both photos: raw `5712×4284`, `file_orientation = 6`, no `photo_edits` row, uploaded.
- Detection **ran** on both (`buffalo_l`, 2026-08-17 06:49): one recorded 2 faces (det_score 0.87
  and 0.81), the other recorded 0. So this is not an unprocessed photo.
- The two recorded boxes are 2.67 and 2.33 times wider than tall. A face is about 0.76 as wide as
  tall in pixels, which in this photo's display frame should normalise to ≈ 1.01.
- Split by provenance, median normalised `w/h` per face:

  | source | orientation | faces | median w/h |
  | --- | --- | --- | --- |
  | imported | 6 | 188 | 0.99 |
  | imported | 8 | 274 | 0.91 |
  | **uploaded** | **6** | **4** | **2.38** |

  Imported (and previously repaired) rotated photos are fine. Every face the **live** path
  produced on a rotated photo is wrong. Four faces is the entire population of that case.

## The suspected cause — verify it before fixing

`internal/facejob` sends the sidecar the **original file with its EXIF intact**
(`ImageSource.OpenDecodable`), and `internal/facejob/bbox.go` rests its whole conversion on one
documented assumption:

> The embeddings sidecar (InsightFace) auto-rotates the image by its EXIF orientation before
> detecting faces, so the returned pixel box is already in display space.

If that is false, both symptoms follow at once: the detector sees a sideways image, so it misses
the faces entirely (the second report) and what it does return is neither face-shaped nor in the
frame the coordinates are then divided by (the first report).

**The decisive experiment:** send the same original to the sidecar twice — once as it is, once
pre-rotated upright with the orientation tag stripped — and compare the face count and the
returned pixel boxes. Do this before changing any code; it decides whether the fix belongs in what
we send, in how we convert what comes back, or in both.

## What to do

- Fix the cause the experiment identifies, and make the assumption impossible to get wrong again:
  whichever side owns the rotation, state the invariant where the code enforces it, not only in a
  comment. The last bug in this family was caused by a comment that had drifted from reality.
- Tests for all four orientations (1, 3, 6, 8), on the path the experiment implicates — not only
  on the one photo from this report.
- **Repair the existing data.** Renormalising the stored numbers is only enough if the detector
  actually saw the faces; where it did not, no coordinate math recovers them and those photos need
  re-detection. Decide from the experiment which applies, do it dry-runnable and reversible the way
  `maintenance repair --dimensions` already is, and reuse that command's shape rather than inventing
  a second repair idiom.
- Re-detection reaches the sidecar on the box, which is usually asleep — the jobs queue and wait,
  which is fine, but say in the report how many photos were scheduled.
- Verify visually in a browser against a real rotated photo, not only with a unit test. This is
  geometry, and a unit test will happily confirm the wrong frame — that is exactly how the previous
  fix nearly went wrong.

## Notes

- Face crops come only from `fit_*`; `tile_*` is a centre-cropped square, so a bbox lands
  elsewhere there. Do not verify against a tile.
- `markers.score` is import provenance, not quality — never rank faces by it.
- Affected today: 4 faces across the uploaded rotated photos, plus however many rotated photos
  have been through the live detector with nothing to show for it. Bound the set in the report.
- Docs: `docs/PACKAGES.md` for `internal/facejob`, `docs/OPERATIONS.md` if the repair grows a
  command or a flag.
