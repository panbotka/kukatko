# Share photos into the phone's own library (Apple Photos / Google Photos)

Someone else uploads the photos, and I want mine in my phone's library: filter, select, share,
saved. A "Share" action next to the existing ZIP download hands the selected originals to the
system share sheet, where iOS offers "Save Images" into Apple Photos and Android offers Google
Photos.

## Requirements

### The share action

- The selection bar (`BatchActionBar`) gains a Share action beside the ZIP download, and the
  photo detail page gains the same action for the single photo shown.
- Both are gated exactly like the ZIP download (`RequireDownload`); a user without the download
  permission never sees them.
- The action is only rendered when the browser can actually do it — `navigator.canShare({files})`
  says yes for a probe file. Where it cannot (desktop Firefox/Linux), nothing appears and the ZIP
  download stays the answer. Never render a button that will throw.

### What gets shared

- Photos and videos are shared as their **original** bytes, under their original filename.
- A photo whose original is a RAW file (CR2, NEF, ARW, DNG, RAF…) is shared as its largest
  cached JPEG preview (`fit_3840`, falling back to the largest size that exists) — a phone
  library handles a RAW badly, and the point is a picture that lands in Fotky.
- The bytes must be fetchable by the page itself: same-origin end to end. If the download route
  answers with a redirect to a signed object-store URL, this flow needs an explicit way to get
  the bytes streamed through the app instead (or verified CORS on the bucket) — a cross-origin
  redirect the page cannot read is the most likely way this feature silently fails.

### Batching, because a phone has a finite amount of memory

- A share batch holds at most 20 files or roughly 300 MB, whichever limit is reached first.
- A selection larger than one batch is shared in several batches, in order, never truncated.
- Each batch is one share-sheet handoff, and each needs its own tap: iOS only allows
  `navigator.share()` inside a fresh user gesture, so a chained call without one throws. The UI
  therefore reads "Share batch 2 of 5" and waits for the tap; between batches it shows how far
  the sequence has got.
- Files are fetched into memory for one batch at a time and released afterwards, so a 400-photo
  selection never holds 400 files at once.
- Cancelling the share sheet (`AbortError`) stops the sequence quietly — it is a decision, not
  an error. A fetch that fails names the photo it failed on, and the remaining batches can still
  be shared.

### Text and feedback

- While a batch is being fetched the button shows progress ("Preparing 12 of 20"), because
  originals over a mobile connection are not instant.
- Czech and English texts complete in both locales; Czech is the default and must not read as a
  translation.

## Implementation notes

- `DownloadZipButton` is the pattern to mirror for placement, permission gating and error
  handling; the ZIP endpoint's `maxZipFiles` cap is the precedent for refusing too much at once.
- Keep the file-fetching and batching logic in a hook/service that can be unit-tested without a
  share sheet; the component should only render its state.
- Tests: vitest over a stubbed `navigator.share`/`canShare` covering the batch split, the
  per-batch gesture, an aborted sheet, a failed fetch and the unsupported-browser case; Go tests
  for whatever the backend has to grow to serve readable original bytes.
- Verify for real in a browser, not only in jsdom: a stubbed `navigator.share` that records what
  it was handed proves the files really arrive as `File` objects with the right names and types.
