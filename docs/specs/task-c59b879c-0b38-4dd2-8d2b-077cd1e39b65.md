`family:<name|uid>` matches photos showing the chosen subject, any of their descendants, and
those descendants' partners — the same set the tree draws, so the page and the filter can
never disagree.

1. `KeyFamily Key = "family"` in internal/query with `specs[KeyFamily] = {kind: KindText}`.
   NO Czech alias: the key registry is English-only by convention, and `osoba:` is already
   deliberately unsupported for exactly that reason.
2. `familyCond` in internal/photos/store_query.go, shaped like `personCond`: a correlated
   EXISTS over markers, with the descendant set as an inner WITH RECURSIVE. That exact shape
   was executed against the test database while the design was written and is valid — see
   section 3.5 of the design.
3. `family:me` resolves through internal/personme exactly as `person:me` does, which keeps
   internal/query caller-blind.
4. `Keys()` publishes the key, so the command palette and `GET /search/schema` should pick it
   up with no further work. VERIFY that they do; do not assume it.

## Traps

- Bind the LIKE pattern and the UID as TWO separate placeholders, the way personCond does.
  Reusing one `$n` for a VARCHAR uid and a text expression fails with SQLSTATE 42P08.
- Never interpolate a user value into SQL; always go through `env.bind(x)`.

## Performance

The inner recursive CTE does not depend on the outer row, so the planner should hoist it into
an InitPlan. MEASURE it — production holds 21 018 photos — and record the timing in the task
notes. Only on evidence take the documented fallback: resolve the descendant set in Go and
pass it as `= ANY($n)`, which needs a pre-pass before compilation because `condBuilder`
receives neither a context nor a pool. Prefer the in-SQL form.
