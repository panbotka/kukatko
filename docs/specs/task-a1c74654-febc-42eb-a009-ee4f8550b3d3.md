# The navbar keeps the old avatar after a profile-picture change

Found in the pre-release walkthrough of `ea97e70`, on the new profile-picture feature
(`ea97e70 feat(account): a user may wear a real picture instead of a coloured letter`).

**Severity: NIT.** It self-heals after a navigation or two, but it lands at exactly the moment
the user is most likely to look — right after setting their picture.

## Symptom

1. Sign in, go to `/account`.
2. In **Moje fotka**, upload a picture (or pick one from the library).
3. The card itself updates immediately. The **navbar account control keeps showing the
   previous avatar** — and it survived a full page reload.

Measured on staging (admin linked to "Testovací osoba 1", then a green test PNG uploaded):

    navbar <img>  src .../users/{uid}/avatar        naturalWidth 55   centre px rgb(151,112,105)  <- old face
    account card  src .../users/{uid}/avatar?v=0    naturalWidth 200  centre px rgb(51,112,83)    <- new upload
    fetch(url, {cache:'reload'})                    200x200, 2380 B, ETag "up-14d66b..."          <- server is correct

So the endpoint is right; the navbar `<img>` is serving a stale cached entry.

Screenshot: `/mnt/nas-botka/kukatko/prerelease-ea97e70/R1-account-picture.png`

## Cause

`GET /users/{uid}/avatar` answers `Cache-Control: private, max-age=600, must-revalidate`.
Within those 600 s the entry is *fresh*, so the browser does not revalidate at all —
`must-revalidate` only governs what happens once it goes stale.

`MyPictureCard` sidesteps this by requesting `...avatar?v=0`, a separate cache key.
`PersonAvatar` in the navbar requests the bare URL, so it keeps the pre-change copy.

Note the comment threads (the other target the spec names) *do* pick up the new picture —
they were fetched fresh in a later page context. Only the navbar was observed stale.

## What to do

Make the avatar URL carry a version that actually changes when the picture changes, and use
it consistently everywhere `PersonAvatar` renders the current user — the navbar included.
The `?v=0` in `MyPictureCard` looks like a placeholder that never increments; a real token
(the picture's `updated_at`, or the ETag body the chain already computes) would fix both
call sites at once.

Alternatively, drop `max-age` to 0 with `must-revalidate` for this endpoint so the ETag does
the work — cheap, since a 304 costs almost nothing and the picture is small.

## Acceptance

- Upload / pick / clear a profile picture; the navbar avatar reflects the change without a
  reload, and certainly after one.
- A cleared picture falls back to the linked subject's face, then to the coloured initial,
  in the navbar as well as on the account card.
- Revalidation still returns 304 for an unchanged picture (do not lose the caching entirely).
