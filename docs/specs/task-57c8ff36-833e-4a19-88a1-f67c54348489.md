# Tasks: a daily e-mail digest

An agent opens questions and review batches in the task queue (`/tasks`) for a human, but nothing reaches the human outside the app. Kukátko already sends four transactional mails through `internal/mailer` (templates rendered purely, Czech), delivered by the durable `mail_send` job in `internal/mailjob`, whose `Enqueue` refuses to queue anything while mail is off. This task adds one digest per person per day listing the tasks that wait on them, on the same rails.

## Semantic

- "Waits on a person" = an open task (`question`, `working`, `review`) on which the person is a participant and the last activity (the newer of the last state change and the newest live comment) was not by them. The tasks store may already expose this as `waiting_on_me`; if not, implement the query here so the digest never has to load every task.

## Behaviour

- A scheduled job `task_digest` runs once a day at `tasks.digest.hour` (UTC hour, default 7), following the pattern of the existing scheduled maintenance work (trash retention) in the worker. It is enqueued only when `tasks.digest.enabled` is true (default false) **and** mail is on.
- For every active, approved user with a valid e-mail address and at least one waiting task, send one mail: subject "Čeká na tebe N úkolů", body with up to 20 tasks (title, state in words, the absolute link `https://<public base>/tasks/{uid}`) and "…a dalších M" when there are more, plus a link to `/tasks?waiting=1`. Template name `tasks_waiting_digest`, in `internal/mailer/templates.go` next to the four existing ones, Czech like them, rendered purely and tested.
- Send only when something changed since the last digest: keep `users.task_digest_at`; send when any waiting task's last activity is newer than it, or when it is NULL. Stamp it after enqueuing. A person with nothing new receives nothing.
- A `.invalid` recipient is skipped (the mailer already refuses it; do not let it fail the whole run).
- Config keys `tasks.digest.enabled` and `tasks.digest.hour` go into the `Config` struct, `setDefaults`, `config.example.yaml`, the config tests and `docs/OPERATIONS.md`. The public base URL for links should come from the same place the password-reset mail gets its link base.

## Verification

Pure render test for the template; a store test for "who gets a digest" (waiting vs not, changed vs unchanged since the stamp); a job test with the fake mailer and a fixed clock proving one mail per person, none when nothing changed, none when disabled. `make check` must pass. Update `docs/PACKAGES.md` and `docs/OPERATIONS.md`.
