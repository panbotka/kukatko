# The photo viewer truncates the capture date on a phone

The viewer header shows the photo's capture date, which is the photo's primary label. At
phone width it is cut off mid-year, losing the most useful part.

## Evidence

Same photo, same session, only the viewport width changed:

| Viewport | Rendered title |
| --- | --- |
| 393 px | `7. 9. 201…` |
| 600 px | `7. 9. 2019 17:17` |

The header row still had **48 px of unused space** at 393 px
(`headerRowW 196, childrenTotalW 148`), so the title is not running out of room — it is
surrendering width to the button cluster. The title is laid out as `flex: 0 1 auto` while
the buttons keep their intrinsic size.

## Requirements

- At 393 px the viewer header must show a date a person can actually read. Losing the year
  is the specific failure to avoid.
- Prefer giving the title the free space already in the row. If the full date plus time
  still cannot fit at the narrowest supported width, drop the time and keep the date rather
  than truncating the year.
- The back button and the control cluster must stay reachable and keep their touch targets.
- Desktop must keep showing the full date and time.

## Warning for whoever verifies this

`scrollWidth > clientWidth` does **not** detect this truncation. Chrome reports the
post-ellipsis box, so the DOM claims the text fits while the pixels show an ellipsis:

```
h1ScrollW == h1ClientW == 148, inner span 142  -> "not truncated"
...while the rendered pixels read "7. 9. 201…"
```

Verify by comparing the rendered output at two widths, or by measuring the natural text
width in an unconstrained clone, not by trusting scrollWidth.

## Testing

Add a frontend test covering the narrow-width behaviour of the header title — that it is
allowed to grow into available space, and, if you choose to shorten the format, that the
shortened format still contains the year.
