## Goal (user request)
Comments on **albums**, working exactly like the comments on photos and tasks ("stejný princip"): the same thread UI, the same rules, the same Markdown rendering, and the same @mentions once those exist.

## Current state
- One table, `comments` (migration 0052 created `photo_comments`; 0080 renamed it and added `task_uid`). A comment's subject is stored as **nullable foreign keys, exactly one of them set**, enforced by a CHECK. Migration 0080's header explicitly anticipates "one column per subject kind, paid only when a third kind ever appears". The album is that third kind: follow the pattern and don't introduce a type/uid pair.
- `internal/comments`: plain text (1–2000 chars), soft delete, audited in the mutation's transaction, one rate limit. Every role may write, viewers included.
- The endpoints live in `internal/photoapi` (photo) and `internal/phototaskapi` (task). The client renders bodies through the `Markdown` component (GFM since 597058a; `rehype-sanitize` stays on).

## What to build
1. Migration: `comments.album_uid VARCHAR(32) NULL REFERENCES albums(uid) ON DELETE CASCADE`. Widen the exactly-one CHECK to three columns and add an index `(album_uid, created_at)`. Probe the migration against real data in a throwaway schema first (memory: kukatko-probe-a-migration-against-real-data). Check whether `internal/reset/tables.go` needs anything; it is not a new table, but verify.
2. `internal/comments`: the album subject, with the same store API shape as photo and task. Audit actions are the same as for the other subjects (check whether the target type needs a new value).
3. API in `internal/organizeapi` (next to `/albums`): `GET /albums/{uid}/comments`, `POST /albums/{uid}/comments`, `DELETE /albums/{uid}/comments/{cuid}`, with the same guards, rate limit and payload as the photo/task routes.
   - **Visibility:** whoever can see the album can read and write its comments. Mirror whatever `GET /albums/{uid}` allows.
   - Note from memory: `albums.private` is currently a badge only and does not hide the album from viewers. Don't invent new privacy here; just reuse the album's own read rule so the two stay in sync.
4. Frontend: the comment thread on `AlbumDetailPage`, using the **same** comment component the photo and task pages use (no copy). Place it so it doesn't push the photo grid down. Use a collapsible section or a side panel and match the album page's layout on desktop and phone. Show a comment count badge.
   - i18n cs + en;
   - palette tokens only;
   - 16px inputs on phones.
5. **@mentions:** if the "@mentions in comments" task (d0e9225b) is already on main, album comments get mentions too, with the notification text "… v komentáři u alba <title>" and the link to the album. If it is not on main yet, leave a clear note in the task, and in the mentions spec if useful, that albums are the third subject to cover.
6. `ctl`: if `kukatko ctl` has a comments command for photos/tasks, add albums to it.
7. MCP: if comments are exposed as tools, add album comments with the same RBAC.
8. Tests:
   - Go integration: create/list/delete on an album, the CHECK rejects two subjects set, cascade on album delete, visibility guard, rate limit shared;
   - vitest: the album page thread renders and posts.
9. Docs: `docs/API.md`, `docs/FRONTEND.md`, `docs/PACKAGES.md` (comments line + `CLAUDE.md` package-map line "a photo **or a task**" → "+ an album"), `README.md`.
