# Fix several search-filter matching edge cases

Five independent correctness bugs in the search filter compilation. Each is small and
verifiable; all live in `internal/query` + `internal/photos` + `internal/photoapi`.

## Issues (verified)

1. **Fractional numeric ranges drop boundary values (aperture / focal length).**
   `internal/photos/store_query.go:262-279` (`boundsCond`) applies the `floatMatchEpsilon`
   slack only for an exact single value (`lo==hi`). `aperture`/`focal_length` are `REAL`
   (`migrations/0003_photos.sql:44,46`), so f/1.8 is stored as `1.79999995`; `f:1.8-2.8`
   compiles to `aperture >= 1.8` (float8) and `1.7999999523 >= 1.8` is false → every
   f/1.8 photo is excluded. f/1.8, f/1.4, f/2.8 are among the most-filtered apertures.
   - Fix: apply the epsilon slack to range and open bounds too (widen lower bound down,
     upper bound up) for non-integer/float columns, not only when `lo==hi`.

2. **LIKE metacharacters unescaped in positive substring filters.**
   `internal/photos/store_list.go:515-529` (`textClauses`, for camera/lens/free-text
   `Search`, and the `?camera=`/`?lens=` params) binds `%value%` WITHOUT `likeEscape`,
   while the negation path `store_query.go:41-50` (`searchNotClauses`) DOES escape. So
   `q=a_b` matches `axb`/`a1b` (the `_` is treated as a wildcard) but its negation `-a_b`
   matches literally — a term and its negation use different semantics.
   - Fix: route camera/lens/`Search` patterns through `likeEscape` like the negation and
     query-language paths.

3. **An escaped `\*` still becomes a wildcard.** `internal/query/parse.go:218-219`
   (`parseKindValue` KindText → `charsText`) discards per-rune literalness before the
   value reaches `store_query.go:118-124` (`likePattern`), which turns any `*` into `%`.
   So `title:foo\*bar` (intended literal `*`) cannot be searched; there is no way to
   match a literal `*`.
   - Fix: carry the escaped-ness of `*` through to `likePattern` (e.g. pre-escape
     literal `*` runes at parse time), so only an unescaped `*` becomes a wildcard.

4. **`?flag=eye` is rejected though `flag:eye` works.**
   `internal/photoapi/params.go:112-120` (`applyRatingFilters`) accepts only
   `pick`/`reject` (400 otherwise), while `internal/query/query.go:157` (`KeyFlag`)
   includes `eye` and the store honours it (`store_query.go:398-405`,
   `store_list.go:345`). Two ways to express the same filter disagree.
   - Fix: add `eye` to the accepted values in `applyRatingFilters`.

5. **`taken:YYYY` (UTC) vs `year:YYYY`/`?year=` (DB session TZ) classify boundary photos
   differently.** `internal/query/parse.go:369-380` builds UTC boundaries;
   `store_query.go:284-296` (`yearCond`) and `store_list.go:492-499` (`yearClauses`) use
   `make_timestamptz(...)` in the DB SESSION time zone, and nothing pins the pool TZ. If
   the session TZ isn't UTC, a `2019-12-31T23:30:00Z` photo is year 2020 by
   `year:`/`?year=`/buckets but 2019 by `taken:`.
   - Fix: pin the pool session to UTC (preferred — one reference frame everywhere), or
     compute `year:`/`?year=` boundaries in UTC as `taken:` does. Confirm the
     year↔bucket pairing stays consistent.

## Requirements
- All five fixed; existing correct behavior preserved.

## Testing
- Unit/integration tests per issue: `f:1.8-2.8` returns f/1.8 photos; `a_b` and `-a_b`
  match literally; `title:foo\*bar` matches a literal `*`; `?flag=eye` works; year
  filters agree with `taken:` at a boundary. `make check` must pass.
