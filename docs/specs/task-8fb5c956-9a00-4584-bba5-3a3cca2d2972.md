# Evaluate: password change, admin reset and reset link do not revoke API tokens or passkeys

A source-only security audit (2026-10-06, commit 3792f7c) produced this **unconfirmed lead**. It hinges on a product decision, so this task **evaluates and documents. It does not change behaviour.**

## The lead
- Anyone who briefly holds a victim's authenticated principal (a stolen session cookie, an unattended browser, or any API token) can create a non-expiring API token. POST /api/v1/auth/tokens needs only RequireAuth and no re-authentication (`internal/auth/routes.go:82-83`, `internal/auth/service_apitoken.go:54`). They can also register a passkey (`/auth/passkeys/register/*`).
- All three recovery paths delete only `sessions` rows:
  - `Service.ChangePassword` (`internal/auth/service.go:304`)
  - the admin `ResetPasswordAudited` (`internal/auth/service_admin.go:459`)
  - the consumed reset link (`internal/auth/store_passwordreset.go:198`)
- None of them revokes `api_tokens` or deletes `passkey_credentials`. The planted token keeps passing `AuthenticateAPIToken` (`service_apitoken.go:154`), and the passkey keeps minting sessions.
- An admin can revoke any token by id, but has no route that lists another user's tokens, and cannot delete another user's passkey (`internal/auth/passkey.go:459`).
- `docs/ARCHITECTURE.md:1062` promises only session revocation.

## Requirements
1. Write integration tests that demonstrate current behaviour. For each recovery path:
   - mint a token, run the recovery, then call GET /api/v1/auth/me with the bearer token and record the result
   - repeat with a passkey, using the existing virtual-authenticator test pattern (`passkey_virtual_test.go`)
   - keep these tests: they document the behaviour, whatever is decided
2. Do not change auth behaviour in this task.
3. Write a new SEC entry in `docs/SECURITY_AUDIT.md` covering:
   - the confirmed behaviour
   - the threat scenario (persistence after account recovery)
   - two or three concrete fix options with trade-offs, for example: revoke all tokens and passkeys on every recovery path in the same transaction; prompt the user to review them after a password change; add admin list and delete routes for another user's tokens and passkeys; require re-authentication before minting tokens or registering passkeys
   - a recommendation
4. Add one line to `docs/ARCHITECTURE.md` stating what recovery currently does and does not revoke.
