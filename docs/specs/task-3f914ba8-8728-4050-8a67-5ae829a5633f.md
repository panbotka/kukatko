# Photo detail: what has been computed, and who uploaded it

The photo detail page gets a "Processing" block that says which per-photo computations have
already run, which are waiting, and which failed — and it states the upload (who + when) as one
fact.

## Requirements

### Backend

- `GET /api/v1/photos/{uid}` gains a `processing` array, one entry per step, in a fixed order:
  `metadata`, `thumbnail`, `image_embed`, `face_detect`, `ocr`, `places`, `sidecar`. Each entry
  carries the step key, a state, and the timestamp of the evidence when there is one.
- A step's state is decided by persisted evidence first, by the queue second:
  - `done` — the evidence exists: `photos.metadata_extracted_at`, a `photo_phashes` row
    (thumbnail), an `embeddings` row, a `face_detections` row, `photos.ocr_at`, a `photo_places`
    row, `photos.sidecar_written_at`.
  - `running` / `queued` / `failed` — from `jobs` for this `photo_uid` and job type. `failed`
    covers a dead job and one whose last attempt errored, and carries its `last_error`.
  - `skipped` — the step cannot apply to this photo: `places` without GPS, `face_detect` and
    `ocr` on a video.
  - `pending` — none of the above: it never ran and nothing is queued.
- `face_detect` also reports the recorded `face_count`. `ocr` reports whether the recognised
  text was empty: OCR that looked and found no text is a success, never a gap.
- The whole array is resolved without an N+1 — one round trip for the evidence, one for the
  photo's active/failed jobs.
- `storyboard` is deliberately not in the list: it is generated lazily on first playback and has
  no persisted evidence. Record that reason in the code.
- New maintainer-only `POST /api/v1/photos/{uid}/process/{step}` enqueues that one step for that
  one photo through the existing enqueuer (the dedup index makes a double click harmless).
  Unknown step → 400, a `skipped` step → 409, success → the step's new state.

### Frontend

- A new "Processing" section in the photo info panel — its own visible block next to the
  description and organize blocks, not inside the collapsed technical card.
- One row per step: state icon, human label, and for `done` the time it ran. `done` reads
  calmly; `queued`, `running`, `failed` and `pending` are visually distinct; `failed` exposes its
  error text.
- For a maintainer, every step that is neither `done` nor `skipped` gets a "run now" button that
  calls the new endpoint and refreshes the block. Nobody else sees it — same gating as the
  existing regenerate-thumbnail button.
- Czech and English texts complete in both locales.

### Uploader

- The Origin group in the technical card states the upload as one fact — who uploaded it and
  when (`created_at`) — instead of the uploader alone with the timestamp in a different group.
- A photo with no uploader (imported) reads as "imported", not as an empty dash.

## Implementation notes

- Reuse the job-type constants from `internal/jobs`; do not invent new step names.
- `RegenerateThumbnailButton` is the pattern to mirror for the maintainer action.
- Tests: integration tests for the payload in every state and for the new endpoint's RBAC;
  vitest for the block's rendering and the maintainer gating.
