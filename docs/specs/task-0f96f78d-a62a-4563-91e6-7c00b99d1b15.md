# Comment deep link breaks the photo viewer layout

Opening a photo through a comment link — e.g. a mention or comment notification, which leads to `/p/<project>/photos/<uid>?panel=info#comment-<comment uid>` — renders the viewer broken: the whole viewer is shifted up, so its top toolbar (back button, date title, rating stars, panel buttons) is cut off above the viewport and the info panel's "Informace" header is half hidden. The same URL without the `#comment-…` hash renders correctly.

## Observed (desktop 1440×900, Chromium)

- After load, the viewer root `.kk-viewer` has `scrollTop` ≈ 35 px (it should always be 0), and `.kk-viewer__panel-body` is scrolled to the comment (that part is wanted).
- Cause, most likely: `web/src/components/photo/CommentsPanel.tsx` (~line 149) calls `target.scrollIntoView({ block: 'center' })` to reveal the linked comment. `scrollIntoView` scrolls **every** scrollable ancestor, so besides the panel body it also scrolls the viewer container, which is a fixed full-screen layer whose overflow should never move.
- No console errors, no failing API calls — purely a layout/scroll issue.

## Requirements

- Opening a photo with `#comment-<uid>` scrolls only the panel's own scroll container so the linked comment is visible (and still highlighted, if it is today); the viewer root, the page and every other ancestor stay at scroll 0.
- The viewer's top toolbar and the panel header stay fully visible after the deep link, on desktop and on phone widths (where the panel is a sheet/drawer — check that layout too).
- The second `scrollIntoView` in the same file (~line 271, `block: 'nearest'` on focus) must not shift the viewer either; fix it the same way if it can.
- Prefer scrolling the known scroll container explicitly (compute the offset and set its `scrollTop`/`scrollTo`) over `scrollIntoView`; alternatively make the viewer root non-scrollable (`overflow: hidden` / `overflow: clip`) if that is the right structural fix — but verify the root has no legitimate scrolling use (small viewports, zoom).
- Add a regression test (Vitest) proving the deep link targets the panel's scroll container and does not call a whole-ancestor scroll; jsdom has no layout, so assert on the call / scroll target rather than pixels.
- Verify in a real browser (throwaway vite or a staging-like instance, see docs/DEVELOPMENT.md): open a photo with many comments via a `#comment-…` URL, confirm `.kk-viewer` `scrollTop` is 0 and the toolbar is visible.
