Found during the /prerelease walkthrough of v0.22.0..7afafd9 (staging, commit 7afafd94). Pre-existing, not a regression of that range.

## What is wrong

Most `key:value` text filters are case-insensitive but **accent-sensitive**, so a Czech user who types without diacritics gets an empty result with no hint that the word was right.

Reproduce against any instance with a geocoded photo:

    q=country:Cesko   -> total 0
    q=country:Česko   -> total 3
    q=city:Chotěmice  -> total 3

Same shape for `title:`, `description:`, `notes:`, `filename:`, `keywords:` and `lens:`.

## Why it is inconsistent

`internal/photos/store_query.go` has two builders. Only `text:` (OCR) uses the accent-insensitive one:

    query.KeyText: unaccentLikeCond("ocr_text")      // immutable_unaccent on both sides
    query.KeyTitle: likeCond("title")                 // ILIKE only
    query.KeyCountry: placeCond("country")            // ILIKE only

Elsewhere in the library the accent-insensitive form is already the convention: album and label search (`internal/organize/search.go`), subject search (`internal/people/search.go`), the photo fulltext index (`immutable_unaccent` in the generated `fts` column, migration 0007), and — as of 7afafd9 — the task queue search (`internal/phototask/store.go`).

## What to do

Move the remaining text filters onto `unaccentLikeCond` (and give `placeCond` the same treatment for `country`/`city`), so every text filter matches the way the rest of the search does.

Two things to weigh rather than assume:

1. **Cost.** `immutable_unaccent(col) ILIKE …` cannot use a plain index. These are already `%…%` contains-matches that could not use one either, so the change is probably free — but `photos` is the big table here, unlike `photo_tasks`. Measure a plan on a realistic row count before committing to it (see the "Measure on prod with TEMP tables" note in memory), and say in the commit what you measured.
2. **Scope.** Decide deliberately whether `filename:` should unaccent too. A filename is a machine string, and matching it loosely may be more surprising than helpful; if you leave it out, say why in the code comment.

## Done means

- The filters listed above match regardless of diacritics, proven by an integration test in `internal/photos` in the shape of `TestSearch_diacriticsInsensitive`.
- The unit test over the compiled SQL asserts `immutable_unaccent` on both sides, as `internal/phototask/store_test.go` does.
- `docs/API.md`'s filter list says which keys are accent-insensitive, and the line is true for every key it names.
- `make check` green.
