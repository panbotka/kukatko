# Evaluate: uploaded text manifest named .mp4 reaches ffprobe/ffmpeg without a demuxer/protocol allowlist

A source-only security audit (2026-10-06, commit 3792f7c) produced this **unconfirmed lead**. First establish whether it is real, then fix it if it is.

## The lead
- An anonymous upload-link holder (POST /api/v1/u/{code}/upload) or a curator can upload a file named `clip.mp4` whose bytes are a DASH MPD (`<?xml…<MPD…>` with a `BaseURL`) or an HLS playlist (`#EXTM3U`).
- `internal/uploadlinkapi/public.go:255` checks only the filename extension.
- The bytes are staged to an extensionless temp file (`internal/ingest/ingest.go:312`, `kukatko-ingest-*`) and go to `admit` (`ingest.go:242`).
- `looksLikeMedia` matches no signature, so `probedAsMedia` (`internal/ingest/sniff.go:186-196`) runs `video.Probe`. It does so because the client filename has a video extension.
- `ffprobeArgs` (`internal/video/probe.go:56-63`) passes no `-protocol_whitelist`, `-format_whitelist` or `-f`. libavformat auto-detects the demuxer, and dash or hls may then fetch the URLs the manifest names. That would be a server-side GET to an attacker-chosen or internal host, and it would happen during admission, before anything is stored.
- If ffprobe then reports a codec or duration (`video.HasContainerMetadata`, `internal/video/video.go:126`), the file is stored. Every later ffmpeg run on it has the same argv shape and would repeat the fetch:
  - poster: `internal/video/poster.go:191`
  - HLS encode: `internal/hls/encode.go:165`
  - storyboard: `internal/storyboard/generate.go:198`
  - on-the-fly transcode: `internal/video/transcode.go:49`
  - metadata re-probe: `internal/metajob/extractor.go:77`
- Whether this is exploitable depends on the installed ffmpeg build. Recent `hls_probe` refuses a playlist without a .m3u8/.m3u extension. The dash demuxer needs libxml2 and may have no such check. Production runs the unpinned `alpine:3` ffmpeg package (Dockerfile).

## Requirements
1. **Reproduce locally. Never probe production or any external host.**
   - Write a test (build-tagged, or skipped when ffprobe is missing) that starts a loopback `httptest` listener.
   - Write a minimal static DASH MPD whose BaseURL points at that listener, plus an HLS playlist variant. Save each without an extension, as the staged file is.
   - Run the exact `ffprobeArgs` on each fixture with the locally installed ffprobe, and record whether the listener receives a request.
   - Repeat with the `posterArgs` argv on a copy named `clip.mp4`.
   - Also run `ffprobe -hide_banner -demuxers` and `-buildconf` locally and note whether dash and libxml2 are present.
2. **If any request reaches the listener (confirmed):**
   - Make every ffprobe/ffmpeg argv builder that reads user media refuse manifest demuxers. The preferred approach is `-format_whitelist` with only the expected container demuxers (mov/mp4/m4a/3gp/3g2/mj2, matroska/webm, avi, asf, flv, mpeg, mpegts, raw h264/hevc as needed).
   - Keep the behaviour that the transcode input may be a signed R2 https URL. So do not simply restrict protocols to `file` there, or restrict protocols per call site with that in mind.
   - Make `admit` treat a manifest disguised as video as not-media (`ErrNotMedia`).
   - The reproduction test becomes the regression test (the listener receives nothing). Existing video fixtures must still ingest, get a poster, and transcode.
3. **If no request reaches the listener with the local build:** do not change behaviour except as hardening justified in writing. Record which demuxers or checks stopped it and that the result depends on the ffmpeg build.
4. Record the outcome as a new SEC entry in `docs/SECURITY_AUDIT.md`, following its existing format: what was tested, the ffmpeg version, the result and the fix commit.
