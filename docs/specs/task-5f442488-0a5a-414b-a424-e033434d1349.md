# New colour palette: still dark, more cheerful, swappable later

The UI stays dark but moves to a ready-made palette with livelier colours: https://coolors.co/palette/001524-15616d-ffecd1-ff7d00-78290f

- `#001524` deep navy (base/background)
- `#15616D` teal
- `#FFECD1` cream (text on dark)
- `#FF7D00` orange (the accent)
- `#78290F` rust

The user expects to **change the palette again in the future**, so the main deliverable is a structure where swapping palettes is cheap. The hard constraint: **no light text on a light background and no dark text on a dark background anywhere**.

## Requirements

### One palette, everything derived
- The five colours live in **exactly one place**: five `--kk-palette-*` custom properties at the top of `web/src/styles/tokens.css`, or a dedicated `palette.css` imported first. Name them by role (base, surface accent, ink, accent, warm), not by hue, so a future palette maps onto the same names.
- Every other colour in the app is derived from those five: surfaces/elevations, borders, hover/active states, focus ring, muted text, link, selection, badges, and the `--bs-*` variables (including the `--bs-*-rgb` triplets Bootstrap uses for alpha utilities). Derive with `color-mix()` or explicit derived tokens. The `--kk-*` layer keeps working as it does today. **No hard-coded hex/rgb outside the palette file**, except the semantic exceptions below. Add a test (like the existing `styles/*.test.ts`) that fails when a raw colour literal appears in `app.css`/components outside the allowed files.
- A suggested mapping, which the implementer may refine: background `#001524` with lighter navy surface steps; body text `#FFECD1`; primary/accent buttons, active nav, the selection outline and focus in `#FF7D00` **with dark (`#001524`) text on it**, because white on that orange fails contrast; secondary/info elements and the navbar accents in `#15616D` with cream text; rust `#78290F` for warm surfaces/danger-ish emphasis, never as text on navy.
- Semantic colours (success/warning/danger) must stay recognisable. The palette has no green, so success may keep a tuned green, defined next to the palette as a derived "semantic" block. Danger must not be confused with the orange accent.
- Keep `data-bs-theme="dark"` and the Superhero base; the known white-on-white trap (light `--bs-tertiary-bg`/`--bs-secondary-bg` at `:root`) must stay covered.

### Do everything, not just the obvious chrome
Go through every screen and component: navbar + mobile drawer, library grid + selection/hover states, photo viewer chrome and overlays, face boxes/markers, filter panels, forms/inputs/placeholders/disabled states, dropdowns, modals, offcanvas, toasts, alerts (incl. links inside alerts), badges/pills/count tones, tables and record cards, the review game, tasks/comments, maps (Leaflet controls, clusters, popups), the upload page and the public `/u/{code}` page, the sign-in/registration/password-reset screens, empty states, skeletons/blurhash placeholders, charts on the system/admin pages, and scrollbars. Also update `meta theme-color` and the PWA manifest `theme_color`/`background_color`.

### Contrast is tested, not eyeballed
- An automated contrast test over the token pairs (each text/background combination the tokens define): **WCAG AA ≥ 4.5:1 for text, ≥ 3:1 for large text, icons, borders of inputs and the focus ring.** It runs in `make check`, so a future palette swap that breaks contrast fails the gate.
- Additionally run axe-core's `color-contrast` rule (or an equivalent script) in a real browser against a throwaway instance over the main pages, desktop and mobile. Fix every violation. Put the summary (pages checked, 0 violations) in the commit/task notes.
- Take screenshots of the key pages (library, viewer, people, map, users, review, sign-in) desktop + phone, and attach them to the task notes.
