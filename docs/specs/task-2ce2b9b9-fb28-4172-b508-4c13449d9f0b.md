# Library: incremental loading at the end of the page

The library (`/p/<slug>`, `web/src/pages/LibraryPage.tsx`) renders a **windowed** grid: from the first response it is as tall as the whole library (the scrollbar represents all N photos as placeholders) and it fetches whichever pages come into view. That design existed so the timeline scrubber could jump anywhere in one scroll; the scrubber is currently switched off (`TIMELINE_SCRUBBER_ENABLED`). Owner feedback (2026-10-16): the scrollbar spanning the entire library feels wrong; they want ordinary incremental loading — the page grows when you reach its end. Other grids in the app already use the appending mode of the shared grid component (`onEndReached` → next page); see `docs/FRONTEND.md` for the grid component's two modes.

## Requirements
- The library grid uses the appending mode: first page on load, the next page when the user nears the end (prefetch a little before the bottom so scrolling stays smooth), a small loading indicator at the end while a page is in flight, and an end-of-library state when there is nothing more. The scrollbar reflects only what is loaded.
- The total count in the toolbar ("Počet fotek a videí: N") stays the real total from the API.
- **Back always works** (project rule): returning from a photo detail or another page restores the same position in the list — the pages loaded before and the scroll offset — without jumping to the top and without refetching everything one by one visibly. Test it with a position several pages deep.
- The photo viewer's next/previous keeps working past the last loaded photo (it loads the next page when needed), and the selection (shift-click ranges, select all in view, bulk actions), keyboard navigation in the grid and the "Doporučujeme"/"Co je nového" sections above the grid keep working.
- Filters, sort and search still live in the URL; changing them resets the list to its first page.
- Remove or keep switched off the timeline scrubber code paths that depend on windowing; if removed, delete the dead code and its tests rather than leaving it unreachable. Do not change the other grids' behaviour.
- Performance: no regression in time to first thumbnails; keep virtualization of rendered rows (only the data loading changes, not DOM virtualization).
- Tests (vitest; remember jsdom mounts no virtuoso items — mock it and route through the real list as existing tests do): first page, end reached → next page, end-of-library, filter change resets, Back restores the loaded pages and position, viewer next across a page boundary.
- Verify in a browser against a library of a few hundred photos (box staging stack or a throwaway instance), desktop and phone width; update `docs/FRONTEND.md` (and `docs/ARCHITECTURE.md`/`docs/PERF.md` where they describe the windowed library).
