# "You were tagged in N photos" — one notification per window, not per photo

When somebody uploads an album from a village event and then spends an afternoon assigning faces, the people they tag must not receive forty separate notifications. This task collects tagging into one message per person: the first tag opens a window, everything tagged inside that window is counted, and when the window closes one notification says how many photos.

## Context that already exists

`internal/people` owns subjects and markers and keeps the `faces` cache consistent. `AssignSubject` / `AssignSubjectAudited` in that package is the write path **every** assignment goes through — manual tagging, the review game's answers, cluster assignment and candidate acceptance all end there — which is why hooking it once covers every way a person gets tagged.

An account can be linked to a subject (`users.subject_uid`, migration 0060); `internal/personme` resolves `person:me` through that link and is the place to look for how the link is read.

`internal/notification` stores a notification record with a **frozen ordered set of photos** and per-(account, kind) preferences, and already has the kind constant for this message. `internal/pushjob` delivers durably, enqueued inside the caller's transaction, refusing silently when push is off or the account has no devices. The job queue (`internal/jobs`) supports `RunAfter` to delay a job, and dedup through partial unique indexes.

## Requirements

- A migration adding a **pending notices** table: one row per (account, photo) waiting to be announced, with when it was recorded. Unique on (account, photo), so tagging the same person twice on one photo counts once.
- A migration adding a **dedup index on the job queue** for the new job type, keyed on the account in the payload and scoped to `state = 'queued'` only. Migrations 0075 (`family_export`) and 0084 (`task_digest`) do exactly this and explain why the existing per-photo dedup index cannot see a job whose payload has no `photo_uid` — read both before writing yours. Scoping to `queued` matters for a real reason: a job that is already running has read its rows, so a tag landing afterwards must open a **fresh** window instead of being swallowed as a duplicate and lost.
- Hooked into the assignment write path: when a marker is assigned to a subject that is **linked to an account**, insert a pending notice, and — only when this is the **first** pending notice for that account — enqueue the aggregation job with `RunAfter` one window into the future. Both happen in the assignment's own transaction, so an assignment that rolls back announces nothing.
- The window length is a config key, `push.tags.window`, default `1h`. Not a constant.
- A new package for the aggregation job. When it runs it reads every pending notice for that account, creates **one** notification record with the frozen photo set in a sensible order (newest photo first), enqueues its delivery, and deletes the pending notices it consumed — all in one transaction, so a crash part-way re-runs cleanly rather than losing the notices or announcing them twice.
- The message: a title in the shape of "You were tagged in photos" and a body naming the count, for example "You were tagged in 12 photos." It has to read correctly for a single photo, and it has to use **Czech plural forms correctly — Czech has three** (1, 2–4, 5 and up). Czech is the default language, English is the other one.
- **The message must not name who did the tagging.** Several people can tag inside one window, so a single name would be either wrong or a list.
- The deeplink points at the notification's own page — the short per-notification route another task builds. Store the path on the record.

## Hard rules

- **Never notify somebody about their own work.** An assignment made by the account linked to the tagged subject records no pending notice at all.
- **Never record a notice for a photo the recipient may not see.** A private, hidden or archived photo must not produce a pending notice — a notification would otherwise disclose that such a photo exists. Use the same visibility rules the photo listing already applies; do not reinvent them.
- **An untagging before the window closes must un-announce.** Removing an assignment deletes the matching pending notice. A notification must never name a photo the person is no longer on.
- A subject not linked to any account produces nothing; there is nowhere to send it.
- An account that has turned this kind off produces **no pending notices at all**, so the table does not quietly fill up for somebody who does not want the message.

## Edge cases

- Every pending notice was removed before the window closed (it all got untagged): the job finds nothing, sends nothing, completes successfully. It must never create an empty "you were tagged in 0 photos".
- A tag landing while the job is running opens a new window, because the dedup index is scoped to `queued`. That is correct behaviour, not a bug — say so in a comment so the next reader does not "fix" it.
- A whole cluster assigned in one transaction: hundreds of notices, **one** job, one notification. Make sure the first-notice check cannot enqueue hundreds of jobs — test this specifically.
- The recipient's account is deleted before the window closes: the cascade removes the notices, and the job finds nothing.

## Verification

Integration tests against the real test database: many tags inside one window collapse into one notification with the right count; a second window opens after the first closed; untagging removes a notice; a self-assignment records nothing; a private, hidden and archived photo each record nothing; the kind turned off records nothing; a bulk cluster assignment queues exactly one job; the Czech plural is correct for 1, 3 and 12.
