# Curator role 5/5 — unlock the curation actions in the UI

Swap `canWrite` for `canCurate` on the controls a curator is entitled to, which is what
finally makes the role usable.

Read `docs/superpowers/specs/2026-09-26-curator-role-design.md` section 7 before starting.
Requires steps 1 to 4.

## Requirements

- Follow `canCurate` in the album, label, people, subject, family-tree, faces-panel,
  upload, share-target and organize-panel controls — the pages and components that create,
  rename, delete or attach albums, labels, people, faces and family relations.
- Keep `canWrite` in the metadata panel, technical details, photo location, the stack
  strip and the task pages. A curator must not see a control for a capture date,
  an image edit, archiving, hiding, stacking, a task it cannot create, or a duplicate
  merge.
- `BulkEditModal` shows a curator only the album and label fields, plus favorite and
  rating. `useBulkEdit` and `BatchActionBar` follow, so a curator can select photos and
  put them in an album but is never offered the fields the backend would refuse.
- A forbidden action is not rendered at all — the same mechanic `canWrite` already uses
  for a viewer. No greyed-out controls and no explanatory badges.
- Sweep the whole of `web/src` for `canWrite` and decide each site deliberately; roughly
  twenty of the 38 files that consult it belong to curation.
- Tests: vitest covering, for a curator, that a curation control renders and that a
  metadata, stack, task and bulk-date control does not.
- Docs: `docs/FRONTEND.md` for the component-level rule and the `BulkEditModal` field set,
  and `README.md`, where the role list is user-visible.
