# Copy an upload link again after it was created

A curator can copy a live upload link's URL from the links management page at any time, not only right after creating it.

## Requirements

- The short code is stored readably next to the existing `code_hash` (new migration, nullable column). Lookup by code (`ByCode`) keeps going through the hash. This deliberately drops the "plaintext exists only in the create response" rule. Precedent: the registration secret in `internal/settings` is stored readable. Rewrite the package doc in `internal/uploadlink/models.go` and the `internal/uploadlink` line in CLAUDE.md's package map to match.
- Newly created links store the readable code.
- Links created before the migration have only a hash. **The one existing production link MUST keep its current URL working — never rotate or invalidate it.** For such a link, add a "restore code" action: the manager enters the original code, the server checks that its hash matches the link's `code_hash`, then stores the readable code and writes an audit entry in the mutation's transaction. A wrong code is refused (422) and nothing changes. Only a matching code is ever stored. Nothing about the link changes except that the code becomes readable.
- Additionally, a "new code" action (rotate) for any live link, e.g. when a link leaked: generate a fresh code, replace `code_hash`, store the readable code, audit it. The old URL stops working, and the UI must say so before the user confirms. It is a secondary, explicitly confirmed action, never automatic, and never part of the migration. A revoked link refuses both actions with the same error as extend. Decide for expired links and document the choice.
- The migration only adds the column. It must not touch existing links' `code_hash`, expiry or state.
- Only someone who may manage the link can see or copy its URL and generate a new code. That is the same rule as revoke/extend: the link's creator or an admin. The listing (`GET /upload-links`) returns the URL/code only on links the caller manages. For everyone else the field is absent, never an empty string pretending a code exists.
- UI (`web/src/pages/UploadLinksPage.tsx`):
  - Every live link with a known code gets a copy button. It copies the full absolute `/u/<code>` URL and shows the same confirmation the create flow uses.
  - A link without a known code shows "restore original code" as the primary action: an input field, with a clear error on mismatch. "Generate new code" stays available as a secondary action behind a warning confirmation.
  - Revoked and expired links show no copy button.
  - Texts go through i18n (cs default, en).
- The `ctl` client covers it too: the URL appears in the upload-links listing output, and `ctl` has commands for restore code and new code.

## Tests

- Store integration tests: the readable code round-trips. Restore with the matching code stores it and `ByCode` on that same code still finds the link. Restore with a wrong code → error, row unchanged. A pre-migration-shaped row (hash only) keeps resolving after the migration. Rotate invalidates the old code. Both actions write audit entries.
- API tests: a manager sees the code, a non-manager curator does not; the new code endpoint follows the revoke/extend permission matrix; revoked → refused.
- Vitest: the copy button copies the right URL. A legacy link shows restore (primary) and rotate (secondary, with a warning). A mismatch shows the error. A revoked link has no copy button.
- Add the new column/action to `internal/reset` classification if it touches tables (see existing rules).
