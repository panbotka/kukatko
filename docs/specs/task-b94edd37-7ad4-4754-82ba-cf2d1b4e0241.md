# The streaming segments are a new prefix that two operations never learned about

Encoding a video writes its segments into the object store under a prefix of their own. Two
operations reason about the whole store and predate that prefix, and both are wrong today. The
streaming package deliberately exports its prefix so that operations reasoning about whole
prefixes can name the one it owns — deletion and the library reset took it up, backup and the
storage migration did not.

## The two defects

**The storage migration strands every rendition.** The migration plans exactly three classes of
object: the original, the metadata sidecar and the cached thumbnails. Streaming segments are not
planned at all. A migration from local disk to the object store therefore moves originals and
thumbnails and leaves the segments where they were — while the rendition rows in the database
survive untouched. The photo detail keeps reporting the clip as streamable, the player asks for
its playlist, and every segment answers 404. The library looks fine and every video is broken.

**The backup copies segments as if they were originals.** The originals lister enumerates the
whole bucket and skips only the database dumps and in-progress uploads; its own comment states
the invariant that everything else in the bucket is an original because derived artefacts are
cached elsewhere. The streaming commits broke that invariant. Every segment of every video is now
copied into the backup bucket and counted as an uploaded original. On the staging instance that is
470 MB of regenerable data against 1.9 GB of video originals — the backup carries a quarter again
of pure derived weight, and it grows with every encode. The disk-based originals walker has the
same hole.

## Requirements

- The storage migration handles the streaming prefix. Decide deliberately between two answers and
  implement one:
  - **move the segments too**, planned like any other object class, verified before the source
    copy is dropped, in keeping with how the migration already treats everything else; or
  - **leave them behind and drop the rendition rows** for what was left, so the catalogue stops
    claiming a clip is streamable and the ordinary encode backfill can rebuild it.
  Whichever is chosen, the outcome that must be impossible is the one that exists today: rows
  saying a clip streams while its segments are unreachable.
- The backup classifies the streaming prefix as derived, not as an original — the same judgement
  it already applies to thumbnails, which are cached elsewhere and never backed up. Renditions are
  reproducible from the original by the encode job, so they do not belong in a backup. Fix both
  the bucket lister and the disk walker.
- Restoring a backup taken *before* this fix must not break: extra objects in the backup are
  tolerated, not fatal.
- After a restore, a video whose segments were not restored must end up in a state the ordinary
  encode backfill repairs. State plainly in the restore documentation what happens to streaming
  renditions on a restore and what to run afterwards — that document does not mention them at all
  today.
- Add a regression test that fails if a new prefix appears in the store that neither operation
  classifies. The point is not to test today's prefixes but to make the next one impossible to
  forget.

## Documentation

`docs/RESTORE.md` gains the streaming renditions in its account of what is and is not restored.
`docs/OPERATIONS.md` gains a sentence in the backup section on what the backup deliberately omits
and why. `docs/PACKAGES.md` gets the changed packages.

## Verification

The backup change is measurable: on a library with encoded videos, the object count and the byte
count of a backup run must drop by the size of the streaming prefix, and a second run must not
re-upload it. Report the before and after numbers.
