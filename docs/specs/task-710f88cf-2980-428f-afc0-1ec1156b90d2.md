# Filter the library by who uploaded the photos

After an event several people upload into the same album, and I want to see one person's
contribution and take it with me. The uploader becomes a first-class filter: a control in the
filter bar, a `uploader:` key in the query language, and one click from a photo's detail.

## Requirements

### The facet — who uploaded into what I am looking at

- New `GET /api/v1/photos/uploaders` (RequireAuth) answers the list of users who uploaded at
  least one photo **within the currently applied filter**, each with a photo count, ordered by
  count descending. In an event album it therefore lists that event's contributors, not every
  account on the instance.
- It accepts the same filter parameters as `GET /photos` (album, label, person, date range,
  place, camera…), exactly the way `GET /photos/years` already does — mirror that handler.
- Photos with no uploader (imported items) are reported as their own entry, not silently
  dropped, so the count adds up to what the grid shows.

### The query language

- `internal/query` gains `uploader:` (text, so `*` wildcards work like the other text keys), plus
  two reserved values:
  - `uploader:me` — photos uploaded by the caller. Resolved outside the parser, the way
    `person:me` is (`internal/personme`); the parser must stay caller-blind.
  - `uploader:none` — photos with no uploader at all (imported).
- A plain `uploader:tomas` matches the user's username or display name, case-insensitively and
  diacritics-insensitively, the way the other text filters match.
- The existing `?uploader=<user uid>` list parameter keeps working unchanged — it is what the
  filter control sets, and saved searches may already carry it.
- The key is documented in the query-language help the way every other key is.

### The controls

- `FilterBar` gains an uploader select, populated from the facet: each entry shows the person's
  name and their count in the current view, with "anyone" as the default and "imported" for the
  no-uploader group. Picking someone narrows the grid; the choice lives in the URL query params
  like every other filter, so Back works.
- The detail page's "Uploaded by" row becomes a link to the library filtered by that person —
  the shortest path to "show me everything this person contributed".
- Combining uploader with an album is the case this exists for: album + uploader + select all +
  the existing bulk actions must work together with no special-casing.

## Implementation notes

- `internal/photoapi/years.go` is the model for the facet endpoint: same parameter parsing, same
  scoping, one query, no N+1.
- The store already filters on `uploaded_by` (`internal/photos/store_list.go`); matching by name
  needs a join to the users table rather than a second round trip to resolve a UID first.
- The pending task `3f914ba8` also edits the detail page's "Uploaded by" row (it adds the upload
  time next to it). Whichever of the two runs second must keep the other's change.
- Tests: parser unit tests for `uploader:` including `me`/`none`/wildcards; integration tests for
  the facet endpoint (scoped by album, counts correct, no-uploader entry) and for the store
  filter; vitest for the select and for the detail link.
- Docs: `docs/API.md` for the endpoint, `docs/FRONTEND.md` for the control, and the query
  language's own documentation for the new key.
