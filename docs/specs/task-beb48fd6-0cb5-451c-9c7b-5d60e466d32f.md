# iOS PWA: fullscreen modal controls land under the status bar

A fullscreen Bootstrap modal ignores the safe-area insets, so in the iOS PWA its close button sits
under the status bar — on the battery indicator — where the tap belongs to the system and the
overlay cannot be closed.

## Background

`web/index.html` ships `viewport-fit=cover` together with
`apple-mobile-web-app-status-bar-style=black-translucent`, so in iOS standalone the page paints
under the status bar. The app answers that everywhere with `env(safe-area-inset-*)` — the
`/outliers` page header itself does (`components/review/review.css:39`) — but **nothing in `web/src`
touches `.modal-header`, `.modal-content` or `.modal-fullscreen`.** A fullscreen modal therefore
starts at y=0.

Two modals are affected:

- `ReviewLightbox` (`components/review/ReviewLightbox.tsx`) is `fullscreen` always. Its close button
  sits in `Modal.Header`, pushed right with `ms-auto`, which puts it exactly under the battery.
  Reported from `/outliers?subject=…` on an iPhone, but it is the same overlay on `/faces`,
  `/recognition` and their siblings.
- `SearchQueryHelp` (`components/search/SearchQueryHelp.tsx`) is `fullscreen="sm-down"`, so on a
  phone its Bootstrap `closeButton` has the same problem.

## Requirements

- Fix it once, in `web/src/styles/app.css`, for any fullscreen modal — not with a patch per
  component. A fullscreen modal's `.modal-content` is inset by all four safe-area insets, so its
  surface still paints edge to edge (the background lies under the padding) while every control
  moves inside the safe area.
- `.modal-fullscreen` takes the rule unconditionally: `env()` resolves to zero wherever there are no
  insets, so a desktop or Android modal is unchanged.
- The `.modal-fullscreen-sm-down` variant takes it **inside the same `max-width: 575.98px` media
  query Bootstrap uses for it**. Unconditionally it would add dead padding to the windowed modal
  that class renders above the breakpoint — visible on an iPad in standalone, where the top inset is
  non-zero but the modal is nowhere near the status bar.
- The bottom inset must be part of it: the lightbox's row of buttons is the last thing in
  `Modal.Body` and otherwise sits under the home indicator.
- Left and right insets too, for landscape on a notched phone — the close button is at the far right.
- Do not change `index.html`, the manifest or the status-bar style. Painting under the status bar is
  deliberate; only the controls have to respect it.
- The lightbox's stage needs no change and must not regress: `.review-lightbox__stage` is
  `container-type: size`, so `ReviewStage`'s `100cqh` cap remeasures against the inset box on its own
  and the photo keeps fitting the visible area.

## Testing

- A CSS-rule assertion in the style the repo already uses (`ruleBody`, as in
  `components/people/Outliers.test.tsx`): the fullscreen-modal rule exists and names all four
  `safe-area-inset-*` values, and the `-sm-down` one is inside the phone media query. Mind the
  first-match trap — pass `ruleBody` its `contains` argument.
- `ReviewLightbox` and `SearchQueryHelp` component tests must still pass untouched: this is CSS
  only, no markup or behaviour changes.
- `env()` insets are zero in desktop Chromium and cannot be emulated, so neither `make check` nor
  agent-browser can see the bug. Prove the geometry with a standalone static harness (the project's
  usual trick) in which the four `env()` calls are replaced by literal iPhone inset values: measure
  the close button's rect with and without the fix and show it moved clear of the top inset. Report
  the numbers. Final confirmation is the user's own iPhone PWA and is not yours to claim.

## Docs

- `docs/FRONTEND.md`: record that fullscreen modals inherit the safe-area inset from one rule in
  `app.css`, next to the existing safe-area notes, so the next fullscreen modal does not re-learn
  this.
- `CLAUDE.md` needs no change: styling only, no package added or removed.
