# A filename can date a photo to the year 9009

`internal/exif/filename.go`, in `timeFromGroups`, validates only that the captured numbers
round-trip to the same calendar date — so it correctly rejects month 13 and day 32, but it
places no plausibility bound on the **year**. Any run of digits in a filename that happens
to form a valid calendar date is accepted, however absurd, and is then stored as the
photo's capture date with day precision and `taken_at_source = "filename"`.

## Evidence

A Facebook download in a real sample triggers it:

```
90090310_638783213372240_7483353598378639360_n.jpg
  -> taken_at 9009-03-10, taken_at_source "filename", precision "day"
```

The leading `90090310` is a Facebook asset id, not a date. The file carries no EXIF date at
all (Facebook strips EXIF; `exiftool` returns only FileModifyDate), so the filename
fallback is what runs.

The result is visible across the whole interface. The library's year scrubber reads:

```
["9009", "2026", "2025", "2024", "2023", "2022", ... "2010"]
```

on both desktop and phone, the photo sorts first under "Nejnovější" forever, and the year
facets and histograms are skewed. In a 400-photo sample, 5 photos were dated from their
filename and 1 of those (20%) got a nonsense year. Any family archive holding Facebook or
WhatsApp downloads will hit this, because those filenames are long digit runs.

## Requirements

- A date parsed from a filename must be rejected when its year is not plausible for a
  photograph. Use a lower bound at the birth of photography (1826) and an upper bound of
  roughly the current year plus one, so a camera with a slightly wrong clock still passes
  but an asset id does not.
- A rejected filename date must fall through to the same "no capture date" outcome the
  code already has for a file with no date, not to some new third state. Such a photo must
  be findable with `dated:no`, exactly like any other undated photo.
- The bound applies only to the filename heuristic. A genuine EXIF date must keep whatever
  it says, even if odd — an EXIF date is an assertion by the camera, a filename match is a
  guess, and only the guess should be second-guessed.
- Do not narrow which filename *patterns* are recognised; the change is about the year
  value, not the shapes matched.

## Testing

Extend the existing table tests in `internal/exif/filename_test.go`: the real Facebook
filename above must yield no date; a normal `IMG_20230115_143052.jpg` must still parse; the
boundary years just inside and just outside the accepted range must land on the right side
of it. Existing cases must keep passing unchanged.

## Note on production data

Production does not currently show this, because those photos were imported from PhotoPrism
with a date already attached. The same bytes uploaded directly reproduce it every time, so
this is about the ingest path, not about repairing existing rows. Do not write a data
migration; if any rows need fixing later that is a separate decision for the library owner.
