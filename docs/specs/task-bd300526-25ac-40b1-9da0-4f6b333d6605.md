# Face grouping never starts and nothing in the interface can start it

Face detection runs automatically, but face *grouping* never happens on its own and the
interface offers no way to ask for it. On any instance where nobody has manually called
the API, "Lidé" and "Skupiny obličejů" stay permanently empty and the review game has no
face candidates to offer.

## Evidence

Observed on a test instance that had been ingesting photos for an hour:

```
faces: 439   unassigned: 439
jobs by type: face_detect, image_embed, ocr, sidecar     <- no face_cluster, ever
face_clusters: 0
```

One manual `POST /api/v1/process/clusters` then returned `{"scheduled":true}` and 61
groups appeared immediately. The feature works correctly; it is simply unreachable.

## Why it happens

- Opening `/people/clusters` calls `clusterjob.EnsureSummaries`, which by its own doc
  comment "regroups nothing" — it only builds summaries for clusters that already exist.
  With zero clusters nothing is pending, so it enqueues nothing.
- Grouping only happens on a `Recluster` payload, which today is reachable solely through
  the maintainer-only `POST /api/v1/process/clusters`.
- The frontend never calls that endpoint: `grep -rn "process/" web/src/services` finds
  only the unrelated per-photo `process/{step}` call, and no "recluster" string exists
  anywhere under `web/src`.

## Requirements

- A library that has unassigned faces and no clusters must end up with clusters without
  anyone calling the API by hand. Decide whether that is best done by having the face
  groups page schedule a grouping pass when it finds unassigned faces and no clusters, or
  by scheduling one after face detection completes — pick whichever fits the existing job
  and service boundaries, and say why in the commit message.
- Scheduling must stay idempotent and bounded: at most one grouping pass in flight, and
  repeated page loads must collapse into the pass already queued rather than piling up.
- Browsing must never change who a face belongs to. Only grouping of *unassigned* faces
  may be triggered this way; an already-named face must not be regrouped or reassigned.
- Give a user who cannot trigger it implicitly a way to see what is happening: while a
  grouping pass is queued or running, the face groups page should say so rather than
  showing a bare empty state.
- Correct the empty state text on `/people/clusters`. It currently promises "Nové skupiny
  se tu objeví, jakmile aplikace rozpozná obličeje na vašich fotkách", which is not true
  today. After this change it must either be true, or say accurately what the user is
  waiting for. Update both the Czech and English catalogues.

## Edge cases

- A library with zero faces at all must not schedule anything and must keep a calm empty
  state, not a permanent "working…" message.
- A viewer or editor (not maintainer) must reach the same outcome — the whole point is
  that non-maintainers currently cannot get face groups at all.
- Repeatedly reloading the page must not enqueue a pass per reload.

## Testing

Integration coverage for the scheduling decision against a real test database: a library
with unassigned faces and no clusters ends up with a grouping pass enqueued exactly once;
a library already holding clusters does not re-enqueue; a library with no faces enqueues
nothing. Add a frontend test for whichever empty/pending states you introduce.
