# Attaching a person by hand, with no face and no box

A person is linked to a media item only through a face marker created from a face the detector
found. That covers less than it looks. Face detection on a video only ever sees the poster frame,
so anyone appearing later in the clip is invisible to it; and on a photo the detector misses
profiles, backs of heads and faces in a crowd. In all those cases there is no way to record who
is in the picture. This task adds the backend for saying so by hand: no bounding box, no detected
face, no embedding.

This is backend only. The user interface is separate work.

## Requirements

- A user with write access can attach a subject (person, pet or other) to any media item — image,
  live photo or video — giving only the subject. No bounding box, no face index.
- Attaching is idempotent: attaching the same subject twice leaves exactly one link and answers
  success, not a conflict.
- The link can be removed again by a user with write access.
- Once attached, the media behaves like any other media of that person:
  - it appears in the subject's photo gallery,
  - it is found by the `person:` search filter and by the person scope,
  - it counts toward the subject's media count on the people listing and the subject detail,
  - it is written into the photo's metadata sidecar, so the link survives losing the database,
  - subject merge carries it over exactly as face markers are carried over,
  - it is audited in the same transaction as the mutation, like every other curation write.
- Attaching to a subject or a photo that does not exist answers 404; without write permission,
  403; an already-attached subject answers the same success body as the first attach.

## The hazard: everything that reads markers

Every person-to-media linkage in this app runs through the marker table, and roughly a dozen
packages read it. Adding a new kind of row there silently changes all of them. A hand-attached
person has no crop, no geometry and no embedding, so it must never leak into anything that
assumes a face image exists.

Grep the repository for every read of the marker table and decide, query by query, whether the
new kind belongs. At minimum confirm behaviour is unchanged for: the per-photo faces roll-call
and the face overlay payload; face clustering and the cluster listing; candidate search, the
recognition sweep and the review game; outlier detection; duplicate-marker detection; subject
avatar and album/collection cover election — a hand-attached person has no crop to cut an avatar
from and must never win; the nameless-subject repair; the library metrics gauge counting markers
by assigned/unassigned state; the dashboard counts and remaining-work backlogs.

It must never be reported as an unassigned face and never enter a nearest-neighbour search.
Write a test for each surface whose answer is "must be excluded" — a comment is not enough,
because a later change to the query would silently re-include it.

## Data model

Reuse the existing marker table rather than inventing a parallel one — the person filter, the
subject gallery, subject counts, subject merge and the sidecar export all read it already, which
is what makes most of the behaviour above fall out for free. Its type column already carries a
CHECK constraint with two kinds and a third that carries no geometry fits. Whatever representation
you pick, the constraints above are what matter.

## Also fix: the processing report lies about faces on videos

The per-photo processing report classifies the face-detection step as "does not apply" to a
video. That is not true: the upload pipeline enqueues face detection for every media type and the
detector runs on the video's poster frame — on the staging instance six faces are recorded across
two videos. Because the report resolves persisted evidence before the applies-rule, the lie is
invisible once detection has run, but a freshly uploaded video reports "not applicable" while its
face-detection job is queued and about to run.

Make the report tell the truth: face detection applies to a video. Check the same question for
the neighbouring steps while you are there — text recognition genuinely is skipped for videos in
both the job and the backfill queries, so that one is correct as it stands. Update the API
documentation, which repeats the wrong claim.

## API

Add under `/api/v1`, guarded by the write role, and document in `docs/API.md`:

- `POST /photos/{uid}/people` with a body naming the subject to attach.
- `DELETE /photos/{uid}/people/{subject_uid}` to detach.
- `GET /photos/{uid}` carries a `people` array of the hand-attached subjects, each giving at least
  the subject uid, name and type, so a client renders the list without a second round trip.
- Both mutations answer with the resulting `people` array.

## Out of scope

- The frontend.
- `kukatko ctl` support for the new endpoints.
- Time-coded tags (at which second of a video the person appears).
- Changing what face detection looks at: it still only sees the poster frame.
